# 全量代码扫描操作文档

## 一、原理说明

### 1.1 背景:为什么需要全量扫描

代码检查平台(基于 Jenkins)默认**按 MR(合并请求)的变动文件**触发扫描:每次提交增量 MR,只扫描本次改动的文件。这种"增量扫描"模式高效,但有一个局限——**历史代码中已存在的问题不会被增量扫描覆盖**。只有当某个老文件被再次改动时,它的问题才会被发现。

因此,定期(如每月、每个迭代、发版前)需要做一次**全量扫描**,把仓库里所有自主维护的代码一次性送入检查平台,确保存量问题也能被识别和治理。

### 1.2 扫描触发机制:Jenkins 如何决定扫哪些文件

GitCode(基于 GitLab)与 Jenkins 的集成流程如下:

1. **创建 MR**:在 GitCode 上创建合并请求(源分支 → 目标分支)。
2. **评论触发(关键)**:在 MR 评论区手动回复 `build`(评论内容仅 `build` 一词),由 COO_CI 机器人监听并启动 Jenkins 流水线。**仅创建 MR 不会自动触发扫描。**
3. **CI 启动**:COO_CI 回复「CI 启动」,附 Jenkins 构建与 CI Deck 报告链接。
4. **计算 MR diff**:Jenkins 拉取源分支与目标分支的**差异文件列表**(等价于 `git diff target...src --name-only`)。
5. **执行静态检查**:对 diff 命中的文件,按语言分发到对应检查器(pylint / flake8 / sonarqube / SQLGuardian / codemars 等)。
6. **CI 结束**:COO_CI 回复「CI 结束」,附执行结果(如 `Codearts Check:执行 SUCCESS,质量 未通过`、`平台测试:未执行`)。

**关键点**:
- **触发方式 = 创建 MR + 评论区回复 `build`,二者缺一不可**。仅创建 MR 不会触发任何扫描。
- **扫描范围 = MR 的 diff 文件集合,而不是整个分支**。这就回答了"如何全量扫描":只要让一次 MR 的 diff 文件集合 = 你想扫的全部代码即可。

### 1.3 核心思路:构造"全量 diff"的 MR

MR 的 diff 由「源分支」相对「目标分支」的差异决定:

- 若目标分支**与源分支相同**,diff 为空,扫不到任何文件。
- 若目标分支**为空(0 文件)**,则 diff = 源分支的全部文件。
- 若目标分支**是某个旧基线**,则 diff = 自旧基线以来的增量。

因此,构造"全量 diff" MR 的方法就是:**目标分支保持空,源分支放入待扫的全量代码**。

| 分支 | 作用 | 内容 |
| --- | --- | --- |
| `<用户名>/dev-scan-base` | MR 目标(基线) | **空分支**(0 文件,基于主线创建并清空索引,与主线有共同祖先) |
| `<用户名>/dev-scan-src` | MR 源 | 最新主线代码 **去除 不需要扫描的目录** |

因为 base 是空的,MR `src → base` 的 diff 就是 src 的全部文件。Jenkins 据此触发全量扫描并生成报告。

> **本项目示例**:主线为 `dev` 分支(跟踪 **2543** 个文件),需排除的目录为 `open_source`(占 **2509** 个文件,包含 `codebase-memory-mcp` 和 `codegraph` 两个第三方开源项目,不纳入自主扫描);`open_source` 整体被 git 跟踪,仅部分构建产物在 `.gitignore`,故需在 src 分支用 `git rm --cached` 显式移除整个目录。源分支最终包含约 **34** 个项目自主开发文件。

### 1.4 为什么 base 必须保持"空基线"

全量扫描的关键前提是 **base 始终为空**:

- 若 MR 被真正合并到 base,base 就有了代码,下次 `src → base` 的 diff 就只剩"增量",不再是全量。
- 所以这套流程里 **MR 仅用于触发扫描,不真正合并**;扫描完成后关闭 MR 即可。
- 万一 base 被误合并污染,按第三节步骤 5 的命令把它重置回空基线再继续。

### 1.5 为什么 base 必须与 src 有共同祖先(关键)

Jenkins 在扫描前会执行 `git merge` 把源分支合到目标分支来计算 diff。Git 的合并要求**两个分支必须有共同祖先提交**,否则会报错:

```
fatal: refusing to merge unrelated histories
```

错误码 `CH.1010204.453`。这意味着 base 和 src **不能是两条独立的历史线**。

| 创建方式 | base 与 src 是否有共同祖先 | Jenkins 合并 |
| --- | --- | --- |
| base 用 `git checkout --orphan` 创建(独立历史) | **无** | **失败(refusing to merge unrelated histories)** |
| base 基于主线 dev 创建(`git checkout -b`)+ 清空索引 | **有**(共同祖先 = base 的父提交,在 dev 上) | 成功 |
| src 基于 base 创建(`git checkout -b src origin/base`) | **有**(共同祖先 = base 自身) | 成功 |

**正确做法**:
- base 基于主线 dev 创建(**不要用 `--orphan`**),再 `git rm -rf --cached .` 清空索引 → base 有 0 文件,但历史连接到 dev。
- src 基于 base 创建(`git checkout -b src origin/<base>`),再 `git checkout origin/dev -- .` 把 dev 的文件拉进来 → src 的起点就是 base,二者共同祖先 = base 自身。

这样 Jenkins 的 `git merge` 能正常执行,扫描才会触发。

### 1.6 为什么排除某些目录

通常以下内容不纳入扫描:

- **第三方/开源代码**(`open_source/`、`vendor/`、`node_modules/`、第三方 SDK 等):非自主维护,扫了也无法修改,徒增噪音与扫描耗时。
- **自动生成代码**(如 `*.gen.py`、构建产物):由工具产出,问题应在生成器侧解决。
- **大型数据/模型文件**:非源代码,不在静态检查范围。

具体排除哪些目录,各项目按自身情况决定(见第八节"适配其他项目")。注意区分两种"排除":

| 情形 | 是否被 git 跟踪 | 处理方式 |
| --- | --- | --- |
| 已在 `.gitignore`(如 `node_modules`、`__pycache__`) | 否 | 无需处理,本就不会进入 diff |
| 未在 `.gitignore` 但不想扫(如 `open_source`) | 是 | 需在 src 分支用 `git rm -r --cached` 移除 |

### 1.7 分支命名约定

- 使用**个人命名空间**(`<用户名>/dev-scan-*`)而非仓库默认命名空间,避免与他人的扫描分支冲突,也便于各自维护。
- `dev-scan-src` 与 `dev-scan-base` 是约定俗成的语义命名,可一眼识别用途。
- 本文档分支命名空间 `hetaoist` 取自本地 `git config user.name`。若你的 GitCode 用户名与之不同,请全局替换为实际用户名。

## 二、前置准备(仅首次,创建自己的空基线分支)

本节用于首次创建你自己的 `hetaoist/dev-scan-base` 空基线分支。**仅需执行一次**,后续每次扫描复用即可(若你打算直接复用同事已有的 `wuanyong/dev-scan-*` 分支并有推送权限,可跳过本节,后续命令把 `hetaoist` 换成 `wuanyong` 即可)。

```powershell
# 1. 切到 dev 并拉最新
git checkout dev
git pull origin dev

# 2. 基于 dev 创建 base 分支(不要用 --orphan,否则与 src 无共同祖先,Jenkins 合并会报 unrelated histories)
git checkout -b hetaoist/dev-scan-base

# 3. 清空索引(仅从索引移除,不删工作区文件;工作区文件保留,对该分支为 untracked)
git rm -rf --cached .

# 4. 提交一个空 commit 作为基线(此时工作区文件已从索引移除,commit 后 base 为 0 文件,但历史仍连接 dev)
git commit --allow-empty -m "empty baseline for dev scan"

# 5. 推送到远程
git push origin hetaoist/dev-scan-base

# 6. 切回 dev(此时工作区文件对 base 分支为 untracked,git 会拦阻普通 checkout,用 -f 强制覆盖;内容与 dev 一致,安全)
git checkout -f dev
git pull origin dev
```

验证 base 创建正确:

```powershell
git fetch origin hetaoist/dev-scan-base
# 期望 0 文件
git ls-tree -r --name-only origin/hetaoist/dev-scan-base | Measure-Object -Line
# 期望输出一个 commit hash(与 dev 的共同祖先,非空)
git merge-base origin/hetaoist/dev-scan-base origin/dev
```

## 三、每次全量扫描操作步骤

> 下文以你自己的 `hetaoist/dev-scan-src` 和 `hetaoist/dev-scan-base` 为例。

### 步骤 1:确保工作区干净并切到 dev

```powershell
git status                  # 确认无未提交改动;若有先 stash 或 commit
git checkout dev
git pull origin dev
```

### 步骤 2:基于 base 创建 src 分支(关键:不要基于 dev)

```powershell
# 拉取最新 base
git fetch origin hetaoist/dev-scan-base

# 删除本地旧分支(如有),基于远程 base 重建——确保 src 与 base 有共同祖先
git branch -D hetaoist/dev-scan-src 2>$null
git checkout -b hetaoist/dev-scan-src origin/hetaoist/dev-scan-base

# 从 dev 把全部文件拉到当前分支的工作区与索引(分支起点仍是 base,不会改变共同祖先)
git checkout origin/dev -- .
```

> ⚠ **不要写成 `git checkout -b hetaoist/dev-scan-src`(基于 dev)**。若 src 基于 dev 创建,虽然 src 与 base 都源自 dev,但 src 的起点是 dev 最新 commit,base 的起点是 dev 上某个旧 commit,**二者的共同祖先 = 那个旧 commit**。这在大多数情况下也能合并,但一旦 base 被重置过、或 dev 在两次操作之间前进过,共同祖先可能丢失或变得很旧,引发 `refusing to merge unrelated histories` 或 diff 异常。**基于 base 创建 src 是最稳妥的做法,共同祖先就是 base 自身。**

### 步骤 3:从 src 移除 open_source

```powershell
# 仅从 git 索引删除,工作区文件保留(push 后切回 dev 会自动恢复)
git rm -r --cached open_source

# 提交(此时分支不再包含 open_source)
git commit -m "dev full scan: all codebase except open_source"
```

说明:
- `--cached` 只从索引删除,**不会真的删除本地 `open_source` 文件夹**,不影响本地开发。
- 切回 `dev` 分支后,`open_source` 会重新被跟踪,文件保持原样。

### 步骤 4:强推 scan-src 到远程

```powershell
git push origin hetaoist/dev-scan-src --force-with-lease
```

使用 `--force-with-lease` 是因为该分支每次都要覆盖为最新内容。首次 push 会自动在远程创建 `hetaoist/dev-scan-src` 分支。

### 步骤 5:确认 scan-base 仍是空基线且与 dev 有共同祖先

```powershell
git fetch origin hetaoist/dev-scan-base
# 检查文件数,应为 0
git ls-tree -r --name-only origin/hetaoist/dev-scan-base | Measure-Object -Line
# 检查与 dev 的共同祖先,应输出一个 commit hash(非空)
git merge-base origin/hetaoist/dev-scan-base origin/dev
```

若文件数返回 `0` 且共同祖先非空,说明 base 正常,继续步骤 6。

若文件数非 0(被之前的 MR 合并污染),需重置回空基线(**不要用 --orphan**,要基于 dev 重建):

```powershell
git checkout dev
git pull origin dev
git branch -D hetaoist/dev-scan-base
git checkout -b hetaoist/dev-scan-base
git rm -rf --cached .
git commit --allow-empty -m "empty baseline for dev scan"
git push origin hetaoist/dev-scan-base --force-with-lease
git checkout -f dev
```

### 步骤 6:在 GitCode 创建 MR(scan-src → scan-base)

**方式 A:网页创建(推荐)**

1. 浏览器打开仓库:https://gitcode.com/hi_kb_base/rag_mcp_server
2. 点击「合并请求 / Merge Requests」→「新建合并请求」
3. 源分支选 `hetaoist/dev-scan-src`,目标分支选 `hetaoist/dev-scan-base`
4. 标题填:`全量代码扫描 YYYY-MM-DD`(日期便于追溯)
5. 创建后检查「变动文件」数量应约为项目自主开发代码文件数(即除 open_source 外的全量),确认无误
6. **在 MR 评论区回复 `build`**(评论内容仅 `build` 一词,提交即可)触发 CI

> ⚠ **触发扫描的关键一步**:仅创建 MR **不会**自动触发扫描,必须在 MR 评论区手动回复 `build`,COO_CI 机器人收到后才会启动 Jenkins。回复后留意 COO_CI 的「CI 启动」评论确认已触发。

**方式 B:push 时自动创建 MR(GitCode 支持 GitLab 风格 push options)**

```powershell
git push origin hetaoist/dev-scan-src --force-with-lease `
  -o merge_request.create `
  -o merge_request.target=hetaoist/dev-scan-base `
  -o merge_request.title="全量代码扫描"
```

> push options 若不生效,回退到方式 A。

### 步骤 7:等待 CI 结束并查看报告

- 回复 `build` 后,COO_CI 会回复「CI 启动」,随后 Jenkins 扫描 MR 的全部变动文件
- 扫描完成后,COO_CI 回复「CI 结束」,内容形如:
  - `Codearts Check:执行 SUCCESS,质量 未通过`
  - `平台测试:未执行(至少一项检查质量未通过或未确认)`
- 点击 COO_CI 评论里的「Jenkins 构建」/「CI Deck 报告」链接查看明细;汇总报告可在代码检查平台查看(参考此前 `model_issues1.json` 报告)

### 步骤 8:清理本地分支(可选)

```powershell
# 此时仍在 src 分支,工作区有 untracked 的 open_source,切回 dev 需 -f
git checkout -f dev
git branch -D hetaoist/dev-scan-src
```

| 检查项 | 期望值 | 命令 |
| --- | --- | --- |
| scan-src 不含 open_source | 无输出 | `git ls-tree -r --name-only origin/hetaoist/dev-scan-src \| Select-String open_source` |

| scan-src 与 base 共同祖先 | 非空(= base 自身) | `git merge-base origin/hetaoist/dev-scan-src origin/hetaoist/dev-scan-base` |
| MR 变动文件数 | 约等于 scan-src 文件数 | GitCode MR 页面「Files changed」 |

## 五、注意事项

1. **不要真的合并 MR 到 base**:MR 仅用于触发 Jenkins 扫描,扫描完成后**关闭 MR 即可**,不要点「合并」。保持 base 为空基线,下次扫描才能再次生成全量 diff。
2. **base 必须与 src 有共同祖先(关键)**:Jenkins 扫描前会 `git merge` 源到目标,若两者无共同祖先会报 `fatal: refusing to merge unrelated histories`(错误码 `CH.1010204.453`)。**切勿用 `git checkout --orphan` 创建 base**;正确做法是 `git checkout -b <base>` 基于 dev 创建再清空索引。src 也应基于 base 创建(`git checkout -b <src> origin/<base>` + `git checkout origin/dev -- .`),确保共同祖先 = base 自身。
3. **`open_source` 删除用 `--cached`**:避免误删本地开发依赖的文件;push 后切回 `dev` 即可恢复。
4. **每次都要 force push src**:因为 src 分支需要每次刷新为最新 dev,`--force-with-lease` 比 `--force` 更安全(防止覆盖他人改动)。
5. **MR 变动文件数应接近 scan-src 文件数**:若远小于该值,说明 base 被污染(非空),按步骤 5 重置 base。
6. **分支命名空间**:本文档使用 `hetaoist/`(本地 `git config user.name`)。若你的 GitCode 用户名不同,请把文档中的 `hetaoist` 全局替换为实际用户名;或直接复用同事的 `wuanyong/dev-scan-*` 分支(需有推送权限)。
7. **`--cached` 模式下切回主线需 `-f`**:本文档采用 `git rm -r --cached` 移除目录(不删本地文件),被移除的文件对该分支变为 untracked。切回 `dev` 时 git 会因"覆盖 untracked 文件"而拦阻,需用 `git checkout -f dev` 强制切换(文件内容与 dev 一致,安全)。步骤 8 清理本地分支、脚本结尾切回主线均需 `-f`。

## 六、一键脚本(可选)

将以下内容保存为 `do-full-scan.ps1`,每次扫描只需执行 `.\do-full-scan.ps1`:

```powershell
# do-full-scan.ps1
# 全量代码扫描一键脚本:基于 base 重建 scan-src 为最新 dev(去 open_source),并提示发 MR
$ErrorActionPreference = 'Stop'

$srcBranch  = 'hetaoist/dev-scan-src'
$baseBranch = 'hetaoist/dev-scan-base'
$mainBranch = 'dev'

Write-Host "==> 切到 $mainBranch 并拉最新"
git checkout $mainBranch
git pull origin $mainBranch

Write-Host "==> 拉取最新 base"
git fetch origin $baseBranch

Write-Host "==> 基于 base 重建 $srcBranch(确保共同祖先)"
git branch -D $srcBranch 2>$null
git checkout -b $srcBranch "origin/$baseBranch"

Write-Host "==> 从 $mainBranch 拉取全部文件到 src"
git checkout "origin/$mainBranch" -- .

Write-Host "==> 移除 open_source(仅从索引)"
if (Test-Path open_source) {
    git rm -r --cached open_source | Out-Null
} else {
    Write-Host "    open_source 不存在,跳过"
}
git commit -m "dev full scan: all codebase except open_source" | Out-Null

Write-Host "==> 强推 $srcBranch"
git push origin $srcBranch --force-with-lease

Write-Host "==> 校验 $baseBranch 是否为空基线且与 $mainBranch 有共同祖先"
$baseCount   = (git ls-tree -r --name-only "origin/$baseBranch" | Measure-Object -Line).Lines
$baseAncestor = git merge-base "origin/$baseBranch" "origin/$mainBranch"
Write-Host "    $baseBranch 文件数: $baseCount"
Write-Host "    $baseBranch 与 $mainBranch 共同祖先: $baseAncestor"
if ($baseCount -ne 0 -or -not $baseAncestor) {
    Write-Host "    警告:base 异常,请按文档步骤 5 重置后再发 MR"
    exit 1
}

$srcCount    = (git ls-tree -r --name-only "origin/$srcBranch" | Measure-Object -Line).Lines
$srcAncestor = git merge-base "origin/$srcBranch" "origin/$baseBranch"
$hasOpenSource = git ls-tree -r --name-only "origin/$srcBranch" | Select-String -Pattern 'open_source'
Write-Host "    $srcBranch 文件数: $srcCount"
Write-Host "    $srcBranch 与 $base 共同祖先: $srcAncestor"
Write-Host "    open_source 残留: $(if ($hasOpenSource) { '是(异常)' } else { '无(正常)' })"

Write-Host ""
Write-Host "==> 完成。请按以下步骤触发扫描:"
Write-Host "    1) 在 GitCode 创建 MR: $srcBranch -> $baseBranch"
Write-Host "       https://gitcode.com/hi_kb_base/rag_mcp_server"
Write-Host "    2) 在 MR 评论区回复 build (仅一个单词) 启动 CI"
Write-Host "    3) 等待 COO_CI 回复 CI 结束 后查看报告"
Write-Host ""
Write-Host "==> 清理本地分支(可选):"
Write-Host "    git checkout -f $mainBranch; git branch -D $srcBranch"

# 此时在 src 分支,工作区有 untracked 的 open_source,切回主线需 -f
git checkout -f $mainBranch
```

## 七、流程小结(一句话)

> 每次扫描:**确保 base 基于主线且为空(0 文件,有共同祖先)→ 基于 base 创建 src,从主线拉全部文件,移除排除目录 → 强推 src → 在 GitCode 发 MR(src → 空的 base)→ 在 MR 评论区回复 `build` 触发 CI → Jenkins 全量扫描**。base 始终保持空基线,不要真正合并 MR。

## 八、适配其他项目(指南)

本流程适用于任何「GitCode 仓库 + Jenkins MR 扫描」组合的项目。适配新项目时,按以下清单调整。

### 8.1 必改项

| 项 | 本文档取值 | 适配时改为 |
| --- | --- | --- |
| 主线分支 | `dev` | 目标项目的主线(如 `main` / `master` / `dev`) |
| 排除目录 | `open_source` | 目标项目里需排除的目录(可为多个,或为空) |
| 命名空间 | `hetaoist` | 你的 GitCode 用户名(或团队约定的命名空间) |
| 仓库地址 | `https://gitcode.com/hi_kb_base/rag_mcp_server` | 目标项目仓库 URL |

> 触发方式(创建 MR 后评论 `build`)、COO_CI 机器人、检查器规则集等均为**平台级约定**,跨项目通用,无需适配。

### 8.2 排除多个目录的写法

若要排除多个目录(如 `open_source`、`vendor`、`third_party`),步骤 3 重复执行:

```powershell
git rm -r --cached open_source
git rm -r --cached vendor
git rm -r --cached third_party
git commit -m "full scan: all codebase except excluded dirs"
```

或排除指定文件类型(利用 pathspec):

```powershell
# 排除所有 .min.js 压缩文件
git rm -r --cached ':(glob)**/*.min.js'
```

### 8.3 判断哪些目录需要处理

只有「**被 git 跟踪但不想扫描**」的目录才需要 `git rm -r --cached`;已在 `.gitignore` 的目录本就不会进入 diff,无需处理。判断方法:

```powershell
# 查看某目录是否被 git 跟踪(返回行数 >0 表示被跟踪)
git ls-files <目录名> | Measure-Object -Line
```

### 8.4 一键脚本的泛化

把 `do-full-scan.ps1` 顶部的硬编码改为参数,即可跨项目复用:

```powershell
# do-full-scan.ps1(参数化版本)
param(
    [string]$MainBranch    = 'dev',
    [string]$SrcBranch     = 'hetaoist/dev-scan-src',
    [string]$BaseBranch    = 'hetaoist/dev-scan-base',
    [string[]]$ExcludePaths = @('open_source')
)
$ErrorActionPreference = 'Stop'

git checkout $MainBranch
git pull origin $MainBranch
git fetch origin $BaseBranch

# 基于 base 创建 src(确保共同祖先)
git branch -D $SrcBranch 2>$null
git checkout -b $SrcBranch "origin/$BaseBranch"
git checkout "origin/$MainBranch" -- .

foreach ($p in $ExcludePaths) {
    if (Test-Path $p) { git rm -r --cached $p | Out-Null }
}
git commit -m "full scan: $MainBranch except $($ExcludePaths -join ',')" | Out-Null
git push origin $SrcBranch --force-with-lease

# 校验 base 为空且有共同祖先
$baseCount    = (git ls-tree -r --name-only "origin/$BaseBranch" | Measure-Object -Line).Lines
$baseAncestor = git merge-base "origin/$BaseBranch" "origin/$MainBranch"
if ($baseCount -ne 0 -or -not $baseAncestor) {
    Write-Host "警告:base 异常(文件数=$baseCount, 共同祖先=$baseAncestor),请先重置 $BaseBranch"
    exit 1
}

Write-Host "完成,请在 GitCode 创建 MR: $SrcBranch -> $BaseBranch"
# 此时在 src 分支,工作区有 untracked 的排除目录,切回主线需 -f
git checkout -f $MainBranch
```

调用示例:

```powershell
# 默认参数(本项目)
.\do-full-scan.ps1

# 适配其他项目:main 分支 + 排除 vendor 和 third_party
.\do-full-scan.ps1 -MainBranch main -ExcludePaths vendor,third_party
```

### 8.5 常见问题排查

- **回复 build 后 CI 没启动?** 确认评论内容仅为 `build` 一词(无多余字符/空行);确认 MR 状态为 Open(未关闭/未合并);若仍无 COO_CI 响应,联系平台管理员确认机器人服务正常。注意:仅创建 MR 不会自动触发,必须评论 `build`。
- **MR diff 文件数远小于预期?** 大概率是 base 被合入了代码(非空),按步骤 5 重置 base 后重发 MR。
- **报错 `fatal: refusing to merge unrelated histories`(CH.1010204.453)?** base 与 src 无共同祖先。检查:base 是否用 `--orphan` 创建了(错误),改为基于主线创建;src 是否基于 base 创建(正确)而非基于主线。按 1.5 节与第二节重建 base,再按第三节步骤 2 重建 src。
- **push options 不生效?** GitCode 部分版本对 `-o merge_request.*` 支持不完整,回退到网页方式 A 创建 MR。
- **权限不足无法 push 到命名空间?** 确认你的 GitCode 账号对目标仓库有 `Write` 权限;或复用同事已有的扫描分支(需对方授权)。
- **扫描报告为空?** 确认检查器规则集已对目标仓库启用;确认 diff 文件的语言与检查器匹配(如 `.py` 走 pylint,`.sql` 走 SQLGuardian)。
- **open_source 排除后又出现在 diff 里?** 说明该目录被 git 跟踪但 `git rm --cached` 未执行成功,检查 `Test-Path` 与目录名拼写;或该目录被其他分支的 `.gitignore` 忽略导致行为异常。

### 8.6 安全提示

- `git rm -rf --cached .`(创建空基线时清空索引)只在 base 分支上执行,**切勿在 dev/master 等主线分支执行**。
- `--force-with-lease` 会拒绝覆盖远程有新提交的情况;若确需覆盖他人改动,先与对方确认。
- MR 仅用于触发扫描,**不要点「合并」**;扫描报告归档后关闭 MR 即可。
