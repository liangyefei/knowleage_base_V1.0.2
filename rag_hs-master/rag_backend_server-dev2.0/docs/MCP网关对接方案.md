阶段一（聚合转发 + 工具命名空间 + 失败隔离）已完成，**用官方 Quarkiverse 扩展实现协议层**，
并对 CCE dev 的 4 个真实上游跑通验收。实施中实测确认/推翻了原方案里的若干假设，逐条记录：

### 0.1 上游实测基线（原 §6 待确认项 3 已解答）

| 上游 | 端口 | `initialize` 协商版本 | serverInfo.name | 工具数 | 下发 session |
| --- | --- | --- | --- | --- | --- |
| hisi-code-mcp | 9800 | `2025-06-18` | `hisi-code-mcp` | 11 | 是 |
| hisi-codegraph | 9801 | `2024-11-05` | **`hisi-code-mcp`**（与 9800 重名） | 1 | 是 |
| hisi-docs-mcp | 9802 | `2025-06-18` | `hisi-docs-mcp` | 7 | 否 |
| hisi-docs-search | 9803 | `2024-11-05` | `hisi_docs_search_chunk` | 1 | 否 |

**合计 20 个工具。** 三个关键实测结论：

1. **协议版本不统一，但上游对版本不敏感**：9800 对 `2024-11-05` 与 `2025-06-18` 都接受并**原样回显**。
   网关因此按 `2025-03-26` 与上游协商（实测 9800/9802 得 `2025-03-26`），
   对外支持版本由扩展决定——**两端版本分别维护**，与原方案 §2 的口径一致。
2. **传输是纯 JSON，无 SSE**：`GET /mcp` 返回 405，响应 `Content-Type: application/json`。
   原 §5 担心的"旧 SSE-only 实现"不存在。
3. **错误一律走 HTTP 200**：未知工具/方法返回 `200` + JSON-RPC `error` 体
   （如 `-32601`「工具 xxx 不在允许列表」）。**不能只看 HTTP 状态判成败**——网关据此实现。

### 0.2 与原方案的差异

| 项 | 原方案 | 落地实现 | 原因 |
| --- | --- | --- | --- |
| 协议层 | 自研透传（"初始化握手与协议版本协商正常透传"） | **官方扩展 `quarkus-mcp-server-http` 2.0.3** 承担全部协议面 | 用户要求"尽量用官方，不要自己写"；扩展的**编程式 `ToolManager` API** 正好支持运行期动态注册上游工具 |
| 工具注册 | 未指定 | 编程式 `newTool` + 原样透传上游 `inputSchema` | 上游清单是运行期拉取的，注解式 `@Tool` 要求编译期静态方法，不适用 |
| 前缀命名空间 | 阶段 1 固化 | 已落地 `上游名__工具名`；**并额外提供裸名别名** | 实测确认 `hisi_docs_search` 在 9802/9803 都存在，前缀**必需**；裸名别名让 agent 凭直觉调用也能通 |
| 重名工具路由 | 未指定（原写"多义时报错并列出候选"） | **主备路由**：按上游 `priority` 选主，主传输层失败自动切备（9803 主 / 9802 备） | 2026-10-22 定稿口径——重名工具应有一个默认可用入口，而不是把消歧推给 agent |
| 上游清单缓存 | 不缓存 | 一致：启动拉一次 + `POST /gateway/refresh` 手动刷新 | 上游升级版本后调一次即可，不发版 |
| 端口/前缀 | 8080 / 9000 / `/hisilicon-knowledge-mcp` | 一致 | — |

### 0.3 阶段一验收证据（dev 环境真实上游）

- **聚合 20 个工具、0 degraded**，与直连 4 个上游逐项核对一致。
- **同名工具不串台**：`hisi-docs-mcp__hisi_docs_search` 与 `hisi-docs-search__hisi_docs_search`
  各自返回**不同结果**（15 条 / 5 条），证明同名工具确实路由到不同上游。
- **失败隔离**：把 `hisi-codegraph` 指向不可达地址 → 该上游 degraded，
  其余 3 个上游 19 个工具照常列出与调用，端点不被拖死；调用故障上游的工具回**工具级错误**而非 5xx。
- 网关自带 20 个自动化测试（协议面 + 注册表 + 服务冒烟）全绿，且测试完全不依赖外网。

### 0.4 实施中发现、原方案未预见的两点

1. **`hisi_docs_search` 跨上游重名是既成事实**（9802 与 9803），不是"未来风险"。
   前缀命名空间从"阶段 1 固化"变成**上线必需**。
2. **上游工具名（`serverInfo.name`）也可能重名**：9800 与 9801 都自称 `hisi-code-mcp`。
   因此网关上**上游的标识必须用配置里的 `name`，不能信上游自报的 `serverInfo.name`**。

## 1. 目标与定位

`hisilicon-knowledge-mcp-gateway` 是**面向 agent 的入站 MCP 聚合网关**：

- 对外暴露**一个** MCP Streamable HTTP 端点，外部 agent（MCP Client）经此访问模型侧工具
- 对内聚合模型侧**多个** MCP 工具服务（MCP Server），上游列表可配置增减
- **不做 agent 循环、不做 LLM 编排**：tool-calling 循环在外部 agent 侧，网关是转发层
- 模型侧 MCP 服务不直接对外，网关是其唯一入口

### 1.1 链路

```
外部 Agent (MCP Client)
        │  Streamable HTTP + 鉴权（阶段2起）
        ▼
hisilicon-knowledge-mcp-gateway（聚合 / 前缀路由 / 审计）
        │  Streamable HTTP，内网（阶段3起）
        ├──▶ hisi-code-mcp     (:9800)
        ├──▶ hisi-codegraph    (:9801)
        ├──▶ hisi-docs-mcp     (:9802)
        └──▶ hisi-docs-search  (:9803)
```

### 1.2 与其他模块的关系

| 模块 | 关系 |
|---|---|
| `commons-ai` | 模型服务访问适配层，走独立通道；**与 MCP 网关是两条线，互不依赖** |
| `commons-web` | 鉴权过滤器复用（阶段 2） |
| `commons-oidc` | 华为账号 token 验证落点（当前空壳，阶段 2 落地） |
| iam 服务 | 令牌体系，阶段 2 视选型决定是否参与（见 §4.2） |
| `commons-sensitive` | 预留接缝：工具结果敏感词检查（阶段 2 预留，不实现） |

### 1.3 明确不做的事

- 不实现 agent 循环 / LLM 编排
- 不缓存、不改写工具结果（除前缀映射与审计记录）
- 不做模型侧 MCP 服务的鉴权改造（模型侧保持无鉴权，由网络边界保证）

## 2. 协议要点

- 数据层：JSON-RPC 2.0（request / response / notification）
- 传输：**Streamable HTTP**（现行标准）；上游现状即 `"type": "http"` 端点（`/mcp` 路径）
- `initialize` 握手与协议版本协商正常透传；网关对外支持的协议版本与对上游协商的版本**分别维护**
- 注意：`mcpServers` JSON 配置格式是 agent 客户端（Claude/Cursor 系）的配置约定，**不是 MCP 规范的一部分**；网关上游配置可直接沿用该结构，但仅作为自有配置格式

> **实测补充（2026-10-22，4 个上游全部验证）**——四点会直接影响实现，务必知悉：
>
> 1. **上游对协议版本不敏感**：9800 对 `2024-11-05` 与 `2025-06-18` 都接受并**原样回显**。
>    因此"两端版本不一致时明确报错"这条**不必实现为硬失败**：按 `2025-03-26` 协商即可，
>    各上游会回各自支持的版本（实测 9800/9802 → `2025-03-26`，9801/9803 → `2024-11-05`）。
> 2. **无 SSE**：`GET /mcp` 返回 405，响应是纯 `application/json`，无需处理流式分帧。
> 3. **错误也返回 HTTP 200**：错误信息在响应体的 JSON-RPC `error` 字段里（如 `-32601`）。
>    **判成败必须解析响应体，不能只看 HTTP 状态码**——这是最容易写错的一点。
> 4. `Mcp-Session-Id` **可选**：9800/9801 下发、9802/9803 不下发；不下发时直接调用同样成功。

## 3. 上游配置

沿用现有 agent 客户端配置结构，经 `application.yml` + 环境变量注入（对齐 `KB_KG_PUBLIC_URL` 风格）：

```yaml
mcp-gateway:
  upstreams:
    - name: hisi-code-mcp
      url: ${MCP_UPSTREAM_CODE_URL:http://139.9.104.64:9800/mcp}
    - name: hisi-codegraph
      url: ${MCP_UPSTREAM_CODEGRAPH_URL:http://139.9.104.64:9801/mcp}
    - name: hisi-docs-mcp
      url: ${MCP_UPSTREAM_DOCS_URL:http://139.9.104.64:9802/mcp}
    - name: hisi-docs-search
      url: ${MCP_UPSTREAM_SEARCH_URL:http://139.9.104.64:9803/mcp}
```

- 上游清单配置化，增减上游不发版
- **阶段 3 目标**：url 切换为 CCE 内网地址，公网 EIP 端口关闭（见 §5）

## 4. 分阶段实施

### 阶段 1：内测直通（**已完成**，2026-10-22 验收通过）

范围：聚合转发 + 工具命名空间 + 失败隔离。**无鉴权**（已确认：内测直接调模型，不走平台鉴权）。

1. **工程骨架** ✅
   - 启用 `hisilicon-knowledge-mcp-gateway` 部署单元：独立容器，业务 8080 / 探针 9000（`quarkus.management`）
   - `root-path: /hisilicon-knowledge-mcp`，与其他服务 root-path 错开（APIG 按前缀转发）
   - 依赖保持最小：不引 `commons-web`（会把 Redis/Hibernate 拖进来），只依赖 `commons-errorcode`
2. **聚合 `tools/list`** ✅
   - 并发拉取所有上游 `tools/list`，合并注册进官方扩展的 `ToolManager`
   - 跨上游工具名冲突：暴露名加 `上游名__` 前缀（如 `hisi-docs-mcp__hisi_docs_search`）
   - 上游失败：跳过该上游，其余工具照常可用并标记 degraded；单上游挂不拖死端点
3. **`tools/call` 路由** ✅
   - 按前缀定位上游，剥前缀后转发，结果原样返回
   - 不带前缀的工具：唯一命中直接路由；**重名工具按上游 `priority` 走主备路由**——
     主（如 9803）可用即走主，主传输层失败自动切备（如 9802），agent 无感知。
     实测为裸名别名工具实现（`tools/call` 的派发在扩展层完成，无法在 handler 里兜底未知名字）
4. **透传与协商** ✅
   - `initialize` / notifications 由扩展与上游客户端分别处理；两端协议版本分别维护
   - ⚠️ 实测：`tools/call` 的未知工具名由**扩展**回 `-32602`（不是 `-32601`）
5. **部署** ⏳
   - 代码、`application.yml`、Dockerfile（jvm/legacy-jar/native/native-micro）已就绪
   - **尚未做**：CCE 部署、APIG 前缀路由配置、探针指向 `:9000/q/health` 的落地核对
   - agent 客户端以一份 `mcpServers` 配置指向网关端点即可接入

**验收标准**：agent 客户端配置网关单端点后，能列出全部上游工具并成功调用；任一上游停机，其余工具仍可用；网关 root-path/探针符合平台规范。
→ **前两条已在 dev 环境真实验证**（20 工具全中、同名不串台、degraded 隔离生效）；root-path/探针由自动化测试断言，CCE 侧待部署时核对。

### 阶段 2：正式对外（鉴权 + 华为账号）

> ⚠️ **开工前必须先澄清一处口径不一致**（2026-10-22 发现）：
> 本节原写"验证**华为账号签发**的 token（JWKS、iss/aud）"，但本仓库现状是
> **平台自签的 RS256 JWT**——`commons-oidc` 的 `PlatformJwtVerifier` 用配置的 `rsa.public-key`
> **本地验签**（不查 JWKS），claim 为 `sub` / `roles` / `source` / `type`，由
> `hisilicon-knowledge-iam-service` 签发；模块 `AGENTS.md` 也明确"入站请求携带平台签发的 JWT"。
> 需要先定：**agent 到底拿华为账号 token 还是平台 JWT 访问网关？**
> 前者要落地 JWKS/iss/aud 校验（依赖华为账号侧文档），后者可直接复用现成的 `PlatformJwtVerifier`。

1. **鉴权：验证华为账号签发的 token**（选型待按上文澄清）
   - agent 侧持 token 访问网关；网关验签、校验 iss/aud/exp，取 `sub` 映射平台用户身份
   - 验证逻辑落 `commons-oidc`（`PlatformJwtVerifier` **已落地**，非空壳）
   - **外部依赖（实施前置条件）**：若走华为账号路径，需华为账号开放平台的 issuer / JWKS 端点、
     token claims 结构、aud 约定；未确认前本阶段不开工
   - iam 服务是否参与：验签在网关本地完成则 iam 不在关键路径；如需平台权限体系再桥 iam，实施时按需定
2. **审计**：`tools/call` 记录（调用方身份 / 工具名 / 参数摘要 / 结果状态 / 耗时）
3. **工具权限过滤**：按调用方身份过滤 `tools/list` 与 `tools/call`；首版可做简单角色映射，不引 abac
   - ⚠️ 落地提示：官方扩展的 `ToolFilter` **同时作用于列表与调用派发**（实测：设为不可见后调用会被拒），
     正适合做"按身份隐藏且禁止调用"的权限过滤；但**不能**用它做"隐藏但仍可调用"
4. **接缝预留**：工具结果敏感词检查挂钩点（commons-sensitive 端口），默认直通

**验收标准**：无效/过期 token 被拒；不同身份看到并只能调用其有权工具；审计可查询。

### 阶段 3：网络收口（与运维配合）+ token 统计

1. 模型侧 MCP 服务与后端收进同一 VPC，上游 url 改内网地址
2. 公网 EIP 9800–9803 端口安全组关闭（可保留堡垒/白名单）
3. 网关成为模型工具唯一公网入口
4. **token 按日统计与管理员限额**（本轮需求新增）：

   - **只做初步统计，不需精确**
   - 埋点位置**已预留**：`ToolRegistry#forward` 是工具调用的唯一收口点，
     可在不改动协议层的前提下加计量
