# 前端对接调整说明（后端拆分为两个服务后）

> 面向：前端联调同学
> 适用：dev（前端 nginx 转发）、test/prod（APIG + 前端 nginx 转发）
> **结论先说：端口不用改（还是 8080），浏览器侧调用的 URL 一个字都不用改。**
> 前端代码零改动，只要改部署时那份 nginx / 开发代理配置里的**上游指向**，外加**4 个登录端点**的转发路径。

## 1. 与以前的对照

| | 以前（拆分前） | 现在（拆分后） |
| --- | --- | --- |
| 后端服务 | 1 个：`hisilicon-knowledge-platform-service` | 2 个：`hisilicon-knowledge-core-service`（问答 / 知识库 / 搜索 / 字典 / 敏感词）+ `hisilicon-knowledge-iam-service`（登录 / 令牌 / 公钥 / 用户） |
| 业务端口 | 8080 | **8080，两个服务都是，没变** |
| 服务侧 `root-path` | `/hisilicon-knowledge` | core：`/hisilicon-knowledge`（没变）<br>iam：**`/hisilicon-knowledge-iam`（新增）** |
| 探针 / 健康检查 | 8080 上的 `/q/health` | **挪到 9000** 上的 `/q/health`（**前端不要指这个端口**，那是给 CCE 探针用的） |
| 浏览器可见 URL | `/hisilicon-knowledge/...` | **完全不变**（前缀差异由网关 / nginx 内部 rewrite 消化） |

一句话：**做对外的接口没动，动的是"这个请求该发给哪个后端"**。

## 2. 哪些路径转发到哪个服务

| 浏览器请求（保持原样） | 实际转发到 | 要不要改 |
| --- | --- | --- |
| `POST /hisilicon-knowledge/user/login`<br>`POST /hisilicon-knowledge/user/refresh`<br>`POST /hisilicon-knowledge/user/logout`<br>`GET /hisilicon-knowledge/publicKey` | `hisilicon-knowledge-iam-service:8080`，路径为 `/hisilicon-knowledge-iam/user/...`、`/hisilicon-knowledge-iam/publicKey` | **要改**：换上游 + 加一段 rewrite |
| `/hisilicon-knowledge/` 其它**全部**（问答 SSE、热门词、文档搜索与上传、分类、版本、`/system/dict/**`、`/system/sensitive/**` …） | `hisilicon-knowledge-core-service:8080`，**路径原样透传** | 只换上游主机名 |

> ⚠️ 别被路径名骗了：`/hisilicon-knowledge/system/dict/**`、`/system/sensitive/**` 虽然带 `system`，
> 但字典域与敏感词域现在归**业务侧**，仍然由 **core** 提供，**不要**转发给 iam。
> iam 只服务上面那 4 个端点，多传过去的路径会 404。

## 3. nginx 怎么改（改上游名即可）

```nginx
# 1) 4 个登录端点 → iam（新增；正则 location 优先于下面的前缀 location）
location ~ ^/hisilicon-knowledge/(user/(login|refresh|logout)|publicKey)$ {
    rewrite ^/hisilicon-knowledge/(.*)$ /hisilicon-knowledge-iam/$1 break;
    proxy_pass http://hisilicon-knowledge-iam-service:8080;                  # ← 换成实际的 Service / DNS 名
    proxy_set_header Authorization $http_authorization;     # 默认就会透传，显式写出便于审阅
}

# 2) 其余全部 → core（原来怎么配就怎么配，只换上游）
location /hisilicon-knowledge/ {
    proxy_pass http://hisilicon-knowledge-core-service:8080;                 # ⚠️ 结尾不要加 /，否则前缀会被剥掉
}
```

- 上游地址以实际部署为准（CCE 里是 Service 名，本地联调是 `localhost:8080` 之类）；**端口都是 8080**。
- test/prod 经 APIG 接入，上面这段 rewrite 具体落在 APIG 的路径改写还是前端 nginx，**以运维实际配置为准**；
  两种情况都不影响前端代码与浏览器 URL，联调时按第 5 节自检即可。
- SSE 流式问答（`proxy_buffering off`、超时等）保持原有配置，本次未改动。
- 若开发环境用 Vite 的 `server.proxy` 而不是 nginx，同样配两条：一条把 4 个端点 `rewrite` 到
  `/hisilicon-knowledge-iam` 并指向 iam，一条把 `/hisilicon-knowledge` 指向 core。

## 4. 不要做的三件事

1. ❌ 不要把探针端口 **9000** 配进前端代理（浏览器侧不该访问探针）。
2. ❌ 不要把 `/hisilicon-knowledge/` 继续整体指向**旧聚合服务**：它只是过渡期保留，随后会下线。
3. ❌ 不要在前端代码里手写 `/hisilicon-knowledge-iam` 前缀——那是服务侧路径，靠网关 rewrite；
   代码里再拼一次会变成双前缀、全部 404。

## 5. 30 秒自检

```bash
入口=http://<前端访问入口>

# ① iam：取公钥（登录前用它做 RSA 加密），应返回真 PEM
curl -s $入口/hisilicon-knowledge/publicKey

# ② iam：登录端点，空 body 应返回 JSON 错误体（如 A0400 / A0301），返回 404 说明 rewrite 没生效
curl -s -X POST $入口/hisilicon-knowledge/user/login

# ③ core：业务接口应返回业务响应而不是 404
curl -s -o /dev/null -w '%{http_code}\n' $入口/hisilicon-knowledge/hotword/listEnabled
```

- ① 返回 HTML 或 404 → 登录端点的 rewrite 没生效，请求落到了前端页面或 core。
- ② 返回 404 → 同上。
- ③ 返回 404 → `/hisilicon-knowledge/` 没转发到 core（上游还是旧服务或写错了）。

## 6. 后台页面的接口

后台用到的字典（`/hisilicon-knowledge/system/dict/**`）与敏感词
（`/hisilicon-knowledge/system/sensitive/**`）**路径与上游都没变**，仍在 core，无需调整。
本次调整只涉及上面第 2 节那 4 个登录 / 公钥端点。
