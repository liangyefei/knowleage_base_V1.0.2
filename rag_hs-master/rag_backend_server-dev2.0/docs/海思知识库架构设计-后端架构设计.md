架构图涵盖了从客户端接入到外部基础设施及AI模型服务的全链路交互，具体分层与模块职责如下：

* 接入与后端服务层：客户端（Web前端/第三方调用）通过 HTTP 请求或 SSE 流式协议与后端交互。后端服务基于 Quarkus 框架并严格遵循 DDD 四层架构（接口层 Facade、应用层 CommandService、领域层 Domain、基础设施层 Repository），负责参数校验、业务编排及事务管理。
* 业务模块拆分：系统内部按职责划分为三大核心域及通用组件。knowledge 模块负责知识库、文档管理及 ABAC/ACL 细粒度权限；system 模块涵盖用户、角色、部门及审计日志；llm 模块专门对接模型服务以处理问答场景；commons 提供错误码、国际化等基础能力。
* 外部基础设施：依托华为云构建坚实底座，包括 PostgreSQL 关系型数据库、Redis DCS（缓存）、DMS Kafka（消息队列）、SFS 文件存储以及 LTS 日志服务，为系统提供高可靠的数据持久化与缓存能力。
* 异步解耦与 AI 集成：文档处理采用 DMS Kafka 实现异步入站与出站，通过消息传递机制更新文档状态，有效提升系统吞吐量。在智能问答场景下，系统通过 REST Client 调用外部的模型服务进行向量化与问答推理，同时 system 模块通过 OIDC 协议对接第三方 IdP，实现统一的身份认证与单点登录。

### 0.2 模块职责速查

| 模块 | 一句话职责 | 你关注什么 |
|------|-----------|-----------|
| **system** | 管理用户、角色、部门，处理登录认证与审计日志 | 谁可以用系统？有什么权限？做了什么操作？ |
| **knowledge** | 管理知识库、类别目录、文档生命周期，以及 ABAC/ACL 权限策略 | 知识库怎么建？文档怎么上传、审核？谁能看什么？ |
| **llm** | 对接模型服务，负责智能问答（SSE 流式返回） | 用户提问后怎么得到答案？ |
| **commons** | 提供错误码、国际化、Web 基础组件，被以上三个模块共同引用 | （不直接面向业务，是底层支撑） |

#### system（系统管理）模块

主要负责系统中用户、角色及部门的基础信息管理，同时承担登录认证与审计日志的处理工作。在日常使用或维护中，核心关注点在于明确谁拥有系统的使用权限、不同用户具备哪些具体操作权限，以及完整记录和追踪用户在系统内的所有操作行为，确保系统访问的安全性与操作的可追溯性。

#### knowledge（知识库管理）模块

聚焦于知识库的整体管理，涵盖类别目录的搭建、文档全生命周期的维护，并引入了ABAC（基于属性的访问控制）和ACL（访问控制列表）等高级权限策略。关注的核心在于如何科学构建知识库体系、文档如何进行规范的上传与审核流程，以及精细化的权限控制——即明确哪些用户或角色有权查看特定的文档内容，保障知识资产的安全共享。

#### llm（大语言模型对接）模块

作为系统与底层模型服务的桥梁，主要负责对接各类模型服务，并处理智能问答功能（特别采用了SSE流式返回技术以提升用户获取答案的实时体验）。此模块最核心的关注点是解决“用户提出问题后，系统是如何调用模型并生成、返回最终答案”这一技术链路，确保问答交互的流畅与高效。

#### commons（公共基础组件）模块

主要提供统一的错误码定义、国际化支持以及Web基础组件等通用能力，并被上述三个业务模块共同引用。作为底层的支撑模块，它不直接面向具体的业务场景，而是通过提供标准化的基础能力，起到减少重复开发、降低系统耦合度以及提升整体开发效率的关键作用。

### 0.3 关键调用链路速览

| 场景 | 经过的模块/组件 | 说明 |
|------|---------------|------|
| **文档上传/知识库变更** | knowledge → DMS Kafka → 模型服务(向量化/切片) → DMS Kafka → knowledge(更新状态) | 知识库创建/删除、文档上传/审核通过/版本管理时，通过 DMS Kafka 通知外部模型服务处理；模型服务完成向量化和切片后回传结果，knowledge 更新文档状态 |
| **用户登录** | system → PG → Redis → 返回 JWT | 校验账号密码，缓存令牌 |
| **权限判定** | knowledge → Redis(ACL缓存) → Redis(ABAC缓存) → 审计日志 | 三层判定：RBAC → ACL → ABAC |
| **模型问答** | llm → 模型服务 → SSE 流式返回 | 用户提问，llm 通过 REST Client 调用模型服务，结果实时推送 |
| **其它模型服务** | llm → 模型服务 → 非流式返回 | 问答以外的功能，切片查看等 |

#### 文档上传/知识库变更场景

在该场景下，系统主要处理知识库的创建与删除，以及文档的上传、审核通过和版本管理等操作。其调用链路为 knowledge 模块通过 DMS Kafka 异步通知外部模型服务进行文本的向量化与切片处理；待模型服务完成后将结果回传至 DMS Kafka，再由 knowledge 模块接收并更新文档的状态，从而实现非阻塞式的文档处理流程。

#### 用户登录场景

该场景涵盖了用户的身份校验与会话建立过程。调用链路始于 system 模块，首先查询 PG（PostgreSQL 数据库）校验用户的账号与密码是否正确；校验通过后，系统会将生成的令牌缓存至 Redis 中，并最终向客户端返回 JWT（JSON Web Token），以此完成登录态的持久化与快速鉴权。

#### 权限判定场景

该场景负责保障系统及知识库的数据访问安全。调用链路由 knowledge 模块发起，依次经 RBAC（角色-权限码门禁）、ACL（资源级解析）、ABAC（策略条件评估）三层短路判定——任一层 DENY 即终止并拒绝，ACL 显式命中即直接返回、不再向下评估，三层均未拒绝方放行至业务层；判定结果写入审计日志。系统采用 RBAC → ACL → ABAC 三层判定（DENY 优先 + RBAC 为地板），实现从粗粒度到细粒度的权限控制。

#### 模型问答场景

该场景针对用户的实时智能问答需求。由 llm 模块作为入口，通过 REST Client 调用底层的模型服务，并利用 SSE（Server-Sent Events）技术实现数据的流式返回。这种机制允许模型生成的答案实时、逐块地推送给前端，显著降低了用户的等待时间，提升了交互体验。

#### 其它模型服务场景

该场景用于处理非问答类的模型相关功能（如切片查看等）。同样由 llm 模块通过 REST Client 调用模型服务，但与问答场景不同的是，此类请求采用非流式返回的方式，即等待模型处理完毕后一次性返回完整结果。

```mermaid
    Knowledge -->|"6. Kafka 出站<br/>（知识库变更 / 文档上传<br/> 审核通过 / 版本管理）"| Kafka
    Kafka -->|"7. 消费消息<br/>（切片 + 向量化）"| ModelSvc
    ModelSvc -->|"8. Kafka 入站<br/>（处理结果回传）"| Kafka
    Kafka -->|"9. 消费结果<br/>（更新文档状态）"| Knowledge
```

**调用关系说明**：

| 编号 | 关系 | 类型 | 说明 |
|------|------|------|------|
| 1-3 | 所有业务模块 → commons | 编译时强依赖 | system、knowledge、llm 均通过 Gradle 依赖 commons，共享错误码、国际化消息、JWT 过滤器 |
| 4-5 | system → knowledge / llm | 运行时间接协作 | system 签发 JWT；knowledge 和 llm 通过 commons-web 的 JWT Filter 验证 Token、提取用户身份。**不直接调用** |
| 6-9 | knowledge ↔ DMS Kafka ↔ 模型服务 | 运行时异步双向 | **这是唯一的跨系统业务链路**。knowledge 在以下时机通过 DMS Kafka 发送消息：创建/删除知识库、上传文档、审核通过、版本管理。外部模型服务消费后进行向量化和切片，完成后通过 DMS Kafka 回传结果，knowledge 消费结果并更新文档状态 |
| 10 | llm → 模型服务 | 运行时同步调用 | llm 仅负责通过 REST Client 调用模型服务。**llm 不参与文档处理链路** |

> **关键结论**：
> 1. 三个业务模块之间**没有直接的同步 RPC 调用**，通过共享 commons 组件（JWT Filter）传递身份
> 2. **文档处理链路**完全在 knowledge 模块和外部模型服务之间，通过 DMS Kafka 双向异步通信，llm 模块不参与
> 3. 哪些操作触发 DMS Kafka 消息：**创建知识库、删除知识库、上传文档、文档审核通过、版本管理**（一切影响问答效果的操作）。类别（子目录）的增删改不触发

## 1 功能域概述

后端模块向上提供接口给前端，向下调用模型服务或MCP服务。

### 1.1 接口描述

- **流式接口**：采用 SSE（Server-Sent Events）方式
- **非流式接口**：JSON 对象返回

**返回体结构：**

| 键 | 说明 | 示例值 |
|----|------|--------|
| code | 错误码，"0"：正常，其他：出错 | `"0"`, `"A0103"` |
| data | 返回数据，可为空 | `{ "pageNumber": 1, "pageSize": 20, "totalPage": 1, "totalRow": 1, "records": [] }` |
| message | 消息内容 | `"操作成功"`, `"登录失败，用户名与密码不匹配"` |

### 1.2 权限控制

除登录外，其余操作都需要登录后才能操作。

### 1.3 令牌超时

用户登录成功后会返回两个令牌：**访问令牌**和**刷新令牌**。为方便用户获取新的令牌对，提供刷新令牌对的接口。

| 令牌类型 | 时效 |
|---------|------|
| accessToken（访问令牌） | 1 小时 |
| refreshToken（刷新令牌） | 2 小时 |

### 1.4 国际化

需支持简体中文和英文（通过请求头 `Accept-Language` 切换）。知识库问答时不做语言切换，以模型输出为准。

## 3 功能实现设计

### 3.1 功能编号：获取公钥

#### 3.1.1 功能概述

获取 RSA 公钥，用于前端加密敏感信息（如密码）。

#### 3.1.2 实现设计

返回系统公钥内容。

#### 3.1.3 用户接口设计

```
GET /publicKey
```

- **请求方式**：GET
- **参数**：无
- **返回值**：公钥内容（字符串）

---

### 3.2 功能编号：登录

#### 3.2.1 功能概述

支持用户名+密码登录，也可对接第三方 IdP 登录。关于第三方 IdP，先引入通用 OIDC 组件，待确认实际的 IdP 时再进行调试。

#### 3.2.2 实现设计

**参数校验**：
- 用户名和密码不能为空
- 用户名和密码能正常解密（RSA）

**处理逻辑**：

1. 根据用户名查询用户信息，若未查询到用户信息则提示"账号与密码不匹配"并返回
2. 使用 BCrypt 校验密码，未通过则提示"账号与密码不匹配"并返回
3. 创建令牌对（accessToken + refreshToken）
4. 删除旧令牌（使之前的令牌失效）
5. 缓存并返回令牌对

```mermaid

    end
```

### 3.4 功能编号：用户管理

#### 3.4.1 功能概述

用户管理提供系统用户的创建、查询、编辑、删除、角色分配及 ABAC 属性管理功能。用户是权限系统的主体，通过关联角色获得 RBAC 权限，通过用户属性参与 ABAC 策略判定。用户支持本地创建和 OIDC 外部身份关联两种来源。

#### 3.4.2 SR 设计

| 需求编号 | 需求描述 |
|---------|---------|
| F-097 | **RBAC**：用户通过角色获得操作权限，支持多角色组合 |
| F-098 | **ABAC**：用户属性（部门、地域、雇佣类型、安全级别）参与 ABAC 策略条件判定 |
| F-099 | **细粒度**：用户可作为 ACL 条目的主体，被授予或拒绝特定资源的访问权限 |

#### 3.4.3 实现设计

1. **用户创建**：校验用户名唯一性 → 使用 BCrypt 加密初始密码 → 绑定角色 → 持久化用户记录
2. **用户查询**：支持按用户名、部门、状态分页查询。列表不返回密码字段

5. **角色分配**：调用 `addUserRoles` / `removeUserRoles` 接口，维护 `user_roles` 关联表。变更后触发缓存失效事件
6. **外部身份关联**：OIDC 登录时自动创建 `external_identities` 记录，`source` 字段标记为 `"oidc"`。支持同一用户关联多个外部身份（多 IdP 登录同一账号）

### 3.5 功能编号：角色管理

#### 3.5.1 功能概述

角色管理维护系统的 RBAC 角色体系。预设角色（系统管理员、知识库管理员、审核员、编辑者、开发者）在系统初始化时创建且不可删除。管理员可基于预设角色创建自定义角色，从权限码池中勾选权限组合。

#### 3.5.2 SR 设计

| 需求编号 | 需求描述 |
|---------|---------|
| F-097 | **RBAC**：角色的核心载体，角色→权限码的映射构成 RBAC 的基础 |

#### 3.5.3 实现设计

1. **角色创建**：校验角色 key 唯一性 → 校验所选权限码均在允许范围内 → 持久化角色记录及 `role_permissions` 关联
2. **权限码约束**：自定义角色不可授予 `sys:role` 和 `sys:user` 权限（防止权限扩散）。此约束在后端硬编码校验
3. **角色编辑**：更新角色名称、描述及权限码集合。采用先删后增策略维护 `role_permissions` 表。变更后发送 `RolePermissionsChanged` 领域事件，触发缓存刷新
4. **角色删除**：预设角色（`is_preset=1`）不可删除。删除自定义角色前检查是否有用户仅依赖此角色，给出警告并强制解绑
5. **角色复制**：基于现有角色创建副本，继承其权限码集合，管理员可进一步调整
6. **权限码定义**以枚举类 `PermissionCode` 管理，系统启动时加载全部码值，角色配置页面从该枚举动态渲染可选项

### 3.8 功能编号：知识库管理

#### 3.8.1 功能概述

知识库管理提供知识库的创建、查询、编辑、删除功能，以及知识库下类别（子目录）的树形管理。知识库是权限隔离的顶层容器——每个知识库独立绑定 ABAC 策略和 ACL 条目。

#### 3.8.2 SR 设计

| 需求编号 | 需求描述 |
|---------|---------|
| F-097 | **RBAC**：仅知识库管理员可执行创建/编辑/删除操作；开发者可查询有权限的知识库 |
| F-098 | **ABAC**：每个知识库可独立绑定 ABAC 策略，策略在知识库范围内生效 |
| F-099 | **细粒度**：知识库本身可作为 ACL 的目标资源，支持对知识库级别设置权限 |

#### 3.8.3 实现设计

1. **知识库创建**：校验名称唯一性 → 设置创建者 → 生成默认根类别 → 持久化。创建者自动获得该知识库的管理权限
2. **知识库查询**：返回用户有 `kb:list` 权限的知识库列表。列表不返回已软删除的知识库。开启 ABAC 时，还需经过知识库级别的 ABAC 策略过滤（例如仅返回用户所属部门的知识库）
3. **知识库编辑**：修改名称、描述、所属组织（影响 ABAC `res.org` 属性）、默认敏感等级。修改所属组织将影响该知识库下所有文档的 ABAC 判定
4. **知识库删除**：软删除，标记 `status=0`。删除前校验该知识库下是否存在未删除的文档，提示管理员确认级联处理

#### 3.8.4 类别管理

1. **类别树**：类别以 `parent_id` 字段组织为树形结构，每个类别属于一个知识库。提供递归查询接口返回完整类别树，供前端渲染树形选择器
2. **类别创建**：校验同级名称唯一性（同一父类别下不可重名）→ 持久化
3. **类别编辑**：修改名称、父类别（移动操作需校验不会形成循环引用）
4. **类别删除**：检查是否包含子类别或文档，级联软删除或提示警告

### 3.9 功能编号：文档管理

#### 3.9.1 功能概述

文档管理提供知识库下文档的全生命周期管理：上传、版本覆盖、查询、编辑、删除、审核、模型处理跟踪。文档是权限控制的最小粒度资源，每条文档可独立设置 ACL。文档携带 ABAC 资源属性（文档类型、敏感等级、数据地域、合规标签），参与 ABAC 策略判定。

文档的可用性由**两个正交的状态维度**共同决定：

- **生命周期状态（status）**：由人工操作驱动（编辑者上传/提交审核、审核员批准/驳回、管理员归档/废弃），描述文档的审核流转过程
- **模型处理状态（processStatus）**：由模型服务异步回调驱动，描述文档的切片与向量化进度

> **核心规则：文档真正可检索 = `status = PUBLISHED` 且 `processStatus = COMPLETED`。**
> 审核通过只是人为放行，只有模型服务完成切片+向量化，文档才真正进入知识库问答范围。

| 需求编号 | 需求描述 |
|---------|---------|
| F-097 | **RBAC**：编辑者可上传/编辑文档；审核员可审核文档；开发者可查询/查看文档 |
| F-098 | **ABAC**：文档的 `doc_type`、`sensitivity`、`data_region`、`compliance` 属性参与策略条件判定 |

#### 3.9.3 实现设计 —— 双重状态模型（核心设计）

##### 3.9.3.1 双重状态职责划分

| 状态维度 | 字段 | 驱动方 | 取值 | 语义 |
|---------|------|--------|------|------|
| 生命周期状态 | `status` | 人工操作 | `DRAFT` / `REVIEWING` / `PUBLISHED` / `ARCHIVED` / `DEPRECATED` | 文档审核流转 |
| 模型处理状态 | `processStatus` | 模型服务回调 | `PENDING` / `PROCESSING` / `COMPLETED` / `FAILED` | 切片+向量化进度 |

**为什么拆成两个状态而不是合并：**

1. **驱动方不同**：生命周期由人驱动（确定性、可审计），模型处理由外部服务驱动（异步、可能失败、可重试），两者是不同的主体、不同的节奏
2. **组合爆炸**：合并后 "已发布但没处理完" 的中间值无法表达；`PUBLISHED + FAILED` 也无法表达"内容已放行但向量化失败、需要重试"这一常见场景
3. **职责解耦**：模型服务重启/重试不影响审核流程；审核驳回也不影响已完成的向量化内容（可复用，无需重新处理）

##### 3.9.3.2 生命周期状态流转

```mermaid
flowchart TD
    UPLOAD[上传/版本覆盖] --> DRAFT
    DRAFT[DRAFT 草稿] -->|submit-review 提交审核| REVIEWING
    REVIEWING[REVIEWING 审核中] -->|approve 批准| PUBLISHED
    REVIEWING -->|reject 驳回<br/>须填驳回原因| DRAFT
    REVIEWING -->|cancel-review 编辑者撤回| DRAFT
    PUBLISHED[PUBLISHED 已发布] -->|archive 归档| ARCHIVED
    PUBLISHED -->|deprecate 废弃<br/>仅已发布可废弃| DEPRECATED
    ARCHIVED[ARCHIVED 已归档] -.->|不再支持废弃| ARCHIVED
    DEPRECATED[DEPRECATED 已废弃] -.->|上传/覆盖/审核 均拒绝| DEPRECATED
```

**状态变更操作一览：**

| 操作 | 触发方 | 前置状态 | 目标状态 | 权限 | 说明 |
|------|--------|---------|---------|------|------|
| 首次上传 | 编辑者 | — | `DRAFT` | kb:doc:upload | 初始状态，同时 processStatus → PENDING |
| 版本覆盖上传 | 编辑者 | `DRAFT` / `PUBLISHED` | `DRAFT` | kb:doc:edit | `REVIEWING` 禁止（见 3.9.3.5）；`PUBLISHED` 覆盖后旧版保持可检索 |
| submit-review | 编辑者 | `DRAFT` | `REVIEWING` | kb:doc:edit | 提交审核 |
| cancel-review | 编辑者 | `REVIEWING` | `DRAFT` | kb:doc:edit | **编辑者自己撤回**（无驳回原因），撤回后即可修改/覆盖 |
| approve | 审核员 | `REVIEWING` | `PUBLISHED` | kb:doc:review | 审核通过，记录审核人/审核时间 |
| reject | 审核员 | `REVIEWING` | `DRAFT` | kb:doc:review | 驳回，**必须填写驳回原因**（写入 review_comment） |
| archive | 管理员 | `PUBLISHED` | `ARCHIVED` | kb:doc:delete | 归档，停止对外提供 |
| deprecate | 管理员 | `PUBLISHED` | `DEPRECATED` | kb:doc:delete | 废弃（软删除，保留审计记录）；非已发布状态（DRAFT/REVIEWING/ARCHIVED/DEPRECATED）拒绝 |

> **撤回（cancel-review）与驳回（reject）的区别**：撤回是编辑者主动撤销自己的提交，不需要原因；驳回是审核员否定内容，必须附原因。两者目标状态都是 `DRAFT`。

##### 3.9.3.3 模型处理状态流转

```mermaid
flowchart TD
    NEW[上传 / 版本覆盖] --> PENDING
    PENDING[PENDING 待处理] -->|模型服务拉取任务| PROCESSING
    PROCESSING[PROCESSING 处理中] -->|回调 COMPLETED| COMPLETED
    PROCESSING -->|回调 FAILED| FAILED
    FAILED[FAILED 处理失败<br/>记录 process_error] -.->|PUBLISHED 打回草稿<br/>见下方打回规则| DRAFT
    COMPLETED[COMPLETED 处理成功<br/>进入可检索范围]
```

**规则：**

1. **上传 / 版本覆盖**时 processStatus 重置为 `PENDING`——新文件需要模型服务重新切片、向量化
2. 模型服务处理完成后通过**内部回调接口**上报结果（`COMPLETED` / `FAILED`）。`COMPLETED` 只修改 processStatus，不动 status；`FAILED` **同时将生命周期 status 由 PUBLISHED 打回 DRAFT**（打回规则见下）
3. `FAILED` 记录失败原因到 `process_error` 字段；无人工重试接口——向量化失败由回调自动打回 DRAFT，编辑者修复内容后重新提交审核即重试整个处理周期
4. 生命周期状态变更（submit-review / approve / reject / archive / deprecate）**不修改** processStatus

**FAILED 回调打回草稿规则（向量化失败 → 回 DRAFT）：**

文档真正可检索 = `PUBLISHED + COMPLETED`。`PUBLISHED + FAILED` 意味着内容不可检索却停留在
发布列表，编辑者无感知。因此文档级 `PROCESSING_FAILED` 回调实际生效（通过 messageId 幂等 +
状态机守卫/"最新回调胜"）时，同时将生命周期 status 打回：

| 回调前 status | 行为 | 理由 |
|--------------|------|------|
| `PUBLISHED` | **打回 `DRAFT`** | 失败文档不可检索，回草稿让编辑者修复后重新走审核流 |
| `DRAFT` | 不变（幂等） | 已是目标态（打回后重试失败等场景） |
| `ARCHIVED` / `DEPRECATED` | **不打回**，只落 processStatus + warn 日志 | 人工终态（归档下线/软删除）不被异步回调复活/推翻（处理期间被归档/废弃的竞态） |
| `REVIEWING` | 不打回（防御性，当前链路不可达） | 审核流不被异步回调破坏 |

- **单向门**：后续重试成功的 `COMPLETED` 回调不自动恢复 `PUBLISHED`——文档停留在
  `DRAFT + COMPLETED`（不可检索），重新发布必须经编辑者重新提交、审核员重新批准。
  生命周期由人工驱动，不允许 Kafka 回调隐式改写审核结论。
- 打回与 processStatus 写入同事务，原子生效；重复重投/过期回调/文档已删除等场景被既有幂等
  守卫拦截，天然不会重复打回。
- 不动 `publishedVersion` / `hasPublishedVersion`：打回时来源为 PUBLISHED 的文档旧版向量已被
  模型按契约清理，"无可检索版本"语义准确；来源为 DRAFT 的重试场景保留旧发布版可检索标记。
- KB 级 FAILED 回调（`documentId=null`）只更新知识库处理状态，不涉及文档生命周期。

##### 3.9.3.4 双状态组合矩阵

| status ＼ processStatus | PENDING | PROCESSING | COMPLETED | FAILED |
|------------------------|---------|------------|-----------|--------|
| **DRAFT** | 刚上传/刚覆盖版本 | — | 打回后重试成功（**不可检索，待重审**） | 向量化失败打回/重试再失败（**不可检索，可修复重审或重试**） |
| **REVIEWING** | 审核中，模型未开始 | 审核中+处理中 | 审核中+已处理完（等批准） | 审核中+处理失败 |
| **PUBLISHED** | 已发布未处理（**暂不可检索**） | 处理中（**暂不可检索**） | ✅ **可检索** | 已发布处理失败（**不可检索**，回调即打回 DRAFT，仅竞态窗口短暂可见） |
| **ARCHIVED** | — | — | — | 竞态残留（不打回，见 §3.9.3.3 打回规则） |
| **DEPRECATED** | — | — | — | 竞态残留（不打回，见 §3.9.3.3 打回规则） |

**检索 / 列表过滤条件：**

```sql
WHERE (
    (status = 'PUBLISHED' AND process_status = 'COMPLETED')
    OR has_published_version = TRUE
)
AND kb_id = :kbId
```

> `has_published_version = TRUE` 表示该文档存在已发布的历史版本（见 3.9.3.5），即使当前工作版本处于 DRAFT 修订中，历史已发布内容仍可检索，保证服务不中断。

##### 3.9.3.5 版本管理与覆盖

文档版本管理有两种模式：**隐式覆盖**（DRAFT 阶段通过上传接口自动匹配同名文件覆盖）和**显式版本覆盖**（已发布文档通过专用接口上传新版）。版本号（`current_version` / `version_number`，varchar(64)）由上传/编辑/版本覆盖时的元数据 `version` 字段提供，**不再由系统自增（+1）**；`version` 在上传与版本覆盖时必填（空 → A0420 + `versionRequired`），编辑时可选（空=不改 current_version）。

###### 3.9.3.5.1 隐式覆盖：上传时的同名匹配规则

`POST /kb/documents/upload` 上传文件时，按 `kbId + categoryId + 文件名（去扩展名=title）` 查找已存在文档：

| 匹配到文档的 status | 行为 |
|-------------------|------|
| `DRAFT` | ✅ **自动覆盖**：替换文件内容，复用该 documentId，`current_version` 更新为本次元数据 `version`，processStatus → PENDING |
| `REVIEWING` | ❌ **拒绝**："同名文档正在审核中，请先撤回审核后再上传" |
| `PUBLISHED` | ❌ **拒绝**："同名文档已发布，请使用版本覆盖接口（`POST /kb/documents/versions`）" |
| `ARCHIVED` / `DEPRECATED` | ❌ **拒绝**："文档已归档/废弃，不可覆盖" |
| 未匹配到 | ✅ **新建文档**（DRAFT） |

> DRAFT 覆盖不产生版本记录——草稿阶段的反复迭代不需要追溯历史，`current_version` 取本次上传元数据的 `version`（首次 approve 时该值固化为 `published_version`）。

###### 3.9.3.5.2 显式版本覆盖：`POST /kb/documents/versions`

**仅允许 PUBLISHED 状态的文档**。编辑器携带 metadata（`UploadDocumentCommand`，与上传接口同构）上传新版本文件，形成新的版本链。

| 行为 | 说明 |
|------|------|
| 前置条件 | 文档 status = `PUBLISHED` |
| metadata | 与上传同构（`version` 必填 + tags 校验 + 字典值校验，fail-closed）；author/tags/remark 入 documents 列，product/chip_model/sensitivity/official/access_policy 全量替换 document_metadata |
| 版本号 | `current_version` = 元数据 `version`（必填）；**查重**：不得等于 `published_version` 或已归档历史版（`document_versions`），否则 A0701 + `versionAlreadyPublished` |
| 旧版本处理 | 当前文件信息归档 `document_versions`，标记 `was_published=TRUE`（**旧版保持可检索**） |
| 新版本 | `current_version` = 元数据 version，status → `DRAFT`（需重新审核），`has_published_version=TRUE` |
| 文件名 | ✅ 允许变化（如 `需求v1.xlsx` → `需求v2.xlsx`），title = 文件名去扩展名 |
| 文件类型 | ✅ **同类型强校验**（2026-08 变更，用户确认）：新文件扩展名必须与源文档 file_path 末段扩展名一致，否则 A0701 + `fileTypeChanged`（此前允许跨类型覆盖；tus 版本覆盖路径同规则） |

**已发布文档修订流程（服务不中断）：**

```mermaid
flowchart LR
    P1[PUBLISHED+COMPLETED<br/>v2 可检索] -->|POST .../versions| P2[DRAFT+PENDING<br/>v3 工作版本<br/>has_published_version=TRUE]
    P2 -->|submit-review| P3[REVIEWING]
    P3 -->|approve| P4[PUBLISHED<br/>v3 成为正式版<br/>has_published_version=FALSE]
    P1 -.旧版 v2 归档 document_versions<br/>was_published=TRUE.- P2
```

###### 3.9.3.5.3 文档编辑（属性 / 可选换文件 / 可选改版本）

`POST /kb/documents/edit`（multipart）— `documentId` + 可选 `metadata`（`EditDocumentCommand`：title/author/tags/remark/product/chip_model/version/sensitivity/official）+ 可选 `file`（新文件）。无 metadata 且无 file 视为空编辑（A0508）。

| 能力 | 说明 |
|------|------|
| 属性编辑 | title/author/tags/remark 写 documents 列；product/chip_model/sensitivity/official/access_policy 全量替换 document_metadata（字典值校验，fail-closed） |
| 换文件（仅 DRAFT） | 上传新文件替换现有文件，**扩展名必须不变**（文件类型不能变，否则 A0701 + `fileTypeChanged`）；processStatus → PENDING（新文件需模型重处理）；current_version 不变（除非同时改版本）。大文件可走 tus 断点续传（purpose=docEdit，见《初始化批量上传设计》§4.7） |
| 改版本（可选） | metadata `version` 非空 → 更新 `current_version` 并**查重**（不得等于 `published_version` 或已归档版，否则 A0701 + `versionAlreadyPublished`）；空 = 不改 |

**状态约束：**

| 当前 status | 属性编辑 | 换文件 | 理由 |
|------------|---------|--------|------|
| `DRAFT` | ✅ | ✅（同扩展名） | 编辑中，可改属性可换同格式文件 |
| `REVIEWING` | ❌ | ❌ | 审核中不允许（先撤回再改） |
| `PUBLISHED` | ✅ | ❌（须走版本覆盖接口） | 改属性是轻量操作；换文件须走 `POST /kb/documents/versions` |
| `ARCHIVED` / `DEPRECATED` | ❌ | ❌ | 终态不可修改 |

###### 3.9.3.5.4 元数据编辑

`POST /kb/metadata/set` — 统一元数据编辑接口（entityType = KB / CATEGORY / DOCUMENT），key-value 全量替换。与改名分开，职责清晰。

| 字段 | 说明 |
|------|------|
| `entityType` | 实体类型：`KB` / `CATEGORY` / `DOCUMENT`（必填） |
| `entityId` | 实体 ID（知识库 ID / 类别 ID / 文档 ID，必填） |
| `metadata` | `Map<String, String>`，如 `{"chipModel":"CV620","sensitivity":"内部"}`（必填；空 Map `{}` = 清空全部） |

**全量替换语义**：传入的 Map 完全覆盖该实体的 metadata 记录（先删后插）。不传的 key 被清除。

**校验规则（防直接调用攻击）**：key 为字母开头的字母/数字/下划线且长度 ≤ 50（对齐 `meta_key varchar(50)`）；value trim 后长度 1~200（对齐 `meta_value varchar(200)`）且不含控制字符；条目数 ≤ 50（Bean Validation，超限 400）。校验失败统一 A0420（200 + 业务码）。

**状态约束**：KB/CATEGORY 仅活跃（status=1）可编辑，软删除视同不存在（A0430）；DOCUMENT 同改名（DRAFT/PUBLISHED 允许，REVIEWING 不许，终态不许，A0508）。编辑元数据**不发布任何消息事件**（不影响模型处理）。

**字典 key 白名单校验（方案 A，已实现）**：每个 key 必须存在于某个生效字典类型（`kb_dict_types.status=1`）的 `controlled_meta_keys` 并集中（逗号分隔 + trim + 去重）。白名单经 **commons-dict 模块**的 `DictMetaKeyCacheService` 获取（**Redis cache-aside**：key `dict:active-meta-keys`，TTL 24 小时；miss 回源 DB 并自动写入；缓存损坏按空集 fail-closed）。校验顺序：同步格式校验（key 正则/value 长度，失败短路不查字典）→ 字典白名单校验 → 实体存在性/状态校验 → replaceAll。key 不在白名单 → A0420 + `metadataKeyNotInDict`。**校验失败时任何写操作都不发生**（包括 replaceAll）。system 模块字典管理端（后续实现）在类型变更时调用 `DictMetaKeyCacheService.evictCache()` 删除缓存 key。

```mermaid
        Cmd->>Repo: saveReviewHistory(reviewRecord)
        Repo->>PG: INSERT INTO review_history ...
        Facade-->>FE: 200 {code: "0", message: "已驳回，文档回到草稿"}
    else approve（审核员批准）
        Facade->>Auth: check(user, "kb:doc:review", document)
        Auth-->>Facade: ALLOW / DENY
        Facade->>Cmd: approve(command)
        Cmd->>Repo: findById(documentId)
        Repo-->>Cmd: Document (status=REVIEWING)
        Cmd->>Cmd: document.approve(reviewer)<br/>→ status='PUBLISHED'<br/>记录 reviewedBy / reviewedAt<br/>processStatus → PENDING
        Cmd->>Repo: update(document)
        Repo->>PG: UPDATE documents SET status='PUBLISHED',<br/>process_status='PENDING'

        Note over Cmd,DMS: 步骤3: 通过 DMS Kafka 通知模型服务
        Cmd->>DMS: produce(topic=kb-document-processing,<br/>partitionKey=kbId)<br/>eventType=DOCUMENT_PUBLISHED<br/>{documentId, filePath, kbId, version}
        DMS-->>Cmd: ACK

        Cmd-->>Facade: OK
        Facade-->>FE: 200 {code: "0", message: "审核通过"}

        Note over DMS,Model: ═══ 以下为异步处理（后台） ═══

        DMS-->>Model: 消费 kb-document-processing<br/>(按 kbId 分区，同 KB 消息有序)
        Model->>SFS: 下载文件
        SFS-->>Model: 文件流
        Model->>Model: 文本切片 + 向量化 + 写入向量库

        Note over Model,Facade: 步骤4: 模型回调上报结果（入站）
        Model->>DMS: produce(topic=kb-document-processed)<br/>eventType=PROCESSING_COMPLETED
        DMS-->>Facade: 消费 kb-document-processed
        Facade->>Cmd: 更新 processStatus
        Cmd->>Repo: update(document)
        Repo->>PG: UPDATE documents<br/>SET process_status='COMPLETED'<br/>(status='PUBLISHED' 时进入可检索)
    end
```

> **审核通过后才通知模型**（不是上传时通知），避免了模型处理草稿的浪费。processStatus 在 approve 时重置为 PENDING（确保新内容被模型重新处理）。

##### 3.9.3.8 消息通知设计（DMS Kafka）

###### 通知时机

> **核心原则：只有审核通过后才通知模型服务处理文档。** 上传仅创建 DRAFT，不触发任何模型处理。这避免了模型处理草稿/未通过审核内容的算力浪费。

| 生命周期动作 | 是否通知 | EventType | Topic | 说明 |
|------------|---------|-----------|-------|------|
| 首次上传 | ❌ | — | — | DRAFT，不处理 |
| 版本覆盖上传 | ❌ | — | — | DRAFT，不处理 |
| **approve（审核通过）** | ✅ | `DOCUMENT_PUBLISHED` | `kb-document-processing` | 切片+向量化 |
| **deprecate（废弃）** | ✅ | `DOCUMENT_DELETED` | `kb-document-processing` | 删除向量库所有切片 |
| **archive（归档）** | ✅ | `DOCUMENT_ARCHIVED` | `kb-document-processing` | 从活跃索引移除（保留向量） |
| submit-review / cancel-review / reject | ❌ | — | — | 纯状态流转 |

> 知识库级别事件（`KB_CREATED` / `KB_UPDATED` / `KB_DELETED`）保持原有通知逻辑不变，通过 DMS Kafka 替换 Redis Stream 投递。

###### DMS Kafka 架构

```
出站 Topic: kb-document-processing (Backend → Model)
  分区数: 8（线上实际值；初版设计为 16，创建时按 8 落地——⚠ 文档与线上不一致，以线上为准）
  分区键: kbId (hash(kbId) % 分区数)
  保证: 同一 KB 的所有消息进入同一分区 → 分区内 FIFO 保序
        KB_CREATED 严格先于该 KB 下所有 DOCUMENT_PUBLISHED
        不同 KB → 不同分区 → 多 Pod 并行消费
  ⚠ 分区数即模型端消费并行度上限：模型侧消费者数 M ≤ 分区数（当前 8）。
    同一 KB 内串行（分区键=kbId），单库大批量导入的吞吐由该分区决定 → 提吞吐要么加分区，
    要么改分区键（需模型端确认能否放弃 KB 内强顺序）。分区只能增不能减，且增分区会重分布
    key→分区映射，变更点前后同 KB 顺序保证会断，需择窗口实施。

入站 Topic: kb-document-processed (Model → Backend)
  分区数: 6（线上实际值；初版设计为 8——⚠ 文档与线上不一致，以线上为准）
  分区键: documentId (无顺序依赖，各文档回调独立)
  并发度: concurrency=1（固化单分区顺序消费：@Incoming 返回 Uni，背压 Uni 完成才处理下一条；禁止 >1 否则同分区回调乱序）
  重平衡: partition.assignment.strategy=CooperativeStickyAssignor（协作式：伸缩/发版只迁移需移动的分区，不全组停摆）
  消费者: DmsProcessCallbackConsumer → 更新 processStatus
  顺序假设: 各文档回调独立、无顺序依赖。业务侧 messageId 幂等去重 + 状态机守卫（已是终态→"最新回调胜"裁决）兜底重复/乱序。
  消费并行度上限 = 分区数（当前 6）：多副本部署时最多 6 个 Pod 能分到分区，其余副本"在线、探针全绿、不消费"。
    回调量由模型向量化完成速率决定（模型慢 → 量低），因此 6 个消费者足够；但**禁止**开启基于分区分配的
    就绪检查（health-topic-verification-enabled），否则未分到分区的副本会永久 NotReady，配合 maxUnavailable=0 锁死滚动发布。
  失败处理（2026-10 复盘后定型）:
    ① 非法信封（解析失败/未知 eventType/缺 messageId/缺 kbId）→ ERROR 日志 + ACK（不进死信）；
    ② 瞬时故障（DB 连接/超时/死锁等）→ 有界重试（默认 3 次尝试、退避 200ms，配置 kb.messaging.callback.retry.*），
       每次重试为独立事务；重试耗尽才 nack → 死信（消息保留供人工对账重放）；
    ③ 不可恢复错误（BusinessException / IllegalArgumentException）→ 不重试，直接 nack → 死信。
    为什么不把①也送死信：死信写入失败会让 nack 失败并**终止整条消费通道**（该 Pod 此后永不消费、
    无 ERROR 日志、探针全绿）；而这类消息永远无法被应用，留在无人消费的死信主题里也没有恢复价值。
  DLQ 边界: failure-strategy=dead-letter-queue；死信主题按环境显式配置（<base>-dlq<suffix>，如 dev 的
    kb-document-processed-dlq / release 的 kb-document-processed-dlq-release），必须真实存在（写死信
    失败会终止消费通道）。注意 DMS 的命名是"后缀在最后"，不要用 ${topic}-dlq 派生。
  ⚠ 生产教训（2026-08-31）: 模型回调长期未带 processedAt，重新发布后新周期 COMPLETED 被终态守卫当过期跳过，89 个文档冻结在"已发布+向量化失败"。双重修复：① relay markProcessing 守卫扩为 PENDING/FAILED（发布发送成功即开启新处理周期，清掉上一周期遗留 FAILED）；② 入站 processedAt 缺失时的 COMPLETED→FAILED 兜底覆盖（见 §3.9.3.8）。
  ⚠ 生产教训（2026-10-13）: 多环境共用消费组（组名写死为 knowledge-service，与 topic 环境隔离约定不匹配），
    dev 的分区/位点被其他环境的组成员占走，dev 的 Pod 成员在线、探针全绿、零 ERROR 却永不消费，持续 23 小时
    无人发现。修复：每环境在**挂载的配置文件**里显式写 topic / 消费组 / 死信主题三行
    （如 release = kb-document-processed-release / kb-document-processed-consumer-release /
    kb-document-processed-dlq-release），三件套同时改；仓库内 application.yml 只是 dev 默认值与模板。
```

消费者组并行模型（同一 KB 消息有序，不同 KB 并行）：

```
消费者组: model-service (M 个 Pod, M ≤ 分区数)
  ┌────────────────────────────────────────────────────┐
  │              kb-document-processing (8 分区)        │
  │  ┌──────┐ ┌──────┐ ┌──────┐        ┌──────┐       │
  │  │ P0   │ │ P1   │ │ P2   │  ...   │ P7   │       │
  │  │KB_A  │ │KB_B  │ │KB_C  │        │KB_Z  │       │
  │  └──┬───┘ └──┬───┘ └──┬───┘        └──┬───┘       │
  └──────┼────────┼────────┼──────────────┼───────────┘
         │        │        │              │
         ▼        ▼        ▼              ▼
      Pod 1    Pod 2    Pod 3    ...   Pod M
     (KB_A)   (KB_B)   (KB_C)        (KB_Z)
```

**关键保证**：
- 同一 KB 的消息**严格顺序消费**（分区 FIFO）
- 不同 KB 的消息**并行消费**（不同分区 → 不同 Pod）
- 分区数固定（线上实际 **8**），不随 KB 数量变化——KB 通过哈希映射到分区，无限 KB 可承载
- 单个 KB 内文档按**版本号顺序**消费（v1 → v2 → v3）
- ⚠ 并行度上限 = 分区数（8）：模型端 Pod 数超过 8 时，多出的 Pod 分不到分区（空转）。
  要提并行度必须先加分区——分区只能增不能减，且加分区会重分布 key→分区映射，
  变更点前后同 KB 保序会断，需择窗口实施；模型慢（向量化耗时长）时应先确认是否真的需要

###### 入站回调消费设计（KB 级入站 + 幂等 + DLQ）

> 本节补充入站 topic `kb-document-processed`（模型 → 后端）的完整消费设计，覆盖 KB 级回调、幂等、毒丸/DLQ 策略与字段落库约定。与 §3.9.3.8「与现有代码的映射」表中 `DmsProcessCallbackConsumer` 一行配合阅读。消息信封结构见 `kafka-structure.md` §3（`messageId` 为模型新生成、`documentId` 在 KB 级回调为 `null`）。

**① 消费入口与 KB/文档级分流**

`DmsProcessCallbackConsumer` 是入站 topic 的唯一消费者（dev=`kb-document-processed`，test/release 各带后缀）。**topic / 消费组 / 死信主题三件套必须按环境显式配对**（`<base>[-suffix]` / `<base>-consumer[-suffix]` / `<base>-dlq[-suffix]`，写在 CCE 挂载的配置文件里），绝不允许两个环境落进同一个消费组——2026-10-13 线上故障即"多环境共组"：dev 的分区与位点被其他环境的组成员拿走，dev 的 pod 成员在线、探针全绿、日志零处理零报错，却永不消费。入口按信封 `documentId` 是否为空分流：

```
onProcessed(messageJson) → parse(信封) → ProcessCallbackCommand
  ├─ documentId 非空 → 文档级 → DocumentCommandService.processCallback
  └─ documentId 为空 → KB 级   → KnowledgeBaseCommandService.processCallback
```

- `documentId` 用 `asText(null)` 显式判空，不依赖 `NullNode.asText()` 的版本差异（修复 KB 级回调 `documentId=null` 被误判非法、变毒丸的问题）。
- `eventType` 精确匹配 `PROCESSING_COMPLETED` / `PROCESSING_FAILED`（取消 `startsWith("PROCESSING_")` 兜底，避免拼错被误判为 FAILED）。
- `messageId` 必填（去重主键）；KB 级回调必填 `kbId`，文档级回调亦要求透传 `kbId`（审计/路由）。任一缺失 → 抛 `IllegalArgumentException` → nack → DLQ。

**② KB 级入站处理（新增，对齐双重状态模型）**

契约 §3.3 规定 `KB_CREATED` / `KB_DELETED` 触发回调（`documentId=null`）。此前入站仅设计文档级，KB 级回调是设计空白。现给 `knowledge_bases` 增加与 `documents` 对齐的处理状态：

| 字段 | 类型 | 语义 |
|------|------|------|
| `process_status` | varchar(15) | `PENDING`（createKb/deleteKb 时置，等待回调）/ `COMPLETED` / `FAILED` |
| `process_error` | varchar(255) | `KB_CREATED`/`KB_DELETED` 回调 FAILED 时的失败原因 |
| `process_error_code` | varchar(32) | 失败错误码 |
| `processed_at` | timestamp | 处理完成/失败时间（回调回传） |

- `createKb` / `deleteKb`（软删除）时置 `process_status='PENDING'`；`KB_UPDATED` 无回调，不动处理状态。
- 回调 `COMPLETED` → `COMPLETED`；`FAILED` → `FAILED` + 记录 error/errorCode。
- `KB_CREATED_FAILED`（向量库初始化失败）会令该 KB 下所有文档处理失败，此状态现已**可见可重试**（方案 B）；`KB_DELETED_FAILED`（向量残留）亦可见，供对账/重试清理。

> KB 级回调 `chunkCount` 恒为 0，不落库 KB（`knowledge_bases` 无 `chunk_count` 列）。

**③ 幂等设计（契约 §1 要求）**

契约规定：仅当模型向回调 topic 投递失败时才重投，后端需做幂等处理。采用**双重防线**：

1. **状态机守卫（主防线，零额外成本）**：仅 `PENDING`/`PROCESSING` 可迁移到终态；当前已是终态（`COMPLETED`/`FAILED`）的回调视为重复/过期，ACK 跳过不覆盖。因版本覆盖/重试会把 `processStatus` 重置回 `PENDING`（§3.9.3.3 规则 1），故"从终态到另一终态"只可能是重复回调。覆盖契约 §1 描述的同结果重投全部场景。

2. **messageId 去重表（加固，防 earliest 重放跨周期回归）**：新增 `kb_callback_processed(message_id PK, document_id, kb_id, event_type, status, received_at)`。消费时与状态更新**同事务**内查重 + 落库：

   ```
   @WithTransaction processCallback(cmd):
     1. existsByMessageId(messageId)? → 是则 ACK 跳过（幂等）
     2. findById(documentId|kbId)
        - null（资源已物理删除）→ ACK 跳过 + record(messageId) 防重放
     3. 当前 processStatus 已是终态 → ACK 跳过 + record(messageId)
     4. PENDING/PROCESSING → 应用回调 + update + record(messageId)
   ```

   - `messageId` 是模型回调信封的新生成 ID（非原事件 ID），同一次重投保持一致，可精确去重。
   - 防 `auto.offset.reset=earliest` 在 offset 丢失重放时，把**旧周期**回调误应用到**新周期** PENDING 窗口导致状态回退（状态机守卫挡不住这一种，去重表挡得住）。
   - 回调量低（与文档处理事件同量级），写入开销可忽略；按 `received_at` 定期清理过期记录，兼作回调审计。

**④ 失败与毒丸策略（ACK vs nack vs DLQ）**

区分"不可恢复"与"瞬时故障"，避免毒丸堵塞分区：

| 场景 | 处理 | 触发 |
|------|------|------|
| JSON 解析失败 / 未知 eventType / 必填字段缺失 | **ERROR 日志 + ACK**（不进死信） | 消费端解析阶段拦截 |
| 文档/KB 不存在（已物理删除） | **ACK + warn** + record(messageId) | 代码内正常返回，不抛 |
| 重复回调（状态已终态 / messageId 已处理） | **ACK + skip** | 状态机守卫 / 去重表 |
| DB / 网络瞬时故障 | **有界重试**（默认 3 次尝试、退避 200ms，每次独立事务）→ 耗尽才 **nack → 死信** | `kb.messaging.callback.retry.*` + `failure-strategy` |
| 业务/参数类不可恢复错误（BusinessException / IllegalArgumentException） | **nack → 死信**（不重试） | 消费端异常分类 |

> **为什么非法信封不进死信**（2026-10 复盘定型）：死信写入失败会让 nack 失败并**终止整条消费通道**（该 Pod 此后永不消费、无 ERROR 日志、探针全绿——与 2026-10-13 故障同类的静默失效）。而非法信封永远不可能被应用，留在无人消费的死信主题里也没有恢复价值；改为 ERROR 日志（含原始报文，截断 1000 字符）留证 + ACK，既保护通道又保留可观测性。
>
> **瞬时故障必须先于 DB 超时落地**：设想给回调路径设 DB 拿连接/查询超时以保护消费组不被 `max.poll.interval.ms` 踢出——若没有本行的有界重试，fail-fast 会直接变成「永久丢回调」。两者必须成对存在。

`application.yml` 入站通道启用 DLQ（下面为 dev 取值；**环境实际生效的是 CCE 挂载的配置文件**，每环境显式写这三行）：

```yaml
mp.messaging.incoming.kb-document-processed-in:
  topic: kb-document-processed                                  # test: kb-document-processed-test / release: ...-release
  group.id: kb-document-processed-consumer                      # test: ...-consumer-test / release: ...-consumer-release
  partition.assignment.strategy: org.apache.kafka.clients.consumer.CooperativeStickyAssignor  # 协作式重平衡
  ...
  auto.offset.reset: earliest            # 配合幂等守卫，重放安全
  failure-strategy: dead-letter-queue     # 瞬时故障有界重试耗尽后写死信（非法信封已在解析阶段 ACK）
  dead-letter-queue.topic: kb-document-processed-dlq            # test: ...-dlq-test / release: ...-dlq-release
```

> ⚠️ **不要让 topic 派生组名/死信名**：DMS 里死信的真实命名是 `<base>-dlq<suffix>`（后缀在最后，Kafka 控制台可见 release 的 `kb-document-processed-dlq-release`），而 `${...topic}-dlq` 会算出 `kb-document-processed-release-dlq`——**两者不相等**，指向一个不存在的主题，会让 nack 写死信失败并终止整条消费通道。三行显式写、逐字比对控制台。

DLQ 消息由人工/对账任务排查后重放；earliest 重放由 messageId 幂等兜底（重复消息直接跳过）。

**⑤ 文档级字段落库约定**

`documents` 表新增三列，落库模型回传字段（此前均被丢弃）：

| 字段 | 类型 | 写入时机 |
|------|------|---------|
| `chunk_count` | int | `PROCESSING_COMPLETED` 时写 `payload.chunkCount`；`FAILED` 置空（本周期未产出切片） |
| `process_error_code` | varchar(32) | `PROCESSING_FAILED` 时写 `payload.errorCode`；`COMPLETED` 清空 |
| `processed_at` | timestamp | 回调时写 `payload.processedAt`（COMPLETED）/ `failedAt`（FAILED）；缺失则取 `now()` |

`PROCESSING_FAILED` 缺 `error` 字段时填占位描述（不报错）；`COMPLETED` 清空 `process_error`/`process_error_code`。`processedAt`/`failedAt` 解析失败置空兜底，不因时间字段失败整条消息。`PROCESSING_FAILED` 实际生效时同时将 `PUBLISHED` 文档生命周期 status 打回 `DRAFT`（打回规则见 §3.9.3.3）。

终态守卫的"最新回调胜"裁决依赖 `payload.processedAt`（COMPLETED）/`failedAt`（FAILED）回传；模型侧缺失时（生产实测长期缺失）无法比较，兜底规则：仅 `COMPLETED` 覆盖 `FAILED` 终态（成功清失败；同文档回调按 documentId 分区保序，后消费的必然更晚），其余组合保守跳过。配套出站侧：relay `markProcessing` 守卫为 `process_status IN ('PENDING','FAILED')`——发布/重试消息发送成功即开启新处理周期，上一周期遗留 FAILED 随新周期清掉（COMPLETED 不在守卫内，保留"回调先于 relay 到达置终态"的竞态保护）。

**⑧ 陈旧回调与事件作废（DRAFT+PENDING 窗口防护）**

回调与事件只以 documentId 关联，无内容周期校验。生命周期回退（版本覆盖 PUBLISHED→DRAFT、草稿同格式重传）会把 processStatus 重置为 PENDING，重新打开回调落库窗口——迟到的旧内容周期回调会把草稿盖章为终态，产生"草稿但已向量化"（DRAFT+COMPLETED）状态污染。触发时序：

| # | 时序 |
|---|------|
| 1 | approve → PUBLISHED+PROCESSING（模型排队慢）→ 版本覆盖 → DRAFT+PENDING → v1 的 COMPLETED 回调到达 → 命中 PENDING 窗口 → DRAFT+COMPLETED |
| 2 | approve → outbox 因 Kafka 故障退避 → 期间文档被覆盖 → relay 重发 stale 事件 → markProcessing 把 DRAFT+PENDING 拉成 PROCESSING → v1 回调 → DRAFT+COMPLETED |
| 3 | 上述场景的 FAILED 变体先落成 DRAFT+FAILED（无人工重试接口，FAILED 终态在下次发布/覆盖时随新周期被 relay markProcessing 清掉） |

双保险防护（均在应用侧闭环，无需模型服务配合）：

1. **出站作废**：版本覆盖 / 草稿重传（processStatus 重置 PENDING）时，同事务调用 `outboxRepository.cancelPendingByDocument(documentId)`，将该文档 PENDING 的 outbox 行置 `CANCELLED`——旧内容周期事件不再投递（relay 扫描只取 PENDING，天然跳过）。堵住时序 2，并消除"DRAFT 被误标 PROCESSING"瑕疵。
2. **入站拦截**：`processCallback` 增加窗口守卫——文档处于 `DRAFT + PENDING` 时，任何终态回调视为旧内容周期陈旧回调：WARN + record(messageId) + ACK 跳过，不更新文档。兜住已发出/在途回调（时序 1），FAILED 变体同样拦截。

不破坏合法链路：`DRAFT+PROCESSING`（非 PENDING 窗口）回调正常落库——"FAILED 打回草稿 + 重试成功停留 DRAFT 待重审"语义不变。

##### 3.9.3.9 文档删除（物理删除）与一致性设计

###### 软删除 vs 物理删除职责划分

| 操作 | 机制 | 数据保留 | 文件保留 | 通知模型 | 用途 |
|------|------|---------|---------|---------|------|
| deprecate（废弃） | 状态流转 → `DEPRECATED` | 保留（审计/可恢复） | 保留 | `DOCUMENT_DELETED`（清向量） | 下线内容但留痕 |
| **delete（物理删除）** | 删除 DB 记录 + SFS 文件 | 不保留 | 不保留 | `DOCUMENT_DELETED`（清向量） | 彻底清理，省存储成本 |

> 物理删除与废弃互不替代：废弃是生命周期的一环（保留审计记录），物理删除是资源清理（删除即无法恢复）。

###### 删除规则（状态矩阵）

| status | 是否可物理删除 | 通知模型 |
|--------|--------------|---------|
| DRAFT | ✅ | ❌（从未进入模型） |
| REVIEWING | ❌（须先 cancel-review 撤回） | — |
| PUBLISHED | ✅ | ✅ `DOCUMENT_DELETED` |
| ARCHIVED | ✅ | ✅ `DOCUMENT_DELETED` |
| DEPRECATED | ✅ | ✅ `DOCUMENT_DELETED` |

- `processStatus` 不参与删除判断（DRAFT+FAILED 等组合直接删）。
- 级联删除：`document_versions` + `document_metadata` 随文档一并删除。
- REVIEWING 拒绝原因：删除不可逆，审核中先撤回再删，避免审核员正在看的内容被操作者删除。

###### 事务一致性：业务事务 + Outbox + 两阶段文件删除

问题本质：DB 删除、SFS 文件删除、Kafka 消息发送三者无法构成分布式事务（Kafka 不支持 XA，对象存储删除不可回滚）。行业标准解法是 **Transactional Outbox**（业务提交与消息记录同事务）+ **文件两阶段删除**，达到最终一致、无失败窗口。

**① 业务事务（唯一需要原子的部分）**

```
@WithTransaction delete():
  1. DB 级联删除（documents + document_versions + document_metadata）
  2. 同事务插入 document_outbox 记录（eventType=DOCUMENT_DELETED, kbId, documentId, payload）
  → 提交。文件操作与消息发送都不在事务内。
```

**② 文件删除 — 两阶段（对象存储标准做法）**

```
事务提交后: fileStorageService.moveToTrash(filePath)  ← SFS rename 到 trash/ 目录（幂等、可重试）
定时任务:   清理 trash/ 中超过保留期（默认 7 天，可配）的文件，物理删除
```

- rename 失败 = 文件留在原地 = 无害（孤儿文件由对账/清理任务兜底）。
- 物理删除永远不阻塞业务——SFS 类存储删除不可回滚，先"移走"再"清掉"。

**③ 消息发送 — Outbox relay（多实例安全 + 同 KB 保序）**

```
定时任务（每实例都跑）:
  1. SELECT DISTINCT kb_id FROM document_outbox WHERE status='PENDING'   ← KB 分组
  2. 对每个 kb_id:
       SELECT pg_try_advisory_xact_lock(hashtext('outbox_kb:'||kb_id))   ← KB 级互斥
       成功 → 独占处理该 KB 全部 PENDING（ORDER BY created_at 顺序发送）
       失败 → 其他实例正在处理此 KB，跳过
      → 发送 DMS Kafka（当前 Noop 占位，DMS 接入后替换实现）
      → 同一事务更新 status=SENT
```

- **同 KB 保序核心**：PG 事务级 advisory lock（`pg_try_advisory_xact_lock`，PG 9.4+）——一个 KB 同一时刻只有一个实例获取锁成功，该 KB 内全部 PENDING 消息按 `created_at` 顺序由同一实例发出，**不会出现同一 KB 消息被不同 Pod 乱序处理**；不同 KB 由不同实例并行处理（负载分摊）。
- 锁为事务级：事务提交/回滚自动释放，实例崩溃后由 PG 回收 → 消息保持 PENDING 下次扫描重新处理 → **至少一次投递**，模型侧按 documentId 幂等消费兜底。
- 失败：保留 PENDING + retry_count 递增 + 按 retry_count 指数退避设置 `next_retry_at`（`delay = min(base<<retry_count, max)`，默认 10s→5min 封顶），scan 跳过未到点行（同 KB 保序：头部未到点则后续全部等待）+ 滞留超时告警。
- 所有知识库/文档事件（`KB_CREATED/UPDATED/DELETED`、`DOCUMENT_PUBLISHED/ARCHIVED/DELETED`）**统一经 outbox 投递**：业务事务内 `outboxRepository.insert(KnowledgeEvent)` 写入 PENDING 记录（与业务数据同事务提交），relay 扫描发送。统一入口消除两类问题：①"直发成功的新消息先于 outbox 积压旧消息到达"的乱序；②事务内直发成功但事务随后回滚产生的 phantom 消息（outbox 记录随事务回滚，不会发出）。`KnowledgeEvent` 全字段（`categoryId`/`operatorId`/`payload`）落库，relay 重放透传。
- **发送成功后置 processStatus=PROCESSING**：relay 在 DMS Kafka 发送成功后、与 `markSent` 同事务，按事件类型将对应实体 `process_status` 由 PENDING/FAILED 置为 PROCESSING（向量化中）：`DOCUMENT_PUBLISHED` → 文档 `markProcessing`；`KB_CREATED` → 知识库 `markProcessing`。写 outbox 时不动 processStatus（保持 PENDING，消息未真正发出不提前置 PROCESSING）；移除/更新类事件（`ARCHIVED`/`DELETED`/`KB_UPDATED`/`KB_DELETED`）不动 processStatus。`where process_status IN ('PENDING','FAILED')` 守卫：发送成功即开启新处理周期，上一周期遗留的 `FAILED` 随新周期清掉（否则重新发布后新周期 COMPLETED 回调被入站终态守卫当过期跳过，文档冻结"已发布+向量化失败"，见 §3.9.3.8）；不覆盖 `COMPLETED`（回调先到置终态后 relay 的 markProcessing 不命中，竞态保护）、PROCESSING 幂等。

**④ 幂等消费 + 对账兜底**

- 模型服务对 `DOCUMENT_DELETED` 按 documentId 幂等处理（重复删向量无害）。
- trash 超时未清 → 清理任务物理删除；outbox 滞留超时 → 告警。

###### 多实例（CCE）部署说明

| 关注点 | 方案 |
|--------|------|
| relay 重复发送 / 同 KB 乱序 | `pg_try_advisory_xact_lock` KB 级锁互斥：同 KB 单实例独占顺序发送，不同 KB 并行 |
| 清理任务重复执行 | 物理删除 `deleteIfExists` 幂等，多实例并发无害 |
| 文件路径一致性 | 生产 CCE 多实例**共享挂载同一 SFS 卷**，相对路径（`kb/{kbId}/{categoryId}/{filename}`）在任何实例解析到同一文件 |
| 时间一致性 | trash 超时/outbox 排序均用 DB 时间（`created_at`/`now()`），不依赖实例时钟 |
| 存储实现 | 生产必须用 `SfsFileStorageService`（共享卷）；`LocalFileStorageService` 仅本地开发（单机文件系统，非共享） |

###### document_outbox 表

| 字段 | 类型 | 说明 |
|------|------|------|
| id | VARCHAR | 主键（UUID） |
| event_type | VARCHAR | `EventType` 名称 |
| kb_id | VARCHAR | 知识库 ID |
| category_id | VARCHAR | 分类 ID（可为空） |
| document_id | VARCHAR | 文档 ID（KB 级事件为空） |
| operator_id | VARCHAR | 操作员 ID |
| payload | TEXT | `KnowledgeEvent.payload` 序列化 JSON（null/空→null，relay 重建信封时序列化为 `{}`） |
| status | VARCHAR | PENDING / SENT（FAILED 用重试计数表达） |
| retry_count | INT | 重试次数 |
| next_retry_at | TIMESTAMP | 下次重试时间（失败后按 retry_count 指数退避计算；null/已到点 → 可被 relay 扫描，未到点 → 跳过。同 KB 保序：头部未到点则后续全部等待） |
| created_at | TIMESTAMP | 创建时间（DB 写入，relay 排序依据） |
| sent_at | TIMESTAMP | 发送成功时间 |

索引：`(status, created_at)` —— 多实例并发扫描的前提，无索引会全表锁竞争。

配置项：`kb.storage.trash-retention-days=7`（trash 保留期）；`kb.outbox.batch-size=100`；`kb.outbox.poll-interval=10s`（relay 轮询）；`kb.outbox.retry-base-delay-seconds=10`（退避基准，retry_count=0 时）；`kb.outbox.retry-max-delay-seconds=300`（退避封顶，默认 5min）。退避：`delay = min(base << retry_count, max)`，避免故障期 relay 每 tick 狂试头部失败消息、给 Kafka 压力且同 KB 后续消息被头部阻塞。

##### 3.9.3.10 文档下载

`POST /kb/documents/download`，body `{documentId, version?}`。

- **version 语义**：null/缺省 = 下载最新版（`documents.file_path`）；非空 = 下载 `document_versions` 历史版本（versionNumber 精确匹配）。
- **状态规则**：全部生命周期状态（DRAFT/REVIEWING/PUBLISHED/ARCHIVED/DEPRECATED）均可下载——下载是人工行为，与模型处理状态无关；DRAFT 供上传者预览、REVIEWING 供审核员查看。
- **校验**：文档不存在 A0430；version 为 varchar 自由文本（null/缺省=最新版）；版本号不存在 A0430 + `documentVersionNotFound`；文件物理不存在 A0706 `fileCannotRead`。
- **响应**：HTTP 200 二进制流，Content-Type = 文档 MIME，Content-Disposition `attachment; filename*=UTF-8''{编码文件名}`（RFC 5987 支持中文）。异常仍走统一 JSON 包装（HTTP 200 + 非 0 code）。
- **文件读取**：`FileStorageService.read(path)`（相对路径，store 时已 sanitize 防穿越）；本地 `Files.readAllBytes`，SFS 接入时换 SDK 实现。第一版全量 byte[]（≤100MB），大文件后续可改流式。

### 3.10 功能编号：ABAC 策略管理

#### 3.10.1 功能概述

ABAC（基于属性的访问控制）策略管理是权限系统的核心模块。策略绑定在知识库级别，定义在何种属性条件下允许或拒绝某类操作。策略引擎根据用户属性、资源属性、环境属性动态评估策略条件，与 RBAC 角色权限和 ACL 细粒度权限协同工作，构成三层权限判定体系。

#### 3.10.2 SR 设计

| 需求编号 | 需求描述 |
|---------|---------|
| F-098 | **ABAC**：支持按文档类型、敏感等级、所属组织、地域四个维度定义策略。策略效果分为 ALLOW 和 DENY，DENY 优先于 ALLOW |

#### 3.10.3 实现思路

策略引擎设计采用**轻量级自研方案**，不引入外部规则引擎（如 Drools / OPA），理由如下：

1. 条件表达式的操作符和函数集有限且固定（`=`、`!=`、`>`、`>=`、`<`、`<=`、`IN`、`CONTAINS`、`AND`、`OR`），无需通用规则引擎的完整能力
2. 自研引擎可深度集成缓存机制，策略变更时精准失效对应知识库的缓存，避免全量刷新
3. 减少外部依赖，降低部署复杂度和运维成本

条件表达式存储为结构化字符串，解析后编译为可执行的表达式树（AST），评估时遍历 AST 得出布尔结果。

#### 3.10.4 领域数据模型

#### 3.10.5 实现设计 —— 策略 CRUD

1. **策略创建**：校验条件表达式语法合法性（调用 `ExpressionValidator` 解析，语法错误则拒绝创建）→ 持久化
2. **策略编辑**：同上校验 → 更新记录
3. **策略删除**：物理删除记录。删除后触发 `AbacPolicyChanged` 领域事件
4. **策略启用/禁用**：PATCH 接口修改 `is_enabled` 字段，禁用后策略不参与判定但保留配置
5. **策略查询**：返回知识库下所有策略，按 `priority` 降序排列（优先级高的在前）

#### 3.10.6 实现设计 —— 条件表达式解析器

`ExpressionParser` 负责将条件表达式字符串解析为表达式树（Expression AST），解析过程分为三个阶段：

**阶段一：词法分析（Lexer）**

输入：
```
res.doc_type = "代码" AND user.dept = "研发部"
```

输出 Token 流：
```
[ATTR:res.doc_type] [OP:=] [STRING:"代码"] [AND] [ATTR:user.dept] [OP:=] [STRING:"研发部"] [EOF]
```

Token 类型枚举：

| Token 类型 | 说明 |
|-----------|------|
| ATTR | 属性路径，如 `res.doc_type` |
| OP | 操作符，如 `=`, `!=`, `>` |
| STRING | 字符串字面量，如 `"代码"` |
| NUMBER | 数值字面量 |
| AND | 逻辑与 |
| OR | 逻辑或 |
| LPAREN | 左括号 `(` |
| RPAREN | 右括号 `)` |
| COMMA | 逗号 `,` |
| LBRACKET | 左中括号 `[` |
| RBRACKET | 右中括号 `]` |
| EOF | 输入结束 |

**阶段二：语法分析（Parser）—— 递归下降解析，生成 AST（抽象语法树）**

文法规则（EBNF）：
```
expression  := or_expr
or_expr     := and_expr (OR and_expr)*
and_expr    := primary (AND primary)*
primary     := condition | LPAREN expression RPAREN
condition   := ATTR OP value
value       := STRING | NUMBER | list
list        := LBRACKET value (COMMA value)* RBRACKET
```

AST 节点类型：

| 节点类型 | 结构 |
|---------|------|
| `ConditionNode` | `{ attrPath, operator, value }` |
| `AndNode` | `{ left: ExpressionNode, right: ExpressionNode }` |
| `OrNode` | `{ left: ExpressionNode, right: ExpressionNode }` |

#### 3.10.7 实现设计 —— 策略评估引擎

策略评估引擎 `PolicyEvaluator` 在权限判定时被调用。输入为当前请求上下文（用户属性、资源属性、环境属性），输出为评估结果。

**评估流程（伪代码）：**

```java
PolicyResult evaluate(Long kbId, String operation, EvalContext ctx) {
    // Step 1: 加载知识库的策略（优先从缓存读取）
    List<AbacPolicy> policies = policyCache.get(kbId);
    if (policies == null) {
        policies = policyRepository.findByKbIdAndEnabled(kbId);
        policyCache.put(kbId, policies);
    }

    // Step 2: 筛选匹配目标操作的策略
    policies = policies.stream()
        .filter(p -> p.targetOperation.equals("*")
                   || p.targetOperation.equals(operation))
        .sorted((a, b) -> Integer.compare(b.priority, a.priority)) // 降序
        .toList();

    // Step 3: 按优先级降序逐条评估
    for (AbacPolicy policy : policies) {
        ExpressionNode ast = policy.getCompiledAst(); // 编译后缓存的 AST
        boolean matched = ast.evaluate(ctx);

        if (matched) {
            return new PolicyResult(
                policy.effect,  // ALLOW or DENY
                policy.name,    // 命中的策略名（用于审计）
                policy.id
            );
        }
    }

    // Step 4: 无策略命中
    return PolicyResult.NOT_APPLICABLE;
}
```

**关键设计决策：**

- **"首命中即返回"模式**：按优先级降序评估，命中第一条即停止，不再评估低优先级策略。这与 DENY 优先原则一致——将 DENY 策略设为更高优先级即可确保其优先生效
- **AST 编译缓存**：策略加载时将 `condition_expr` 字符串编译为 AST 并缓存在内存，避免每次评估都重新解析
- **策略缓存**：以知识库 ID 为 key 缓存该知识库的策略列表（含编译后的 AST）。当策略变更（创建/编辑/删除/启禁）时，发送 `AbacPolicyChanged` 事件，监听器精准清除对应 `kbId` 的缓存条目

#### 3.10.8 实现设计 —— 条件节点评估

`ConditionNode` 的 `evaluate` 方法根据操作符类型执行具体比较逻辑：

```java
boolean evaluate(EvalContext ctx) {
    Object actualValue = ctx.resolve(attrPath);  // 从上下文提取属性值
    if (actualValue == null) return false;       // 属性不存在 → 条件不满足

    return switch (operator) {
        case EQ  -> actualValue.equals(expectedValue);
        case NEQ -> !actualValue.equals(expectedValue);
        case GT  -> ((Comparable) actualValue).compareTo(expectedValue) > 0;
        case GTE -> ((Comparable) actualValue).compareTo(expectedValue) >= 0;
        case LT  -> ((Comparable) actualValue).compareTo(expectedValue) < 0;
        case LTE -> ((Comparable) actualValue).compareTo(expectedValue) <= 0;
        case IN  -> ((List<?>) expectedValue).contains(actualValue);
        case CONTAINS -> ((List<?>) actualValue).contains(expectedValue);
    };
}
```

**`EvalContext.resolve(attrPath)` 实现：**

根据属性路径前缀定位数据源：

| 前缀 | 数据源 | 说明 |
|------|--------|------|
| `user.*` | `UserContext` | 当前登录用户信息，含 ABAC 属性字段 |
| `res.*` | `ResourceContext` | 目标资源信息，含文档类型/敏感等级等 |
| `env.*` | `EnvContext` | 请求环境信息，含 IP/网络类型/请求时间 |

### 3.11 功能编号：ACL 权限管理

#### 3.11.1 功能概述

ACL（访问控制列表）提供资源级别的细粒度权限控制。与 RBAC 的全局角色权限和 ABAC 的条件策略不同，ACL 直接绑定在具体资源上，精确控制"谁对这个资源能做什么"。ACL 支持对知识库、类别、文档三级资源分别设置权限，并通过继承机制实现上级权限向下传递。

#### 3.11.2 SR 设计

| 需求编号 | 需求描述 |
|---------|---------|
| F-099 | **细粒度**：权限粒度覆盖读（`doc:read`）、写（`doc:upload`/`doc:edit`）、删（`doc:delete`）、审（`doc:review`）、管（`kb:config`）。对每一条知识或每个知识集合均可独立设置权限，支持继承阻断 |

#### 3.11.3 领域数据模型

**ACL 条目表 `acl_entries`：**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT | 主键 |
| resource_type | VARCHAR | 资源类型：`KB` \| `CATEGORY` \| `DOCUMENT` |
| resource_id | BIGINT | 资源 ID |
| subject_type | VARCHAR | 主体类型：`USER` \| `ROLE` |
| subject_id | BIGINT | 主体 ID（用户 ID 或角色 ID） |
| permission | VARCHAR | 权限码，如 `doc:read` |
| effect | VARCHAR | `ALLOW` \| `DENY` |
| UNIQUE | (resource_type, resource_id, subject_type, subject_id, permission) | 唯一约束 |

**资源表需包含的 ACL 控制字段：**

| 表名 | 字段 | 说明 |
|------|------|------|
| `knowledge_bases` | `inherit_parent` | 知识库为顶层资源，该字段恒为 `false` |
| `categories` | `inherit_parent` | 默认 `true` |
| `documents` | `inherit_parent` | 默认 `true` |

#### 3.11.4 实现设计 —— ACL CRUD

1. **ACL 新增**：校验同一资源下不存在重复的 `(subject_type, subject_id, permission)` 组合 → 持久化
2. **ACL 编辑**：修改 `permission` 或 `effect` 字段
3. **ACL 删除**：物理删除条目。删除后该权限维度恢复为继承或默认行为
4. **继承控制**：通过 PATCH 接口修改资源的 `inherit_parent` 字段。阻断继承后需重新为资源定义 ACL，否则权限回退为 RBAC 默认

#### 3.11.5 实现设计 —— ACL 继承解析算法

ACL 继承解析是权限判定引擎中最复杂的子模块。核心目标：对于给定的 `(resourceType, resourceId)`，向上遍历资源树，收集所有未阻断继承的祖先节点的 ACL 条目，并与当前节点的 ACL 合并为有效的 ACL 集合。

**算法详细流程（伪代码）：**

```java
List<AclEntry> resolveEffectiveAcl(ResourceType type, Long resourceId) {
    String cacheKey = "acl:" + type + ":" + resourceId;
    List<AclEntry> cached = aclCache.get(cacheKey);
    if (cached != null) return cached;

    List<AclEntry> entries = new ArrayList<>();
    ResourceNode current = loadResource(type, resourceId);

    // === Phase 1: 沿资源树向上遍历，收集各层 ACL ===
    while (current != null) {
        // 加载当前节点的 ACL 条目
        List<AclEntry> nodeAcl = aclRepository.findByResource(
            current.type, current.id);

        // 合并规则：子节点的 ACL 覆盖父节点的同维度条目
        // 同维度 = 相同 (subjectType, subjectId, permission)
        entries = mergeWithOverride(entries, nodeAcl);

        // 检查是否阻断继承
        if (!current.inheritParent) {
            break;  // 阻断继承，停止向上遍历
        }

        // 向上移动到父资源
        current = current.getParent();
    }

    // === Phase 2: 写入缓存并返回 ===
    aclCache.put(cacheKey, entries);
    return entries;
}
```

**资源树向上遍历路径示例：**

```
文档 (id=42) → 类别 (id=5, inherit=true) → 类别 (id=2, inherit=false) → [停止]
最终有效 ACL = 合并(文档ACL, 类别5的ACL) + 阻断处停止，不包含类别2和知识库的ACL
```

**`mergeWithOverride` 合并规则：**

```java
for (AclEntry parentEntry : parentAcl) {
    // 检查子节点是否有同维度的覆盖条目
    boolean overridden = childAcl.stream()
        .anyMatch(e -> e.sameDimension(parentEntry));
    if (!overridden) {
        merged.add(parentEntry);  // 父节点条目未被覆盖，保留
    }
}
merged.addAll(childAcl);  // 子节点条目全部保留（优先）
```

#### 3.11.6 实现设计 —— ACL 冲突解决

ACL 条目之间可能存在冲突：同一 `(subjectType, subjectId, permission)` 组合在不同层级有不同 effect。解决规则：

- **规则 1（层级优先）**：子节点 ACL > 父节点 ACL。子节点显式定义的条目完全覆盖父节点的同维度条目
- **规则 2（显式 DENY 优先）**：同一层级的同维度条目，DENY 效果覆盖 ALLOW。此规则在 `mergeWithOverride` 之后，对同一资源节点的 ACL 做内部去重时应用
- **规则 3（用户主体优先于角色主体）**：当 `USER` 和 `ROLE` 类型的条目同时存在时，`USER` 类型的条目优先生效（因为用户级别的授权更精确、更有意图性）

**示例场景：**

```
知识库 ACL：[角色:开发者, doc:read, ALLOW]
文档 ACL：  [用户:张三,   doc:read, DENY]
结果：张三无法读取该文档（子节点 DENY 覆盖 父节点 ALLOW + 用户主体优先）
```

#### 3.11.7 实现设计 —— ACL 缓存策略

ACL 继承解析涉及多表联合查询和向上递归，需要合理缓存以避免性能问题。

**缓存方案：**

- 使用 Redis（DCS）作为分布式缓存，key 格式：`acl:{resourceType}:{resourceId}`
- 缓存值为序列化后的有效 ACL 条目列表（JSON）
- TTL 设为 30 分钟，防止内存膨胀

**缓存失效策略：**

- 当资源的 ACL 条目发生变更时，发送 `AclChanged` 领域事件
- 事件监听器不仅清除该资源自身的缓存，还会**级联清除所有子孙资源**的 ACL 缓存（因为子孙资源可能继承该资源的 ACL，变更后它们的有效 ACL 也变了）
- 级联清除范围：该资源及其所有子类别、子文档的缓存 key
- 为减少 Redis 的 DEL 操作次数，使用 Redis 的 `SCAN + DEL pattern` 批量清除

**缓存预热：**

- 知识库被访问时，后台异步预加载该知识库下所有文档的 ACL 缓存
- 避免首次访问时的冷启动延迟

### 3.12 功能编号：权限判定引擎

#### 3.12.1 功能概述

权限判定引擎是系统授权的统一入口，整合 RBAC（角色权限）、ACL（资源级细粒度权限）、ABAC（属性策略）三层机制，对每一次资源访问请求做出 ALLOW 或 DENY 的判定。判定结果写入审计日志。

#### 3.12.2 SR 设计

| 需求编号 | 需求描述 |
|---------|---------|
| F-097 | **RBAC**：角色→权限码映射作为第一道门禁 |
| F-098 | **ABAC**：策略引擎基于属性条件进行二次过滤 |
| F-099 | **细粒度**：ACL 解析结果作为资源级权限覆盖 |

#### 3.12.3 实现设计 —— 判定流程

权限判定入口 `PermissionChecker.check(User user, String operation, Resource resource)`：

```java
public Decision check(User user, String operation, Resource resource) {

    // ===== Layer 1: RBAC 门禁 =====
    Set<String> permissions = rolePermissionCache.get(user.getId());
    if (permissions == null) {
        permissions = loadUserPermissions(user);
        rolePermissionCache.put(user.getId(), permissions);
    }
    if (!permissions.contains(operation)) {
        auditLog.deny(user, operation, resource, "RBAC: 角色无此权限");
        return Decision.DENY;
    }

    // ===== Layer 2: ACL 细粒度检查 =====
    List<AclEntry> effectiveAcl = aclService.resolveEffectiveAcl(
        resource.getType(), resource.getId());

    // 查找匹配当前用户和操作的 ACL（用户主体优先于角色主体）
    AclEntry userAcl = findAclMatch(effectiveAcl, USER, user.getId(), operation);
    if (userAcl != null) {
        if (userAcl.effect == DENY) {
            auditLog.deny(user, operation, resource, "ACL: 用户级显式拒绝");
            return Decision.DENY;
        }
        auditLog.allow(user, operation, resource, "ACL: 用户级显式允许");
        return Decision.ALLOW;
    }

    // 检查角色主体 ACL
    for (Role role : user.getRoles()) {
        AclEntry roleAcl = findAclMatch(effectiveAcl, ROLE, role.getId(), operation);
        if (roleAcl != null) {
            if (roleAcl.effect == DENY) {
                auditLog.deny(user, operation, resource, "ACL: 角色级显式拒绝");
                return Decision.DENY;
            }
            auditLog.allow(user, operation, resource, "ACL: 角色级显式允许");
            return Decision.ALLOW;
        }
    }

    // ===== Layer 3: ABAC 策略过滤 =====
    EvalContext ctx = buildEvalContext(user, resource);
    Long kbId = resource.getKnowledgeBaseId();
    PolicyResult pr = policyEvaluator.evaluate(kbId, operation, ctx);

    if (pr.effect == DENY) {
        auditLog.deny(user, operation, resource, "ABAC: " + pr.policyName);
        return Decision.DENY;
    }
    if (pr.effect == ALLOW) {
        auditLog.allow(user, operation, resource, "ABAC: " + pr.policyName);
        return Decision.ALLOW;
    }

    // ===== Default: RBAC 通过且无 DENY 策略, 放行 =====
    auditLog.allow(user, operation, resource, "默认: RBAC通过");
    return Decision.ALLOW;
}
```

#### 3.12.4 实现设计 —— 判定优先级总结

三层机制的判定优先级从高到低：

| 优先级 | 层级 | 说明 |
|--------|------|------|
| **1（最高）** | ACL 显式 DENY | 用户或角色在资源上被明确拒绝 |
| **2** | ACL 显式 ALLOW | 用户或角色在资源上被明确允许 |
| **3** | ABAC DENY | 策略引擎判定拒绝 |
| **4** | ABAC ALLOW | 策略引擎判定允许 |
| **5（默认）** | RBAC 默认 ALLOW | 角色权限已通过，无 DENY 拦截 |

**关键设计原则：**

- **DENY 覆盖 ALLOW**：任何层的 DENY 都能否决下层的 ALLOW
- **显式覆盖隐式**：ACL 是管理员/用户主动配置的显式授权，其权威性高于 ABAC 的自动策略
- **用户主体覆盖角色主体**：用户级别的 ACL > 角色级别的 ACL（更精确）
- **RBAC 是地板而非天花板**：RBAC 通过是必要条件，但不充分；ACL/ABAC 可在此基础上进一步收紧

#### 3.12.5 实现设计 —— 性能优化

1. **RBAC 角色权限缓存**：用户登录时加载角色→权限码映射，存入 Redis，key: `user:perm:{userId}`，TTL=30min。角色变更时通过事件失效
2. **ABAC 策略缓存**：知识库级别的策略列表含编译后的 AST，key: `abac:policy:{kbId}`，TTL=60min。策略变更时失效
3. **ACL 有效权限缓存**：解析后的有效 ACL 列表，key: `acl:{type}:{id}`，TTL=30min。ACL 变更或继承变更时级联失效
4. **判定短路优化**：RBAC 不通过 → 直接返回 DENY，跳过 ACL 和 ABAC 评估。ACL 显式命中 → 直接返回结果，跳过 ABAC 评估
5. **批量判定接口**：对于文档列表查询等场景，提供批量判定接口 `batchCheck(List<Resource>)`，合并加载 ACL 缓存和 ABAC 策略，减少 Redis 往返次数

### 3.13 功能编号：系统字典管理

#### 3.13.1 功能概述

系统字典提供统一的受控词汇表管理，用于约束元数据（metadata）中关键属性的可选值范围。字典不替代现有的元数据表——元数据仍然是 key-value 存储（`document_metadata` 等表），字典仅负责校验和前端 UI 的可选值数据源。

**核心概念：**

- **字典类型（dict_type）**：定义一个属性类别（如"产品"、"文档类型"），并声明该类别管控哪些 metadata 键名
- **字典条目（dict_item）**：该类别下的合法取值（如产品下的 `Hi3516CV610`）

**主要使用场景：**

| 场景 | 说明 |
|------|------|
| 导入压缩包 | 用户在导入预览页通过下拉框为文件/目录选择产品、芯片型号等属性，下拉数据来源于字典条目。**导入时只能选择已有条目，不可新增/编辑/删除字典** |
| 文档元数据编辑 | 前端编辑文档的 `doc_type`、`sensitivity` 等受控属性时，提供规范的可选值列表 |
| ABAC 策略配置 | 管理员编写策略条件表达式时，前端提示合法的属性值选项（如 `res.doc_type` 的可选值） |

**与元数据表的关系（桥接模式）：**

```
字典表（数据源 + 校验规则）              元数据表（实际存储）
```

#### 3.13.3 实现设计

1. **字典类型创建**：校验 type_code 唯一性（含已软删除的同名类型）→ 持久化
2. **字典条目创建**：校验同 type_code 下 value 唯一性 → 持久化
3. **删除字典条目**：软删除（`status=0`）。不检查是否有文档已引用该值——元数据写入后是历史事实，删字典条目仅影响"未来的可选选项"，不影响已有数据
4. **导入时的字典交互**：前端展示树形预览时，每个文件/目录可设置受控属性（下拉多选，如同时选多个产品标签）。下拉选项从字典查询接口获取。导入页面不提供字典增删改入口——用户如需新增字典值，需先到字典管理页面操作
5. **字典修改即时生效**：字典读频率低，不需要缓存层

**核心业务规则（已实现）：**

1. **typeCode 创建后不可修改**（2026-08 用户确认，像角色 `is_preset` 一样）：预置与自定义类型统一规则——typeCode 是跨模块稳定契约锚点（controlled_meta_keys 绑定、前端/服务引用、条目关联），编辑接口不接受 typeCode（body 只含 typeName/controlledMetaKeys），打错编码删除重建即可（部分唯一索引已支持软删重建同名）。命名规范：`^[a-z][a-z0-9_]{0,49}$`，非法 → A0420 + `dictTypeCodeInvalid`。
2. **预置类型不可删除**（2026-08 用户确认）：`is_preset=true` 的类型（product/chip/version/sensitivity，migration_006 种子数据）删除时拒绝，返回 A0420 + `dictPresetTypeCannotDelete`。预置类型下的条目不保护（普通数据，管理员自由维护）。
3. **类型删除级联软删条目**（2026-08 用户确认）：`kb_dict_items.status=0 WHERE type_code=?`，同时白名单缓存失效。
4. **条目 sortOrder 例外**（2026-08 用户确认）：编辑条目时 sortOrder 不传 = **保持原值**（不参与全量替换）；创建时不传 = 同级最大 + 1（首个从 1 开始）。
5. **修改 value 不影响历史元数据**：元数据写入后是历史事实，改/删字典值仅影响"未来的可选选项"；管理界面需提示用户。
6. **typeCode/条目 value 唯一性**：部分唯一索引 `WHERE status=1`（软删后可重建同名），详见 migration_005。
7. **缓存失效**：类型 create/edit/delete 后调用 `DictMetaKeyCacheService.evictCache()`（一次删除白名单 `dict:active-meta-keys` 与值缓存 `dict:active-meta-key-values` 两个 key）；**条目 create/edit/delete 后调用 `DictValueValidator.evictCache()` 仅删除值缓存 `dict:active-meta-key-values`**（条目操作不影响 key 白名单）。直接改库（绕过应用 CRUD）后调用 `POST /system/dict/cache/refresh` 手动失效两个缓存，避免等待 24 小时 TTL。
8. **逻辑关联**：`kb_dict_items.type_code` 与 `kb_dict_types.type_code` 是逻辑关联（无物理外键，与项目其他表一致）；typeCode 不可修改后外键恢复需求已不存在。

**SSE 端点实现模式（RESTEasy Reactive 3.37 + HR 3.4.2 实测定稿）**：方法返回 `Multi<OutboundSseEvent>` + `@Produces(SERVER_SENT_EVENTS)`，**全响应式链**：`prepare() → onItem().transformToMulti(stream())`，prepare 失败与模型失败统一用 `onFailure().recoverWithItem(errorEvent)` 转 **`event:error` 命名事件**（head 已写，无法转 JSON，前端统一监听 error 事件）。**四个被实测否决的方案**：① `@Blocking` + await —— HR000068（HR 硬断言必须 EventLoop 线程，worker 线程直接炸）；② `@RunOnVirtualThread` + await —— 同样 HR000068（虚拟线程也非 EventLoop）；③ `Uni<Multi<T>>` 返回类型 —— RESTEasy 3.37 编译期不识别嵌套流，Multi 被当普通对象序列化；④ 注入 `@Context SseEventSink` 参数（jakarta 阻塞式 SSE API）—— RESTEasy 自动把方法调度到 worker 线程池 → HR000068。核心矛盾：HR 只能 EventLoop 执行，但 await 阻塞 EventLoop 被 Mutiny 禁止，SSE head 在订阅前已写出。**唯一可行：返回 Multi + 全响应式 + 错误事件协议**（模型失败/超时/空回答/会话不存在/越权统一 error 事件）。

**SSE 流式错误处理协议（2026-08-13 定稿）**：
- **流前错误**（SSE head 未写）：全部走统一 JSON 错误响应。① body 缺失 → 方法参数 `@NotNull` 拦截 → 400 + A0400（Bean Validation 对 null 参数跳过，必须显式 @NotNull）；② 非法 JSON body → RESTEasy 抛 WebApplicationException(400)，WebApplicationExceptionMapper 4xx 透传状态码 + A0421 参数格式错误；③ 业务异常（会话不存在/越权 A0430）→ prepare 阶段 `@Blocking` await 抛异常走 BusinessExceptionMapper。
- **流中错误**（head 已写，无法改 HTTP 状态/content-type）：统一发 **`event:error` 命名事件 + JSON data**（`{"code":"C0001","message":"..."}`），然后正常结束流。覆盖：模型连不上/5xx/超时（C0001 模型服务调用失败）、模型返回空回答（C0001 空回答消息，不落库 ASSISTANT）。前端监听 error 命名事件展示原因；连接断（无 error 事件）视为未知失败兜底。
- **模型挂死保护**：模型流 `ifNoItem().after(180s).failWith(...)`（Mutiny 3 API，每个 onItem 重置计时）；REST Client `read-timeout: 0`（SSE 长连接不设读超时，防思考期误杀）。
- **异常映射 content-type**：SSE 端点方法标 `@Produces(SERVER_SENT_EVENTS)` 会让所有异常响应继承 event-stream——**全部 8 个 ExceptionMapper 必须显式 `.type(MediaType.APPLICATION_JSON)`**（2026-08 已补全：Business/ConstraintViolation/NullPointer/WebApplication/InvalidFormat/Global/IOException/MutinyTimeout）。
- **REST Client 配置键**：`@RegisterRestClient(configKey="model-service")` 必须用 `quarkus.rest-client.model-service.url`（Quarkus 风格），**不能用 `model-service/mp-rest/url`**（MP 风格），否则运行时 `Unable to determine the proper baseUrl/baseUri`。
- **TEXT 列映射**：PO 中 `String` 字段对应 DDL `TEXT` 列必须显式 `@Column(columnDefinition = "TEXT")`，否则 Hibernate schema 校验报 "found [text] but expecting [varchar(255)]"（conversation_messages.content 已修）。
- **Mutiny 3 API 注意**：`ifNoItem().after(Duration)`（非 onTimeout）、`onCompletion().continueWith(Supplier<Iterable>)`（完成时追加 items，非 concat）。

| 有文件 | /kw/chat/file_chat | knowledge_id = temp_kb_id |
| 无文件 + 至少一个搜索范围选中 | /kw/chat/knowledge_base_chat | knowledge_base_name = 知识库 id（按搜索范围+芯片型号跨三层元数据 + 文档类型/版本文档级过滤筛选所得首个 KB id） |
| 无文件 + 无搜索范围 | /kw/chat/chat | 纯 LLM（外部搜索由模型自行处理，暂不实现） |

历史消息：从 conversation_messages 取最近 10 轮转 `[{role: "user"/"assistant", content}]`（小写 role）传入模型服务。

**搜索范围语义（消息级）**：`searchKbEnabled`(官方库)→OFFICIAL、`searchExternalEnabled`(非官方库)→NON_OFFICIAL（字典 `official` 的值，语义由「外部搜索」改为「非官方库」）。搜索范围/芯片/深度思考/文档类型/版本随 USER 消息持久化（`conversation_messages` 6 列，migration_011+012），会话级配置已废弃移除（`conversations` 原 4 列 drop）。`knowledge_base_name` 解析：`SendMessageCommandService.prepare` 调 `KnowledgeBaseChatResolver`（端口，放 commons-dict；knowledge 实现）按 official+chip_model 跨三层元数据（knowledge_base_metadata / category_metadata / document_metadata，任一层命中即算）+ 文档类型（`documents.doc_type`，DOCUMENT/CODE/CONFIG/OTHER）/ 版本（`documents.current_version` 或 `document_versions` 历史版 `was_published=true`）文档级过滤筛选 `status=1 且 process_status=COMPLETED` 的知识库，取 `created_at` 升序首个 id；无匹配 → SSE error（A0430 noMatchingKnowledgeBase），USER 不落库。docType/version 均省略时不加文档级过滤（=全部类型/最新版）；version 省略时模型默认检索当前最新版向量（与 `DocumentVersionPO`「检索默认指向当前最新版本」一致）。后续模型支持多知识库时改传全量列表。

**规则2（搜索范围+芯片+文档类型/版本传模型，协议未定；深度思考已接通）**：`deep_think` 三端点（chat/knowledge_base_chat/file_chat）均接，模型已支持（见 `docs/智能问答接口.md`），直接下发（null 省略=模型默认 false），不再受 `send-filters` 控制；`search_scope`/`chip_models`/`doc_types`/`version` 仅 `ModelKnowledgeBaseChatRequest`（KB 检索过滤，不适用 file/plain），模型协议未定，由配置 `kb.model.knowledge-base-chat.send-filters`（默认 false）统一控制是否实际下发（null 时 JSON 省略规避 422），模型协议确认后置 true。`ModelServiceClient` 签名端到端贯通（doc_types/version 既参与 KB 解析也传模型）。各请求体均 `@JsonInclude(NON_NULL)`。

**规则3（联网搜索，已接通）**：multi 端点新增 `enable_internet_search` 三态（《RAG问答接口变更说明.md》v1.0，2026-10-21 模型端上线）：`true` 强制联网并融合知识库+联网结果、`false` 强制禁用（知识库未命中也不搜）、`null` 自动模式（知识库未命中且模型端全局配置开启才搜）。同 `deep_think`：模型已支持 → 直接下发、**不受 `send-filters` 门控**；请求侧 `SendMessageCommand.enableInternetSearch` 为消息级一次性开关，**不持久化**（无对应 `conversation_messages` 列，前端每次发消息带上即可；需要回显时再加列）。响应侧：联网结果追加在 `docs` 末尾、`doc_type=["internet_search"]`、`file` 为外网 URL，`ChatDocsEventTransformer` 对该类型项**整项原样透传**（不补 `name`/`id`/`version`），否则会被按 `/kb-files` 路径解析落空而误补哨兵 `id=doc-not-found`、前端误报「来源文档不存在」；触发联网时模型额外推送一条 `route_reasoning` 状态事件（与知识库检索同格式，后端逐字节透传，前端零改动）。

**错误码**：会话不存在/越权/已归档 → A0430 conversationNotFound；无匹配知识库 → A0430 noMatchingKnowledgeBase；重复上传文件 → A0429 conversationFileExists；文件过大 → A0705；文件类型 → A0701；chipModels 格式 → A0420。

**模块归属：** llm 模块（依赖 commons，不编译依赖 knowledge/system）。knowledge_base_name 解析经端口 `KnowledgeBaseChatResolver`（commons-dict，llm 注入、knowledge 实现），严守「llm 不依赖 knowledge」；运行期由 service 聚合注入 knowledge 实现。芯片型号选项 = 字典表（system 模块管理，type_code=chip_model），前端经字典查询接口获取，会话仅透传。

### 3.15 功能编号：命中率仪表盘（kb_stats 统计）

#### 3.15.1 功能概述

基于 multi_knowledge_base_chat 收尾事件落库的 `qa_kb_stats`（见 migration_019 + migration_020），提供检索命中率的统计查询：概览四卡（整体命中率+环比、总查询数、最高/最低芯片）、时间趋势、芯片（=知识库）维度命中率、未命中列表（含处理状态流转与 CSV 导出）。仅 multi 路径问答落统计行；file_chat / 纯 LLM 无 kb_stats 不落行。

**统计口径**：总查询数 = 时间窗内全部 qa_kb_stats 行（含闲聊，"全部计入"，仅作卡片展示）；命中率 = kb_hit=true 行数 / **有效查询数**，有效查询数 = 全部行 − `no_hit_reason='chitchat'` 的闲聊行（闲聊未触发检索，若计入分母，命中率将永远无法由未命中列表解释——2026-10-21 "命中率 82.35% 但未命中列表为空"即此口径差）；芯片维度 = 知识库维度（分母同样排除闲聊）；未命中列表 = `kb_hit` 非 true 且排除闲聊（与分母**同一谓词**，列表为空 ⟺ 命中率 100%）；环比 = 与上一个等长时间窗按同一口径对比。三处共用归一谓词 `LOWER(TRIM(COALESCE(no_hit_reason,''))) = 'chitchat'`（大小写/空白归一，NULL 归空串）。

#### 3.15.2 领域数据模型

**qa_kb_stats（问答 KB 统计表，migration_020 增列）**

| 列名 | 类型 | 说明 |
|------|------|------|
| message_id | VARCHAR PK/FK | ASSISTANT 消息 id（平台侧 assistantMessageId = conversation_messages.id；模型响应 message_id 恒为空串，禁止用于关联） |
| rag_triggered / kb_hit / degraded | BOOLEAN | 模型下发检索指标 |
| no_hit_reason / route_reason | VARCHAR | 未命中原因 / 路由原因 |
| retrieved_count / used_count | INT | 召回块数 / 注入上下文块数 |
| hit_kbs | TEXT | 命中知识库列表（逗号分隔） |
| rewritten_query | TEXT | 改写后的检索 query |
| top_score | NUMERIC | top 块相关性分数 |
| kb_stats_json | TEXT | 模型下发原始 JSON 留档 |
| query_text | TEXT | 用户问题原文（落库冗余，仪表盘单表查询） |
| account | VARCHAR | 提问账号 |
| source | VARCHAR DEFAULT 'CHAT_QA' | 来源渠道：CHAT_QA 智能问答 / RECEPTION_BOT 前台机器人 / AGENT_CALL Agent 调用（发送消息接口可选 source 参数，非法值归一 CHAT_QA） |
| handle_status | VARCHAR DEFAULT 'PENDING' | 未命中处理状态：PENDING 待处理 / PROCESSING 处理中 / RESOLVED 已补充（仅 kb_hit=false 行有业务意义） |
| selected_kbs | TEXT | 用户选择的知识库 id 列表（逗号分隔；multi 路径就绪过滤后下发模型的列表；芯片维度分母口径） |
| created_at | TIMESTAMP NOT NULL | 落库时间 |

索引：(kb_hit, created_at)、(created_at)、(handle_status)。DDL：`docs/sql/migration_019_kb_stats.sql` + `migration_020_hit_rate_dashboard.sql`。

#### 3.15.3 用户接口设计

全部端点位于 **llm 模块**，前缀 `/stats/hit-rate`，@Authenticated。时间参数 from/to 必填 yyyy-MM-dd（to 按含当日解释，内部转 `[from 00:00, to+1d 00:00)`）。

| 端点 | 方法 | 说明 |
|------|------|------|
| /stats/hit-rate/summary | GET | 概览四卡：overallRate/prevRate/totalQueries/totalHits/totalMisses/totalChitchat/max/min（极值按芯片维度；恒等式 totalQueries = totalHits + totalMisses + totalChitchat） |
| /stats/hit-rate/trend | GET | 时间趋势（granularity=day/week/month 默认 day；date_trunc 分桶；每点 hitRate/queryCount/hitCount/chitchatCount） |
| /stats/hit-rate/by-chip | GET | 芯片维度命中率（分子=kb ∈ hit_kbs 且 kb_hit=true；分母=selected_kbs/hit_kbs 含该 kb 且非闲聊的行数） |
| /stats/hit-rate/misses | GET | 未命中列表分页（keyword 模糊/source/时间窗筛选，created_at 倒序；kb_hit 非 true 且排除闲聊，totalRow 恒等于概览 totalMisses） |
| /stats/hit-rate/misses/export | GET | CSV 导出（同筛选全量，UTF-8 BOM，Excel 兼容） |

技术要点：聚合统计用原生 SQL（unnest(string_to_array(...)) 展开逗号分隔列、date_trunc 分桶）；未命中分页/状态流转用 Panache HQL。**闲聊判定只有一处定义**（`KbStatsRepositoryImpl.chitchat/notChitchat` + `MISSES_WHERE` 内的同义 HQL，单测 `KbStatsRepositoryImplTest` 守卫），命中率分母与未命中列表共用，避免"率与列表对不上"回潮；`kb_hit` 为 NULL（模型未下发该字段）按未命中处理。芯片展示名经**落库名称快照** `qa_kb_stats.kb_names_json`（migration_021：落库时经 `KnowledgeBaseNameResolver` 端口解析 selected_kbs ∪ hit_kbs 的 id→name JSON，解析失败回退 id）查询侧 `jsonb_each_text` 展开映射后直接下发——统计是对当时事实的记录，知识库后续改名/删除不影响历史行展示。
