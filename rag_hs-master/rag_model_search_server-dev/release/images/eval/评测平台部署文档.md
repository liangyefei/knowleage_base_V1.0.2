# RAG 评测平台部署文档

## 概述

RAG 评测管理平台：基于 FastAPI + Vue3 的 RAG 系统评测工具。用户维护用例集（问题 + 标准答案 + 证据），对远端 RAG 知识库平台发起问答，用 LLM Judge 对回答打分（5 项指标），报告支持「整体汇总 → 单用例集 → 单用例」多层钻取。

> ⚠️ **源码位置**：本项目源码不在 `haisi_rag_models_server` 仓库内，而是位于其同级目录 `rag_eval_platform/`。本目录（`release/images/eval/`）仅存放部署文档，构建上下文为 `rag_eval_platform/` 项目根目录。
>
> 🔗 **Git 仓库**：<https://gitcode.com/hi_kb_base/rag_eval_tools>

**典型应用场景**：

- RAG 知识库上线前的指标评测（HitRate@K、Recall@K、Faithfulness、Answer Relevancy、Answer Correctness）
- 评测用例集版本化管理（CRUD + jsonl 批量导入）
- 评测任务并发执行 + 实时进度 + 失败日志 + 断点续跑
- 多层评测报告导出（CSV / JSON）

**与主项目的关系**：

| **项**      | **说明**                                       |
| ---------- | --------------------------------------------- |

## 构建镜像

### 1. 进入源码目录

构建上下文是源码项目根目录，不是本部署文档所在目录：

```bash
cd /data/haisi/rag_eval_platform
```

### 2. 多阶段构建

```bash
sudo docker buildx build --provenance=false --output type=docker \
  -f docker/Dockerfile \
  -t haisi-eval-platform:v1.0.0 \
  .
```

构建过程说明：

- **Stage 1（前端构建）**：`node:20-alpine` 镜像内 `pnpm install --frozen-lockfile` 装依赖 → `npm run build` 产出 `frontend/dist/`
- **Stage 2（Python 运行时）**：`python:3.11-slim` 镜像内 `pip install -r requirements.txt` 装依赖 → `pip install --no-deps deepeval==4.2.0`（避免依赖冲突）→ COPY 后端代码 + 前端构建产物 + 启动脚本
- 首次构建约 5-8 分钟（拉基础镜像 + pnpm install + pip install），后续构建命中 Docker layer cache 会快很多
- 前端 lock 文件（`pnpm-lock.yaml`）存在时用 pnpm，否则降级为 npm install

### 3. 验证本地镜像

```bash
sudo docker images | grep haisi-eval-platform
# 预期：haisi-eval-platform   v1.0.0   <IMAGE_ID>   <SIZE>   <CREATED>
```

## 部署运行

### 方式一：在源码目录用 `docker compose`（推荐）

源码目录已带 `docker-compose.yml`，配合 `.env.docker` 模板即可起服务，适合开发 / 单机部署：

```bash
cd /data/haisi/rag_eval_platform

# 1. 生成 .env（从模板复制）
cp .env.docker .env

# 2. 按需修改端口 / 并发上限 / 时区
vi .env

# 3. 修改 docker-compose.yml 中的 image 字段，指向本地或 SWR 镜像
#    image: haisi-eval-platform:v1.0.0
#    或 image: swr.cn-south-1.myhuaweicloud.com/hisilicon-rag/haisi-eval-platform:v1.0.0

# 4. 一键构建 + 启动 + 健康检查
./scripts/deploy.sh

# 或全量清理后重建（首次部署 / 环境异常时）
./scripts/deploy.sh --clean
```

`deploy.sh` 脚本会自动完成：
1. 从 `.env.docker` 生成 `.env`（若不存在）
2. 创建 `data/` 与 `backups/` 目录
3. 检查是否有评测任务在跑（运行中则中止部署避免中断）
4. `docker compose build` 构建镜像
5. `docker compose up -d` 启动容器
6. 等待健康检查通过后输出访问地址

### 方式二：纯 `docker run`（目标服务器从 SWR 拉取镜像）

适用于目标服务器无源码、只拉镜像运行的场景：

```bash
# 1. 拉取镜像
sudo docker pull swr.cn-south-1.myhuaweicloud.com/hisilicon-rag/haisi-eval-platform:v1.0.0

# 2. 准备数据目录（持久化数据库 + 日志 + 报告）
mkdir -p /data/haisi/eval-platform/data/logs \
         /data/haisi/eval-platform/data/reports
chmod -R 755 /data/haisi/eval-platform/data

# 3. 运行容器
sudo docker run -d \
  --name haisi-eval-platform \
  -p 8000:8000 \
  -v /data/haisi/eval-platform/data:/app/data:Z \
  -e EVAL_PLATFORM_DB_PATH=/app/data/eval_platform.db \
  -e EVAL_PLATFORM_LOG_DIR=/app/data/logs \
  -e EVAL_PLATFORM_REPORT_DIR=/app/data/reports \
  -e EVAL_PLATFORM_STATIC_DIR=/app/app/static \
  -e EVAL_PLATFORM_HOST=0.0.0.0 \
  -e EVAL_PLATFORM_PORT=8000 \
  -e EVAL_PLATFORM_MAX_CONCURRENT_RUNS=3 \
  -e TZ=Asia/Shanghai \
  --health-cmd="curl -sf http://127.0.0.1:8000/health || exit 1" \
  --health-interval=20s \
  --health-timeout=5s \
  --health-retries=5 \
  --health-start-period=30s \
  --restart unless-stopped \
  swr.cn-south-1.myhuaweicloud.com/hisilicon-rag/haisi-eval-platform:v1.0.0
```

> `:Z` 是 SELinux 标签（CentOS / RHEL 需要），Ubuntu / Debian 可去掉。

### 方式三：K8s Deployment + PVC 挂载（生产 / 多副本）

适用于 K8s 集群部署，用 PVC 持久化 SQLite + 日志 + 报告，支持多 Pod 共享（SFS Turbo / NFS 等支持 `ReadWriteMany` 的存储）。

#### 1. 路径不冲突说明（重要）

镜像内有两类与「目录」相关的 Dockerfile 指令，需区分清楚：

| Dockerfile 行 | 路径 | 内容 | 是否可挂 PVC 覆盖 |
| --- | --- | --- | --- |
| L55-56 `RUN mkdir -p /app/app/static` + `COPY --from=frontend-builder ... /app/app/static` | `/app/app/static` | 前端构建产物（`index.html` + JS/CSS），**镜像内 baked-in** | ❌ 覆盖会丢前端 |
| L48 `COPY app/ ./app/` | `/app/app/`（含 `api/` `core/` `models/` `worker/` 等） | 后端 Python 源码 | ❌ 覆盖会丢后端代码 |
| L51 `COPY scripts/ ./scripts/` | `/app/scripts/` | 迁移 / 备份脚本 | ❌ 覆盖会丢脚本 |
| L59-60 `COPY scripts/docker-entrypoint.sh /usr/local/bin/...` | `/usr/local/bin/docker-entrypoint.sh` | 容器入口 | ❌ 覆盖会启动失败 |
| L64 `VOLUME ["/app/data"]` | `/app/data` | 数据库 + 日志 + 报告（运行时生成） | ✅ **应挂 PVC** |

**结论**：PVC 挂到 `/app/data` 是设计意图，**安全**。PVC 覆盖的是空的 volume 子树，不会影响镜像内的前端产物或后端代码。

> ⚠️ **禁止挂载到 `/app` 或 `/app/app`**：会把镜像里 baked-in 的前端 dist / 后端源码 / 启动脚本全部覆盖掉，导致容器启动失败或前端页面空白。**只挂 `/app/data`。**

#### 2. PVC 创建（已有可跳过）

参考 PVC（华为云 SFS Turbo，500Gi `ReadWriteMany`）：

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-efs-eval
  namespace: default
spec:
  accessModes:
    - ReadWriteMany
  resources:
    requests:
      storage: 500Gi
  storageClassName: csi-sfsturbo
  volumeMode: Filesystem
```

> `csi-sfsturbo` 是华为云 SFS Turbo CSI driver，支持多 Pod 并发读写，适合 SQLite + 多副本场景（但 SQLite 多进程并发写仍需文件锁，SFS Turbo 支持 `fcntl` 锁）。若用 NFS 也可，但 `accessModes` 要对应 NFS 的 `ReadWriteMany`。

#### 3. Deployment + Service

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: haisi-eval-platform
  namespace: default
  labels:
    app: haisi-eval-platform
spec:
  replicas: 1                      # SQLite 单写者，建议 replicas=1；要多副本需改外部 DB
  selector:
    matchLabels:
      app: haisi-eval-platform
  template:
    metadata:
      labels:
        app: haisi-eval-platform
    spec:
      containers:
        - name: eval-platform
          image: swr.cn-south-1.myhuaweicloud.com/hisilicon-rag/haisi-eval-platform:v1.0.0
          imagePullPolicy: IfNotPresent
          ports:
            - containerPort: 8000
              name: http
          env:
            - name: EVAL_PLATFORM_DB_PATH
              value: /app/data/eval_platform.db
            - name: EVAL_PLATFORM_LOG_DIR
              value: /app/data/logs
            - name: EVAL_PLATFORM_REPORT_DIR
              value: /app/data/reports
            - name: EVAL_PLATFORM_STATIC_DIR
              value: /app/app/static
            - name: EVAL_PLATFORM_HOST
              value: "0.0.0.0"
            - name: EVAL_PLATFORM_PORT
              value: "8000"
            - name: EVAL_PLATFORM_MAX_CONCURRENT_RUNS
              value: "3"
            - name: TZ
              value: Asia/Shanghai
          volumeMounts:
            - name: data
              mountPath: /app/data     # 只挂这里，不要挂到 /app 或 /app/app
              subPath: ""              # 直接用 PVC 根；多服务共享一 PVC 时建议 subPath 隔离
          readinessProbe:
            httpGet:
              path: /health
              port: http
            initialDelaySeconds: 10
            periodSeconds: 10
            timeoutSeconds: 5
          livenessProbe:
            httpGet:
              path: /health
              port: http
            initialDelaySeconds: 30
            periodSeconds: 20
            timeoutSeconds: 5
            failureThreshold: 5
          resources:
            requests:
              cpu: "500m"
              memory: "1Gi"
            limits:
              cpu: "2000m"
              memory: "4Gi"
      volumes:
        - name: data
          persistentVolumeClaim:
            claimName: pvc-efs-eval
---
apiVersion: v1
kind: Service
metadata:
  name: haisi-eval-platform
  namespace: default
spec:
  selector:
    app: haisi-eval-platform
  ports:
    - name: http
      port: 8000
      targetPort: http
      protocol: TCP
  type: ClusterIP                    # 集群内访问；对外暴露改 NodePort / LoadBalancer / Ingress
```

#### 5. K8s 部署注意事项

| 关注点 | 说明 |
| --- | --- |
| **副本数** | SQLite 是单写者模型，`replicas: 1` 最稳；要多副本横向扩容需换 PostgreSQL / MySQL（Dockerfile 已装 SQLAlchemy，理论上可换，但要改 `app/database.py` 的 `DATABASE_URL`） |
| **PVC 挂载路径** | 只挂 `/app/data`；挂到 `/app` 或 `/app/app` 会覆盖镜像内前端 / 后端代码 |
| **subPath 隔离** | 若 PVC 与其他服务共用，建议 `subPath: eval-platform/data` 避免目录冲突；本平台独占 PVC 可不设 |
| **首次启动初始化** | `docker-entrypoint.sh` 会跑 `Base.metadata.create_all` + `migrate_*.py` + `init_db.py`，全部幂等；PVC 第一次挂载是空目录，entrypoint 自动建表 + 种子配置 |
| **SQLite WAL + PVC** | SFS Turbo 支持 `fcntl` 文件锁，WAL 模式可正常工作；但跨 Pod 写仍建议 `replicas: 1`，避免多 Pod 同时写库造成「脑裂」（见下方数据持久化小节） |
| **资源限制** | `requests: 500m / 1Gi` 起步；评测任务并发会拉起 RAG + LLM Judge 子进程，内存峰值可达 2-3Gi，`limits` 建议给到 `4Gi` |
| **滚动更新** | `imagePullPolicy: IfNotPresent` + 显式 tag（如 `v1.0.0`）配合 `kubectl set image` 滚动；不要用 `:latest`，避免缓存命中导致更新不生效 |
| **对外暴露** | `Service.type=ClusterIP` 仅集群内访问；外网用 Ingress 或 `type=LoadBalancer`，配合云 ELB / EIP |

### 系统配置（运行时）

以下配置在容器启动后通过浏览器访问「系统配置」页面填写，不打包进镜像：

- **RAG API URL**：远端 RAG 知识库平台地址（如 `http://192.168.x.x:7861`）
- **登录凭证**：RAG 平台的用户名 / 密码
- **知识库列表**：评测目标知识库 ID 列表
- **评测参数**：Top-K、并发数、超时等
- **评测阈值**：5 项指标的及格线
- **裁判模型参数**：OpenAI 兼容端点（默认 DashScope）+ API Key + 模型名

敏感字段（`password` / `api_key`）在 `GET /api/v1/config` 响应中自动脱敏。

## 数据持久化

容器内 `/app/data` 是唯一的持久化目录，包含三类数据：

| 子路径 | 内容 | 备份策略 |
| --- | --- | --- |
| `/app/data/eval_platform.db` | SQLite 数据库（含 WAL 文件 `.db-wal` / `.db-shm`） | 用 `sqlite3 .backup` 在线热备份，不要直接 cp |
| `/app/data/logs/` | 评测任务运行日志 | 直接 tar 打包 |
| `/app/data/reports/` | 评测报告 CSV / JSON | 直接 tar 打包 |

> ⚠️ **SQLite WAL 注意事项**：
> - 服务运行期间禁止任何外部进程（脚本 / CLI / 手工命令）直接读写 `eval_platform.db*`，外部删除 / 替换 `-wal` 文件会造成「孤儿 WAL 脑裂」
> - 备份用 `scripts/backup.sh`（已用 `sqlite3 .backup` 做热备份），不要直接 `cp` 活库
> - 怀疑脑裂（重测成功但报告页显示旧数据、API 多次请求结果不一致）时，重启容器即可恢复单一 WAL 链

## 运维命令

```bash
# 容器状态
sudo docker ps | grep haisi-eval-platform

# 实时日志
sudo docker logs -f haisi-eval-platform

# 最近 100 行日志
sudo docker logs --tail 100 haisi-eval-platform

# 重启容器

sudo docker exec -it haisi-eval-platform bash

# 资源占用
sudo docker stats haisi-eval-platform

# 停止并删除容器（数据保留在 ./data）
cd /data/haisi/rag_eval_platform
```

| 脚本 | 作用 |

## 故障排查

| 问题 | 可能原因 | 解决方案 |
| --- | --- | --- |
| 容器启动后立即退出 | 数据库迁移失败 / 缺依赖 | `docker logs haisi-eval-platform` 查看错误栈 |
| 健康检查超时 | uvicorn 启动慢或建表失败 | `docker logs` 看是否到 `Application startup complete`；检查 `/app/data` 权限 |
| 前端页面空白 | 镜像构建时前端产物未 COPY 进去 | `docker exec haisi-eval-platform ls /app/app/static/` 应有 `index.html`；缺则 `docker compose build --no-cache eval-platform` 重建 |
| 评测任务卡住 | worker 子进程崩溃 / RAG 平台不可达 | `docker exec haisi-eval-platform cat /app/data/logs/*.log \| tail -100` 查 worker 日志；在系统配置页测 RAG 连通性 |
| 重测结果保存不上、展示随机回退到旧数据 | SQLite WAL 脑裂（外部进程碰过 `-wal` 文件） | 重启容器恢复单一 WAL 链，再重新执行重测 |
| 端口 8000 被占用 | 宿主机已有其他服务占用 | 改 `.env` 中 `EVAL_PLATFORM_PORT=9000`，或 `docker run -p 9000:8000` |
| `docker push` 报 `Invalid image, fail to parse 'manifest.json'` | 构建时未加 `--provenance=false --output type=docker` | 用 `sudo docker buildx build --provenance=false --output type=docker ...` 重建再推 |

更多故障排查与回滚流程详见源码仓库 `rag_eval_run.md` 第八 / 九节。
