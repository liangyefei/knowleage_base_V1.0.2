## 0. 结论速览

### 0.1 四条必须保留的设计

1. **PDP / PEP 分离**：后端决定"这个文档对这个人是否可见"，本服务只执行过滤；
2. **稳定身份**：`file_id`（= Kafka `documentId`）是唯一身份，跨 DB / Milvus / dual-mcp / mempalace 一致；
3. **硬过滤 fail-closed / 软过滤 fail-open**；
4. **查询时解析**：ACL、发布状态、灰度不写 chunk，变更不触发重索引。

### 0.3 新模型的核心变化

```
旧假设（v3.0-v3.2）：file_id 指向"逻辑文件"，同一 file_id 下有 v1.0 / v1.1 / v1.2
新事实（v4.0）    ：每个版本 = 一条独立文档记录 = 独立 documentId = 独立目录
                    v1.0 → file_id A     v1.2 → file_id B     两者互不相关
```

由此产生的三条硬结论：

1. **`file_id` 就是版本身份**，不需要复合键、不需要 `version_id`、不需要 label 归一化比较；
2. **不存在"默认版本"**：检索层无法、也不应该判断"同名的 A 和 B 哪个是最新"；
3. **旧版本下线完全依赖后端发布状态**：后端必须在发布新版本时把旧文档置 `DEPRECATED` / `ARCHIVED`，否则新旧版本会同时被检索到（这是本方案唯一的强制外部前提，§7.1）。

## 1. 背景与目标

### 1.1 业务背景

1. **多版本共存**：所有版本文件共存于不同路径（后端按 `documentId` 分目录），每个文档带版本标签，可按时效/版本标签检索；
2. **文件级灰度发布**：灰度状态的文档只对白名单用户可检索；
3. **账号权限管理**：无权限账号不能基于受限文档做问答；
4. **标签来源**：版本 / 灰度 / 权限 / 业务标签由后端"标签查询接口"按 `file_id` + `user_id` 返回；
5. **过滤方式**：检索后过滤（post-filter），不做 ANN 前置过滤下推；
6. **入库与删除**：全部由后端经 Kafka 触发，本服务**不提供**面向前端的上传/删除 HTTP 接口。

### 1.2 目标

- **文档可见性正确**：无权限、未发布、非白名单灰度的 chunk 不进入最终 LLM 上下文；
- **三路一致**：Milvus 文档路、dual-mcp 代码路、mempalace 记忆路语义一致；
- **旧版本不干扰**：旧版本由后端置 `DEPRECATED` 后不再参与默认检索；
- **显式版本可查**：`version=v1.0` 只召回打了该标签的文档（仍需可见）；
- **软过滤可降级**：tags / category 召回不足时降级，不产生空答案；
- **不改检索架构**：保留"三路召回 + RRF + Reranker + 代码路保底"。

### 1.3 设计原则

| 原则 | 含义 |
|------|------|
| **两级后过滤** | Stage 1 文件级（调接口，RRF 前）+ Stage 2 chunk 级（纯本地，RRF 后） |
| **一文档一记录** | 每个版本独立 `file_id`，接口按文档返回事实，不做跨文档聚合 |
| **PDP / PEP 分离** | 后端算 `qa_visible` / `acl_allow`；本服务只执行，不实现 RBAC |
| **事实与请求分离** | 接口只返回与请求无关的事实；`version=v1.0` 这类请求条件在本地过滤，缓存可复用 |
| **硬过滤 fail-closed** | 接口失败、文档未知、字段缺失 → 丢弃 |
| **软过滤 fail-open** | tags / category 不足时降级为不过滤 |
| **策略不落 chunk** | ACL / 发布状态 / 灰度不写 chunk；`tags` / `category` / `sensitivity` / `version_label` 不可变，可写 |
| **自适应放大** | `factor` 按实测通过率动态计算 |
| **精排预算封顶** | `RERANK_INPUT_MAX` 硬上限 |
| **可观测可回滚** | `legacy / shadow / enforce` 三态 |

## 3. 总体设计

### 3.1 分层结构

```
┌──────────────────────────────────────────────────────────┐
│ 控制面（后端）                                            │
│  文档记录(documentId) / 版本标签 / 发布状态 / 灰度白名单 / ACL │
│  ← 通过「标签查询接口」按 file_id + user 返回，不写 chunk     │
└──────────────────────────┬───────────────────────────────┘
                           ↓ 查询时调用
┌──────────────────────────────────────────────────────────┐
│ 召回层：三路都不做细粒度过滤                                │
│  RECALL_TOP_K = ceil(top_k × factor)                     │
└──────────────────────────┬───────────────────────────────┘
                           ↓
┌──────────────────────────────────────────────────────────┐
│ Stage 1：文件级授权过滤（RRF 前，调接口）                    │
│  按 (kb, file_id) 去重 → 每 KB 一次 query_by_files          │
│  硬：found && qa_visible（或 acl_allow for 审计）           │
│  软：tags(and/or) / category                              │
└──────────────────────────┬───────────────────────────────┘
                           ↓
┌──────────────────────────────────────────────────────────┐
│ 融合层：RRF（key = 内容哈希 + file_id）+ metadata 归并      │
│  合规文档名次前移                                          │
└──────────────────────────┬───────────────────────────────┘
                           ↓
┌──────────────────────────────────────────────────────────┐
│ Stage 2：chunk 级复核（纯本地）                             │
│  复核 qa_visible / 显式 version label / 标签一致性           │
└──────────────────────────┬───────────────────────────────┘
                           ↓
┌──────────────────────────────────────────────────────────┐
│ 精排层：RERANK_INPUT_MAX 截断 → Reranker → top_n(≤30)      │
│  代码路保底只从已过滤 code_pool 补                          │
└──────────────────────────┬───────────────────────────────┘
                           ↓
┌──────────────────────────────────────────────────────────┐
│ 组装层：位置强化排序 → 7:3 预算 → LLM                       │
└──────────────────────────────────────────────────────────┘
```

### 3.2 过滤维度

| 维度 | 性质 | 数据来源 | Stage 1 | Stage 2 | 不足时 |
|------|------|---------|---------|---------|--------|
| 账号权限 | 硬 | `acl_allow` | 拒绝即丢弃 | 复核（防过期） | fail-closed |
| 发布状态 / 灰度 | 硬 | `qa_visible`（后端已综合 status+gray+acl） | 为 false 即丢弃 | 复核 | fail-closed |
| 显式版本 | 硬 | 请求 `version` + 接口 `version_label` | label 不匹配即丢弃 | 复核 | 空 + `version_not_visible` |
| tags | 软 | 请求 + 接口 `tags` | 按 `tag_match` 交/并 | 复核 | 去软重试 |
| 分类 | 软 | 意图 + 接口 `category` | 求交 | — | 去软重试 |

> **没有"默认版本"这一维**：`qa_visible` 已包含"该文档是否应当出现在问答里"。哪个版本在线由后端决定。

### 3.3 为什么 `version_label` 不是身份

| 问题 | 说明 |
|------|------|
| 跨文档重名 | 大量文档都可以叫 `v1.0`，label 无法定位唯一对象 |
| 无聚合关系 | 后端不维护"逻辑文件"或"文件组"，无法从 label 推出"哪些文档属于同一组" |
| 唯一性由后端保证 | 后端在创建文档记录时按自身规则拒绝重复，但本服务不能依赖它做身份判定 |
| 排序不可靠 | label 由管理员手工维护，格式可能混用，不能用于版本大小排序 |

因此：

- **身份 = `file_id`**（`file_id` 本身唯一）；
- **`version_label` 只做两件事**：① 展示；② 用户显式 `version=v1.0` 时的**筛选条件**（字符串相等，大小写/首尾空白归一化）；
- **不做**：不拿 label 拼路径、不按 label 排序、不跨文档聚合、不把 label 当默认版本依据。

### 3.4 过滤位置：为什么拆两级

| 位置 | 接口调用 | 融合质量 | Reranker 成本 | 结论 |
|------|---------|---------|--------------|------|
| 召回前 pre-filter（下推 ANN） | — | 召回即合规 | 最省 | ❌ 标签只能按 file+user 实时查，无法预解析；DENY-list 例外（§8.4） |
| **Stage 1：召回后 / RRF 前** | 每 KB 1 次，入参是去重文件 | RRF 在合规候选上做 rank | 低 | ✅ 推荐 |
| Stage 2：RRF 后 / Reranker 前 | 0（本地） | 一致性复核 | 低 | ✅ 与 Stage 1 组合 |
| Reranker 后 | — | 一般 | 浪费（精排了不合规内容） | ❌ |

必须前置到 RRF 之前的理由：

1. **RRF 是 rank 融合**，先剔除不合规文档，合规文档的名次自然前移（filter-then-rank）；
2. **接口调用量靠"按文件去重"降下来**（chunk → 文件降一个量级），不靠 RRF 截断；
3. **一次调用覆盖三路**；
4. **`code_list` 泄漏自动消失**（Stage 1 直接过滤它本身）。

保留 Stage 2 的理由：

- **防事实过期**：Stage 1 到精排之间仍可能有权限变更，复核成本为零；
- **防元数据不一致**：chunk 自带的 `file_id` / `version_label` 与接口事实不一致时丢弃并告警。

```
Stage 1 回答：这个文档对该用户可见吗？（需要后端）
Stage 2 回答：这条 chunk 属于这个文档、且标签一致吗？（本地）
```

### 3.5 召回放大：按通过率自适应

post-filter 要保证 k 条通过，需要 `k / s` 条候选（`s` = 通过率）。

```
factor        = clip(1 / max(pass_rate_ewma, 0.05), 3, 20)
RECALL_TOP_K  = ceil(top_k × factor)
RERANK_INPUT_MAX = 60
```

- `pass_rate_ewma` 按 **KB × 用户群体**（普通 / 灰度 / 管理员）维护，用 "Stage 1 保留数 / 输入数" 更新，α=0.2；
- 冷启动用 `POST_FILTER_SAFETY_FACTOR_INIT`（默认 10）；
- 分级扩容：Stage 2 后 `len(docs) < max(3, ceil(top_k × 0.5))` → `factor × 2` 重查一次（最多 2 轮），facts 走缓存不重复调接口。

### 3.6 请求级数据流

```
chat request (user_id, kb_names, version, top_k, tags, tag_match, intent)
  → _phase_route：规则闸门 → LLM route（可选）→ 关键词
  → _phase_retrieve：
       三路召回 → Stage 1（文件级）→ RRF（带 file_id）→ Stage 2（本地复核）
       → 截断 RERANK_INPUT_MAX → Reranker → 代码路保底
  → _phase_assemble：位置强化 → 7:3 预算 → LLM
```

### 4.5 检索语义

| 请求 | 语义 | Stage 1 | Stage 2 |
|------|------|---------|---------|
| 不传 `version` | 只返回 `qa_visible=true` 的文档 | 文件级 `qa_visible` | 复核 |
| `version=v1.0` | 在可见文档中再按 label 收窄 | label 归一化相等 | 复核 |
| `version_scope=all`（管理员审计） | 不加发布状态限制 | `acl_allow` 仍生效 | 跳过 `qa_visible`，记审计 |
| 软过滤（tags / 意图） | 在硬集合内收窄 | `tag_match` + `category` | — |

- **不存在"默认版本"**：不猜"哪个版本最新"；旧版本是否下线由后端 `release_status` 决定；
- **显式版本不可见时返回空** + `version_not_visible`，不回退；
- `version=v1.0` 的语义是"该 KB 内所有打了 v1.0 标签的文档"，不假设它们属于同一逻辑文件。

### 4.6 生命周期

> 全部由 Kafka 消息触发，本服务无同步写接口。

**发布（`DOCUMENT_PUBLISHED` / `DOCUMENT_RETRY_PROCESS`）**：

1. 校验 `documentId` / `file_version_label` / `filePath`（§4.8.2）；
2. 幂等：`file_id` 已处理成功 → 直接回成功；
3. `resolve_sfs_path(filePath)` 读文件；
4. 解析 → doc.metadata 写入身份与标签 → 写 Milvus；
5. 写 `file_doc`（含 `file_id`）；
6. `knowledge_file` **按 `file_id` upsert**（同名多版各一行）；
7. 写 dual-mcp / mempalace；
8. 回调。

**归档 / 删除（`DOCUMENT_ARCHIVED` / `DOCUMENT_DELETED`）**：

1. **按信封 `documentId` 定位**，绝不按 `file_name`；
2. 新增 `list_doc_ids_by_file_id(kb, file_id)` 取 pk → 删 Milvus；
3. 删 dual-mcp / mempalace 中该 `file_id` 的条目；
4. `file_doc` 删该 `file_id` 的行；
5. `ARCHIVED` 保留 `knowledge_file` 行并标 `archived`（可从 SFS 重新向量化恢复）；`DELETED` 删除 `knowledge_file` 行并清理中间文件；
6. 同名其他文档**不受影响**（这是必须验收的点）。

> 归档是否真的需要删向量，见专项说明 `DOCUMENT_ARCHIVED回调方案说明.md`：若后端已用 `release_status` 控制可见性，推荐归档在模型端改为 no-op。

**清理（`cleanup_old_versions` → 改名 `cleanup_deprecated_docs`）**：

- 触发依据由后端状态驱动：`release_status ∈ {DEPRECATED, ARCHIVED}` 且超过 N 天；
- 每个待清理文档走上面的删除流程，**不能只删 blob**；
- 孤儿检测：`file_doc` 有 pk 但 Milvus 无、Milvus 有 pk 但 `file_doc` 无、`file_doc.file_id` 不在 `knowledge_file`。

### 4.7 版本对比（verdiff）

- 当前 `_search_version_chunks` 用 `SearchFilter(version=label)`（[version_diff.py L62-80](file:///d:/Code/haisi/haisi_rag_models_server/server/chat/pipeline/version_diff.py#L62-L80)）→ 保留，改成归一化比较；

### 4.8 Kafka 消费侧（身份来源）

#### 4.8.1 payload 扩展

| 字段 | 事件 | 现状 | 目标 |
|------|------|------|------|
| `file_version_label` | `PUBLISHED` / `RETRY_PROCESS` | 可选 | **必填**（展示与显式筛选需要） |
| `file_version_label` | `ARCHIVED` / `DELETED` | 无 | 可选，仅日志/校验；定位靠 `documentId` |
| `tags` | `PUBLISHED` / `RETRY_PROCESS` | 可选，OR | 保留；`and/or` 由检索侧 `tag_match` 决定 |
| `category` | 同上 | 无 | 新增，可选 |
| `sensitivity` | 同上 | 无 | 新增，可选；仅展示/审计 |
| `filePath` | `ARCHIVED` | 契约写"无" | 补进契约（代码已读，缺失会走 no-op） |

#### 4.8.2 消费侧硬校验

| # | 校验 | 失败行为 |
|---|------|---------|
| 1 | `documentId` 非空且为 UUID | `PROCESSING_FAILED(400)`，不写 chunk |
| 2 | `file_version_label` 非空（发布类事件） | 同上 |
| 3 | `filePath` 为相对路径、无 `..`、解析后落在 `SFS_MOUNT_PATH` 内 | 同上 |
| 4 | `kbId` 有效且与消息一致 | 同上 |

#### 4.8.3 幂等

- 幂等键 = **`file_id`**（一个版本一条文档记录，天然唯一）；
- 重复投递 `PUBLISHED`：`content_sha256` 相同 → 直接回成功；内容不同（理论上后端不会）→ `PROCESSING_FAILED(409)`，**不覆盖**已处理文档；
- `RETRY_PROCESS` 是显式重建语义 → 先按 `file_id` 删旧 pk，再重建。

#### 4.8.4 存量迁移

- 后端为存量文档补 `documentId` → 产出 `(kb_name, file_name, md5) → documentId` 映射表；
- 本服务回填 `knowledge_file.id`、`file_doc.meta_data.file_id`、Milvus `metadata.file_id`；
- **回填率 100% 才允许开硬过滤**。

## 5. 后端标签查询接口合约（P1）

### 5.1 定位

- **PDP**：后端账号/文档服务，决定可见性；
- **PEP**：本服务，负责调用与执行；
- 本服务不实现 RBAC/ABAC，不维护用户表、角色表、ACL 表。

### 5.2 请求（文件级、批量）

```json
POST /api/v1/rag/labels/query_by_files
Headers:
  X-Internal-Token: <token>

{
  "user_id": "u123",
  "kb_name": "9f0e3467-2eb0-434e-9452-0b824bd8ed52",
  "include_archived": false,
  "files": [
    {"file_id": "d3c1f0a2-8b7e-4a39-9f10-2e1d6c3b7a90", "source": "kb/9f0e3467/d3c1f0a2/需求文档v3.xlsx"},
    {"file_id": null, "source": "code/drivers/gpio.c"}
  ]

```

要点：

- **`kb_name` 就是后端 `kbId`**，无需映射；
- 入参是**文档**，不是 chunk；调用方先按 `(kb_name, file_id)` 去重，数量通常 30-60；
- `file_id` 优先且是主键；`source` 只给 dual-mcp / mempalace 兼容兜底（命中率低于 `file_id`）；
- 不带 `requested_version`：请求相关判定在本地做；
- `include_archived=true` 仅管理员审计用。

### 5.3 响应（单文档事实）

```json
{
  "files": [
    {
      "file_id": "d3c1f0a2-8b7e-4a39-9f10-2e1d6c3b7a90",
      "source": "kb/9f0e3467/d3c1f0a2/需求文档v3.xlsx",
      "file_name": "需求文档v3.xlsx",
      "found": true,

      "acl_allow": true,
      "acl_deny_reason": null,

      "release_status": "PUBLISHED",
      "gray_visible": true,
      "qa_visible": true,

      "version_label": "v1.2",
      "tags": ["GPIO", "UART"],
      "category": "product_manual",
      "sensitivity": "INTERNAL"
    }
  ],
  "scope_epoch": 42
}
```

| 字段 | 含义 |
|------|------|
| `found` | 后端是否认识该 `file_id`；`false` → fail-closed |
| `acl_allow` | ACL 是否允许（DENY 优先，后端内部算完） |
| `release_status` | `DRAFT / REVIEWING / GRAY / PUBLISHED / ARCHIVED / DEPRECATED`；**仅用于日志与审计** |
| `gray_visible` | 灰度白名单是否命中；**仅用于日志** |
| `qa_visible` | **唯一权威判定字段**：`acl_allow && 发布状态可见 && 灰度命中`。本服务不重复解释状态 |
| `version_label` | 文档自身版本标签，用于显式 `version` 筛选与展示 |
| `tags` / `category` / `sensitivity` | 软过滤与展示；`sensitivity` 不做本服务权限判定 |

**为什么这些字段与请求无关**：全部只依赖 `(user, kb, file_id)`，与 `requested_version` 无关，因此缓存可按文档复用。

**为什么没有再返回"可见版本列表"**：没有版本聚合，每个 `file_id` 就是一个独立版本；列表没有语义。

### 5.4 本地决策

```python
def decide_chunk_visibility(chunk_meta, facts, opts) -> tuple[bool, str | None]:
    """Stage 2：chunk 级判定，纯本地。"""
    if facts is None or not facts.found:
        return (False, 'file_unknown') if opts.hard_enforced else (True, None)

    if not facts.acl_allow:
        return False, 'acl_deny'

    if opts.version_scope != 'all':
        if not facts.qa_visible:
            return False, 'not_qa_visible'
    else:
        return True, None            # 审计：ACL 通过即放行，跳过发布状态

    if opts.requested_version:
        a = norm_label(chunk_meta.get('file_version_label'))
        b = norm_label(facts.version_label)
        if a is None or a != b:
            return False, 'version_not_visible'
        if norm_label(opts.requested_version) != b:
            return False, 'version_not_visible'

    return True, None
```

要点：

- `qa_visible=false` 是**正常业务结果**，不告警；
- chunk 缺 `file_version_label` 但请求了显式版本 → `version_not_visible`；
- chunk 的 `file_id` 必须与 facts 对应（由 `file_key` 保证）；
- 不再有 `default_version_*`、`visible_versions`、`version_label_missing` 等分支。

### 5.5 调用时机

| 阶段 | 是否调用 | 说明 |
|------|---------|------|
| 召回前 | ❌（DENY-list 下推例外） | 拿不到候选 |
| **Stage 1：召回后 / RRF 前** | ✅ 必调 | 每 KB 一次 |
| Stage 2 / Reranker 后 | ❌ | 用 Stage 1 的 facts 本地复核 |

参数：

- 单次最多 500 个文档，超过分批 + 并发 2-3 路；
- 超时 `LABEL_QUERY_TIMEOUT_MS`（默认 400ms），重试 1 次；
- 独立信号量 `LABEL_QUERY_CONCURRENCY`（默认 32），不与 `_RETRIEVE_SEMAPHORE` 混用；
- 单请求内每 KB 只调一次（扩容重查除外）。

### 5.6 缓存

| 缓存 | Key | TTL | 失效 |
|------|-----|-----|------|
| 文档级事实 | `(user_id, kb_name, file_id, include_archived)` | 30-60s | `scope_epoch` 变化 / 权限灰度事件 / 新文档发布 |
| DENY 文档集合 | `(user_id, kb_name)` | 300s | 同上 |

- 单飞合并同 key 并发请求；
- 只缓存**事实**，不缓存检索结果；
- 权限/灰度变更 → 后端递增 `scope_epoch` 并推失效事件。

### 5.7 fail-closed

| 场景 | 行为 |
|------|------|
| 接口超时 / 5xx | `LABEL_QUERY_FAIL_MODE`：`closed`（默认）丢弃本轮候选；`open_with_alert`（仅非敏感 KB）保留 + 告警 |
| `found=false` | 丢弃该文档所有 chunk + 告警（通常是消息缺 `documentId` 或存量未回填） |
| `qa_visible=false` | 丢弃，不告警 |
| chunk `file_id` 与 facts 不一致 | 丢弃 + 告警 |
| 请求显式版本但 chunk 无 label | 丢弃 |
| 软过滤失败 | 忽略软过滤，保留硬过滤 |
| 整体接口失败致候选全空 | 返回空答案 + `label_query_failed`，**不回退未过滤检索** |

### 5.8 读取路径覆盖

前端不直调本服务（chat 与文档管理都经后端代理）。

| 路径 | 处理 |
|------|------|
| `/chat/multi_knowledge_base_chat` | ✅ 本方案核心 |
| `/search_docs` | ✅ 若对外：召回 → Stage 1 → 返回；否则限制内部调用 |
| `list_docs` / `get_file_detail` / `download_doc` | ✅ 对外则只返回 `qa_visible` 文档 |

| `file_chat`（临时文件） / 联网搜索 | 不涉及 |

### 5.9 信任边界：区分"用户鉴权"与"服务身份"

| 问题 | 谁负责 | 本服务做什么 |
|------|--------|-------------|
| 用户是谁、能否看该文档 | **后端** | 只消费 `qa_visible`，不实现 RBAC |
| **谁可以调用本服务** | **本服务** | 校验调用方是后端，拒绝其他来源 |

为什么内网仍需这一层：

- K8s 默认同集群 Pod 互通，ClusterIP 可被任意 Pod 访问；`port-forward` 或误暴露 Ingress 会直接绕过后端鉴权；
- 本服务目前完全无凭证校验 → 任何能连上它的人都能伪造 `user_id` 读全部文档（信任传递，不是重复鉴权）。

P1 最小要求：

| 方案 | 阶段 | 说明 |
|------|------|------|
| `X-Internal-Token`（K8s Secret 注入） | **P1 必做** | 后端代理注入；中间件校验；失败 401 |
| `NetworkPolicy` 限定来源 | **P1 必做** | 只允许 backend Pod 访问 |
| mTLS | P2/P3 | 替代静态 token |
| 响应 HMAC 签名 | P3 | 防篡改（多服务共享缓存时才需要） |

### 6.3 Stage 1：文件级授权过滤

```python
# server/chat/pipeline/post_filter.py

@dataclass(frozen=True)
class FileFacts:
    file_id: str
    source: str
    found: bool
    acl_allow: bool
    qa_visible: bool
    release_status: str | None
    version_label: str | None
    tags: list[str]
    category: str | None


def file_key(meta: dict, kb_name: str) -> str:
    return f"{kb_name}::{meta.get('file_id') or to_source_key(meta, kb_name)}"


def _soft_tags_match(need, have, mode) -> bool:
    if not need:
        return True
    if not have:
        return True                    # soft_miss：放行并计数
    n = {norm_label(t) for t in need}
    h = {norm_label(t) for t in have}
    return n <= h if mode == "and" else bool(n & h)


def stage1_filter_by_file(docs, facts, opts, kb_name):
    out = []
    for d in docs:
        f = facts.get(file_key(d.metadata, kb_name))
        if f is None or not f.found:
            if opts.hard_enforced:
                continue
            out.append(d)
            continue
        if not f.acl_allow:
            continue
        if opts.version_scope != 'all' and not f.qa_visible:
            continue
        if opts.version_scope != 'all' and opts.requested_version:
            if norm_label(opts.requested_version) != norm_label(f.version_label):
                continue
        if not _soft_tags_match(opts.soft_tags, f.tags, opts.tag_match):
            continue
        if opts.soft_categories and f.category and f.category not in opts.soft_categories:
            continue
        out.append(d)
    return out
```

## 7. 灰度发布过滤（P2）

### 7.1 状态模型与唯一强制前提

灰度是**文档**属性，只存在于后端：

```sql
release_status VARCHAR(16) DEFAULT 'PUBLISHED'   -- DRAFT/REVIEWING/GRAY/PUBLISHED/ARCHIVED/DEPRECATED
gray_scope     JSON DEFAULT '{}'                  -- {"user_ids": [...], "roles": [...], "depts": [...]}
published_at   DATETIME NULL
```

**唯一强制前提（必须由后端保证）**：

> 同一 `(kb, file_name)` 发布新版本时，后端必须把旧版本文档置 `DEPRECATED`（或 `ARCHIVED`）。

原因：本服务**没有版本聚合关系**，无法判断同名文档哪个是最新。若新旧都保持 `PUBLISHED`，两者会同时被召回，答案里出现互相矛盾的版本内容，且 RRF 会任意排序。

本服务能做的是**监控而非纠正**：

```yaml
SAME_NAME_MULTI_VISIBLE_WARN: true     # 发现同名多文档同时 qa_visible 时告警
```

检测方式：Stage 1 的 facts 里按 `(kb, file_name)` 分组，若同一 `file_name` 有 >1 个 `qa_visible=true` → 打点 `duplicate_published_name`（每 KB 每分钟最多一条日志，避免刷屏），并可选择性地**只保留后端标记为默认的那条**——但后端目前不返回该信息，所以默认只告警、不自动纠正。

### 7.2 可见性规则（后端计算）

| 用户 | `qa_visible` |
|------|-------------|
| 普通用户 | `PUBLISHED` 且 `acl_allow` |
| 灰度白名单 | `PUBLISHED` 或 `GRAY`，且 `acl_allow` |
| 上传者 / 审核者 | 同普通用户；预览走管理接口 |
| 管理员（`version_scope=all`） | 不看发布状态，但 `acl_allow` 仍生效 |

- 灰度状态不写 chunk；转正/撤销只改后端 DB，本服务下一次请求即生效（缓存 TTL 30-60s + `scope_epoch` 事件）；
- 显式 `version` 不能绕过：`qa_visible=false` 的文档在 Stage 1 就被丢弃。

### 7.3 转正 / 回滚 / 撤销

| 操作 | 后端动作 | 本服务动作 |
|------|---------|-----------|
| 转正 | 新文档 `GRAY → PUBLISHED`；旧文档 `PUBLISHED → DEPRECATED` | 无（下次查询自动生效） |
| 回滚 | 旧文档 `DEPRECATED → PUBLISHED`；当前文档 `→ DEPRECATED` | 无 |
| 撤销灰度 | 文档 `GRAY → DRAFT / ARCHIVED` | 无 |
| 归档 | 文档 `→ ARCHIVED` | 按 `documentId` 清理该文档（§4.6） |

三种状态操作都要求后端递增 `scope_epoch` 并推失效事件，否则本服务缓存会滞后最多 TTL。

### 7.4 执行与审计

- 唯一判定入口是 `qa_visible`，本服务不解释状态机；
- `kb_stats` 增加：`version_scope`、`qa_visible_count`、`post_filter_dropped` 原因分布、`duplicate_published_name`；
- 审计日志：`user_id / kb / query / 命中 file_id 列表 / scope_epoch`；
- 灰度白名单变更 → `scope_epoch` 递增 → 缓存失效。

### 7.5 边界

- 灰度不是权限：无权限用户即使命中白名单，`acl_allow=false` 仍丢弃；
- 灰度不改变 chunk 内容、不重建向量；
- 灰度状态不写 chunk。

### 7.6 记忆路与会话残留

**A. 记忆路（mempalace）**

mempalace 存历史内容，权限回收 / 灰度撤销后旧内容仍可能被召回。当前实现只在有 label 时写 `file_version_label`，**没有 `file_id`**，Stage 1 只能按 `(source, label)` 查接口 → 命中率取决于写入质量。

| 策略 | 说明 | 阶段 |
|------|------|------|
| S1 按 `(source, label)` 映射 + fail-closed | 映射不到的直接丢弃 | **P1 必做** |
| S2 写入带 `file_id` + KB 相对 `source` | 从根上可判定 | P2 推动 mempalace 改造 |
| S3 权限/灰度变更事件触发按 `source` 清理 | 真正的时效保证 | P3 |

S2/S3 落地前必须**明确接受风险**：记忆路对刚被回收权限的文件存在最长 `MEMORY_TTL` 的窗口。

**B. 会话历史**

多轮 `history` 可能包含用户此前看到、现已受限的内容，`_phase_generate` 直接注入无二次校验。

- 权限体系上线时，对"权限变更后的新会话"强制不带跨会话 history（或只带摘要）；
- 或在 history 组装前给每条引用打 `file_id` 标记（成本高，P4 再评估）。

> 两条都要写进 §14.6 已知风险。

## 8. 账号权限过滤（P3）

### 8.1 权限模型（后端实现）

本服务只消费 `acl_allow` / `acl_deny_reason`，不实现规则引擎：

- **文档级**：用户/角色/部门 → 文档 allow/deny；
- **DENY 优先**：任一 DENY 命中即拒绝；
- **敏感级**：`sensitivity` 来自后端预定义字典（普通/秘密/机密…），后端按"用户 clearance ≥ 文档密级"的数值比较解析出 `acl_allow`；本服务不做密级比较；
- 版本级单独授权**不需要**：每个版本已是独立文档，直接按 `file_id` 授权即可（比"版本级覆盖"更简单）。

### 8.2 PDP / PEP 分工

| 方案 | 说明 | 推荐 |
|------|------|------|
| 后端返回 `acl_allow` / `qa_visible` | 逐请求计算 | ✅ 默认 |
| 本服务读 ACL 投影表 | 上游同步只读投影 | 仅在后端无法逐请求计算时 |
| 本服务实现 ABAC | 解析 condition_expr | ❌ 不做 |

### 8.3 三路执行

- 三路统一在 Stage 1 做文件级 ACL 过滤，Stage 2 复核；
- `acl_allow=false` 一律丢弃；
- 旁路接口走同一判定（§5.8）。

### 8.4 DENY-list 下推（可选）

`acl_allow` 是布尔值，但"用户明确 DENY 的文档集合"通常很小且稳定，可缓存 5-10 分钟并下推 Milvus：

```python
deny_sources = await label_client.get_denied_files(user_id, kb_name)   # 缓存 300s
filter_expr += f' and (source not in [{", ".join(esc(s) for s in deny_sources)}])'
```

收益：召回前剪掉"绝不可见"的文档，降低放大系数与接口入参规模。

前置条件：后端提供 `GET /labels/denied_files`，且集合 ≤500 才启用。

### 8.5 判定顺序

```
ACL（acl_allow）→ 发布状态/灰度（qa_visible）→ 显式 version label → 软过滤
```

- ACL 拒绝 → 该文档所有 chunk 丢弃；
- ACL 通过但 `qa_visible=false` → 丢弃（正常业务结果）；
- 显式 `version` 与文档 label 不符 → 丢弃。

### 8.6 安全前提

1. **P1 加服务身份校验**：`X-Internal-Token` + `NetworkPolicy`；这不是用户级鉴权（§5.9）；
2. **`user_id` 由后端注入**：业务鉴权在后端，本服务只在服务身份校验通过后信任它；
3. **不允许** `LABEL_QUERY_FAIL_MODE=open` 时缺接口走全量；
4. 短期无法做服务身份校验时，ACL/灰度只能定位为"防误泄露"，不能宣称安全隔离。

### 8.7 审计

- 记录 `scope_epoch`、可见文档数、命中 `file_id` 列表、`acl_deny_reason` 命中数、丢弃原因分布；
- 对"显式请求受限版本""候选被 Stage 1/2 丢弃"单独告警；
- 不记录完整文档内容。

> 软过滤最后做：它不是权限控制，先把硬过滤做扎实。

### 9.1 意图链路缺口

- `tech_keyword` 分支命中 `TECH_KEYWORDS` 就跳过 LLM route（[L468-480](file:///d:/Code/haisi/haisi_rag_models_server/server/chat/multi_knowledge_base_chat.py#L468-L480)）；
- 技术问题通常含"配置/启动/驱动/芯片"，大多数请求不走 LLM route；
- 所以只在 `route_chat` prompt 加 `intent_code` 覆盖面极小。

### 9.2 混合策略

| 分支 | 意图来源 |
|------|---------|
| greeting / chitchat | 无（不检索） |
| version_diff | 规则：`version_compare` |
| tech_keyword | 规则：`INTENT_RULES`（LAC + query 子串） |
| llm_route | 规则优先；LLM 可选输出 `intent_code + confidence` |

```yaml
INTENT_RULES:
  fault_diagnosis:
    keywords: ["报错", "崩溃", "失败", "异常", "排查", "黑屏", "死机", "无法启动"]
  product_operation:
    keywords: ["怎么配置", "如何设置", "安装", "拆机", "烧录", "编译"]
  contract_query:
    keywords: ["合同", "报价", "采购", "商务"]
  version_compare:
    keywords: ["差异", "对比", "区别", "变更"]
```

### 9.3 意图 → 分类映射

```yaml
INTENT_CATEGORY_MAPPING:
  product_operation:
    allow_categories: ["product_manual", "faq"]
  fault_diagnosis:
    allow_categories: ["faq", "product_manual", "ops_plan"]
  contract_query:
    allow_categories: ["contract"]
  version_compare:
    allow_categories: ["product_manual", "faq"]
  general:
    allow_categories: []

INTENT_CONFIDENCE_THRESHOLD: 0.8
```

`category` 来自接口（§5.3），字典由管理员在后台维护、前端上传页选定；本服务不维护分类表；chunk 可带副本（不可变），但软过滤以接口为准。

### 9.4 软过滤降级

见 §6.6：阈值 `max(2, ceil(top_k*0.5))`（`and` 模式 `×0.8`）；只去软不去硬；不重新调接口；降级计入 `kb_stats`。

### 9.5 不建议的做法

- ❌ 让 LLM 自由输出 category 并拼 Milvus filter；
- ❌ 把软过滤当权限控制；
- ❌ 把 `release_status / acl / gray_scope` 写进 chunk；
- ❌ 只给 Milvus 路加过滤；
- ❌ 用 `doc_type` 做分类过滤（它是检索路 marker）；
- ❌ 在 RAG 侧重复解释 `release_status`。

### 9.6 多标签匹配：AND / OR

多标签语义取决于用户场景，不写死：

| 来源 | 优先级 | 说明 |
|------|--------|------|
| 请求参数 `tag_match=and\|or` | 最高 | 前端高级筛选/调用方指定 |
| 意图规则映射 | 中 | 如 `fault_diagnosis` 默认 `or`、`precise_lookup` 用 `and` |
| 默认 | 最低 | **`or`**（召回优先，后面还有硬过滤与 Reranker 收敛） |

```yaml
TAG_MATCH_DEFAULT: or
INTENT_TAG_MATCH:
  fault_diagnosis: or
  product_operation: or
  precise_lookup: and
```

要点：

- 归一化后比较（大小写/空白无关），回写与审计用原值；
- `and` 语义是"文档带齐请求的全部标签"，**不是**"chunk 文本同时包含这些词"；
- 文件无 tags 时 fail-open 放行并记 `soft_miss`；
- `and` 召回率低，必须允许 §6.6 的去软重试。

## 12. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| **后端未把旧版本置 `DEPRECATED`** | 新旧版本同时被召回，答案自相矛盾 | §7.1 作为灰度阶段准入条件；本服务用 `duplicate_published_name` 告警；不自动纠正 |
| **Kafka 消息缺 `documentId` / label** | 接口全部 `found=false` → 全量丢弃 | 消费侧强校验（§4.8.2），缺失即 `PROCESSING_FAILED`；存量先回填 |
| **至少一次投递导致重复入库** | 同文档重复 chunk、chunk 数虚增 | 幂等键 `file_id` + `content_sha256`；`RETRY_PROCESS` 先删后建 |
| **归档/删除仍按 `file_name`** | 同名其它版本被误删 | §4.6 必须按 `file_id`；新增 `list_doc_ids_by_file_id`；专项验收 |
| **`add_file_to_db` 按文件名 upsert** | 同名新版覆盖旧文档行 | P0 改按 `id`；迁移脚本校验行数 |
| **`DOCUMENT_ARCHIVED` 无回调** | 归档失败对后端完全静默 | 见 `DOCUMENT_ARCHIVED回调方案说明.md`：改 no-op（推荐）或纳入回调 |
| **后端接口未就绪** | P1 无法落地 | 用 mock（`qa_visible=true`）先跑通链路，接口上线切真 |
| **接口延迟过高** | chat 端到端劣化 | 文档级入参 + 30-60s 缓存 + 单飞 + 400ms 超时；P95 < 200ms |
| **接口失败导致空答案** | 体验下降 | `LABEL_QUERY_FAIL_MODE`：敏感 KB `closed`，非敏感 `open_with_alert` |
| **存量 chunk 缺 `file_id`** | 无法判定归属，可能泄漏 | 回填率 100% 才开硬过滤；兼容期按单文档模式 |
| 放大召回拖垮 Milvus | 检索延迟劣化 | factor 自适应（3-20）+ `RERANK_INPUT_MAX` + DENY-list 下推 |
| 放大召回抬高 Reranker 成本 | 精排 P95 上升 | `RERANK_INPUT_MAX=60`；必要时两段式精排 |
| `code_list` 保底绕过过滤 | **权限泄漏** | 改用已过滤 `code_pool`（§6.7）+ 单测覆盖 |
| RRF 内容哈希跨文档合并 | `file_id` 丢失，判定不到归属 | `_rrf_key` 带 `file_id` + metadata 归并（§6.4） |
| 记忆路内容残留 | 权限回收后仍可召回 | S1 fail-closed → S2 写 `file_id` → S3 事件清理；§14.6 记为已知风险 |
| 会话历史残留 | 受限内容出现在历史 | 权限变更后强制新会话不带历史；P4 再评估 |
| 缓存未及时失效 | 旧权限继续可见 | 短 TTL + `scope_epoch` 事件失效 |
| **本服务无服务身份校验** | 伪造 `user_id` → 越权读全部文档 | P1 `X-Internal-Token` + `NetworkPolicy`（§5.9） |
| `cleanup` 只删 blob | 存储膨胀 + 旧内容可召回 | 按 `file_id` 清理三路 + 孤儿检测 |
| 旁路接口未接入 | 权限洞 | §5.8 覆盖矩阵逐项验收 |
| dual-mcp / mempalace 无 `file_id` | 只能按 `source`，命中率低 | 推动改造；未支持前 fail-closed + 已知风险 |
| 多环境配置漂移 | 生产与测试不一致 | §10 配置同步 + 启动校验 |
| `top_k > RERANK_INPUT_MAX` | 截断过度 | 取 `max(60, top_k)` |

## 13. 不做事项（边界）

- 不在召回阶段做细粒度 ACL/发布状态过滤（仅 label 粗过滤与 DENY-list 例外）；
- **不引入 UUID `version_id`**：`file_id` 即身份；
- **不引入"逻辑文件/文件组"聚合**，不做 `visible_versions[]`、不做默认版本判定；
- 不用 `version_label` 做身份判定、排序或路径拼接；
- 不做 `register_file` / `register_version` 握手：`file_id` 由后端生成；
- 不在本服务实现 RBAC/ABAC；
- 不把 `release_status / gray_scope / acl` 写进 chunk；
- 不在 RAG 侧重复解释 `release_status`（只信 `qa_visible`）；
- 不允许软过滤降级时去掉硬过滤；
- 不允许 `LABEL_QUERY_FAIL_MODE=open` 时缺接口走全量；
- 不按 `file_name` 执行任何删除、逻辑删除或 upsert；
- 不在没有 `file_id` 的情况下兜底自增 ID 入库；
- 不把"内网 + 后端已鉴权"当作本服务的安全边界；
- 不把记忆路 / 会话路当作具备实时权限能力。

## 14. 验收标准

### 14.1 功能

- [ ] 默认检索只返回 `qa_visible=true` 的文档；
- [ ] `version=v1.2` 只返回该标签且可见的文档；不可见时返回空；
- [ ] 同名不同版本的文档互不覆盖、互不误删；
- [ ] 灰度用户能检索灰度文档，非灰度用户检索已发布文档；
- [ ] 删除某文档后三路均无其内容，同名其它文档不受影响；
- [ ] 软过滤生效且可降级（不重调接口、不重召回）；
- [ ] `tag_match=or` 与 `and` 均按预期收窄。

### 14.2 权限与安全

- [ ] 无权限文档不出现在三路任何最终结果；
- [ ] 最终 LLM `context` 不含受限 chunk；
- [ ] **代码路保底不会引入未过滤块**（构造受限 code 块验证）；

## 15. 评测与上线

### 15.1 指标

| 指标 | 定义 | 目标 |
|------|------|------|
| `Recall@50` | 过滤前召回（对照标注） | 不低于改造前基线 |
| `Filtered-Recall@k` | 过滤后仍命中正确文档的比例 | ≥ 基线 × 0.95 |
| `nDCG@10` | 精排质量 | 不低于改造前 |
| **`Leakage Rate`** | 受限 chunk 进入最终 context 的比例 | **必须 = 0** |
| `Empty Answer Rate` | 因过滤导致空答案的比例 | < 2% |
| `Post-Filter Drop Rate` | Stage 1/2 丢弃比例（按原因分桶） | 监控 |
| `Duplicate Published Name` | 同名多文档同时可见的次数 | 监控，应趋近 0 |
| `P95 端到端` | 召回 + 过滤 + 精排 + 生成 | < 改造前 + 150ms |

### 15.2 Golden Set

- 50-100 条 query，覆盖：单文档问答、跨文档、版本对比、灰度专查、无权限、软过滤；
- 每条标注：期望 `file_id` / `version_label` / 是否应返回空 / 期望答案要点；
- 标注"用户 × KB × 文档可见矩阵"，用于构造灰度与 ACL 用例；
- 进 CI：跑 `Leakage Rate` + `Filtered-Recall@k`，回归失败阻断合并。

### 15.3 Shadow → Enforce

```
POST_FILTER_MODE = legacy | shadow | enforce
```

| 模式 | 行为 |
|------|------|
| `legacy` | 走现有 `cur_labels` + 客户端过滤 |
| `shadow` | 同时算旧路径与两级过滤；输出仍用旧路径，只记录差异 |
| `enforce` | 两级过滤生效 |

shadow 阶段产出差异报告：

- 少召回文档清单；
- `not_qa_visible` / `acl_deny` / `version_not_visible` / `file_unknown` 分布；
- `duplicate_published_name` 次数；
- 因过滤导致的空答案比例；
- 接口延迟与缓存命中率。

差异可解释后才进 `enforce`；首周保留一键回退开关。

### 15.4 观测

- `kb_stats`：`post_filter_mode`、`stage1_dropped`、`stage2_dropped`、`pass_rate`、`factor_used`、`label_cache_hit`、`rerank_input_size`、`scope_epoch`、`tag_match_mode`、`soft_miss_count`、`duplicate_published_name`；
- 耗时拆解：新增 `stage1_label_query` / `stage2_verify`；
- 告警：`Leakage Rate > 0`、接口超时率 > 1%、`found=false` 比例 > 1%、`duplicate_published_name > 0`。

### 16.1 已确认

| # | 决策点 | 结论 |
|---|--------|------|
| 1 | UUID `version_id` | **不存在** |
| 2 | `file_id` 来源 | 后端自动生成（Kafka `documentId`）；本服务 `knowledge_file.id` 直接采用 |
| 3 | 多版本关系 | **完全独立**：每个版本一条文档记录、独立 `documentId`、独立 SFS 目录；**无聚合关系** |
| 4 | 上传新版本 | 后端**新建**文档记录 + 新目录，不复用原 `documentId` |
| 5 | `version_label` 来源 | 前端上传页下拉框；字典由知识库运维管理员维护、可编辑 |

| 10 | tags 检索语义 | AND / OR 都需要，按场景决定；默认 `or` |
| 11 | 入库链路 | `前端 → 后端 → Kafka(kb-document-processing) → 本服务`；本服务无上传接口 |
| 12 | 删除/归档链路 | `前端 → 后端 → Kafka → 本服务`；`documentId` 精确定位 |
| 13 | chat 调用链 | 也走 `前端 → 后端 → 模型端`；`user_id` 由后端注入 |
| 14 | 模型端鉴权 | 不做用户级 RBAC；需要**服务身份校验**（token + NetworkPolicy） |
