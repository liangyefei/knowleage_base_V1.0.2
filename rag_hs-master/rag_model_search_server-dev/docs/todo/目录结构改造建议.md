## 二、公司规范对照

公司规范：

```
.
├── bin            # 可执行/入口
├── build          # 构建产物
├── libray         # 内部共享库
├── opensource     # 开源组件
├── script         # 脚本
├── src            # 源码
│   └── moduleN
├── test           # 测试（mst/sit/ut）
└── tools          # 工具
```

> **关于 `bin/build/libray`：** 这三个目录是 C/C++ 项目的惯例（二进制入口、编译产物、链接库）。本项目是 Python 算法端项目，不编译二进制、不产 `.so`/`.a`、入口脚本即 `.py` 文件，**不适用这三个目录**。Python 项目的等价处置：
> - 入口脚本（`startup*.py`/`webui.py`/`init_database.py`）保留根目录（Python 社区惯例，如 FastAPI/Django/Streamlit 项目）
> - 构建产物由 `pip wheel`/`python -m build` 输出到 `dist/`（gitignore），无需 `build/` 目录
> - 跨模块公共代码用 `src/common/` 或 `src/core/` 等价，无需 `libray/`
>
> **关于 `opensource` 命名：** 公司规范写作 `opensource`，但 Python 包名/目录名不允许连字符，业界惯例用下划线 `open_source/`（与 `code_base`、`web_ui` 等一致），更可读且可作包名 import。本建议采用 `open_source/`。

| 公司规范目录 | 当前状态 | 改造动作 |

### 3.3 依赖规则（重构的灵魂）

```
services/ ──▶ core/ ──▶ common/            单向依赖，禁止反向
services/ ──▶ services/                    仅允许调对方 service.py，router 禁止互引
core/ 内部：retrieval 可用 clients、db，反之禁止
config_parser/ 与 common/ 同层：任何模块均可引用，它不引用任何业务模块
```

现有耦合的解法：

| 现有耦合（实测） | 新架构解法 |
|---|---|
| `chat/file_chat.py` → `knowledge_base.kb_cache`、`kb_service.base` | 双方都改 → `src.core.retrieval` |
| `comm/*` → `kb_doc_api`、`kb_api`（层次颠倒：消息服务调 API 层） | kb 业务逻辑抽到 `src/services/knowledge_base/service.py`，comm 调 service |
| `server.utils` 被 18 处引用 | 进 `src/common/utils.py`，后续可按 fs/http/text 细拆 |
| workers 只依赖配置（9 处 `from configs`） | 平移进 `src/core/clients/`，import 改为 `from src.config_parser` |

## 四、影响分析（关键风险点）

### 4.1 import 路径（最大风险）

全仓 **218 处 / 100 个 .py 文件** 使用顶层导入：

```python
from configs import ...        # 71 处（配置加载器）
from server.xxx import ...     # 111 处（核心服务）
from document_loaders import ...  # 含在 218 内
from text_splitter import ...
from chains import ...
```

三大改名波及面：

| 改名 | 波及范围 | 改法 |
|---|---|---|
| `server/` → `src/` | **111 个文件**含 `from server.` / `import server` | 全局 sed：`from server.` → `from src.`；含 tests/、webui、startup.py |
| `configs/`(代码) → `src/config_parser/` | **71 个文件**含 `from configs import` | 全局 sed：`from configs import` → `from src.config_parser import` |
| `params/`(YAML) → `configs/` | 5 个 loader 硬编码 `params/` 路径 + llm_api/vlm_api/lac_service/milvus_kb 等 | loader 内路径常量改为 `configs/`；支持 `RAG_CONFIG_DIR` 环境变量覆盖 |

> ⚠️ **改名顺序很重要**：必须先做 `configs/`→`src/config_parser/`，再做 `params/`→`configs/`，否则中间态会出现"configs 既是代码又是 YAML"的歧义。建议同一个 PR 内用 git mv 一次完成三步。

**两种 import 处置方案：**

| 方案 | 做法 | 工作量 | 风险 |
|---|---|---|---|
| **A（推荐，过渡）** | sed 重写 import 为 `from src.xxx`；在入口（startup*.py、webui.py、init_database.py、tests/conftest.py）插入 `sys.path.insert(0, src_dir)`；`pytest.ini` 加 `pythonpath = src` | 中 | 低 |
| **B（推荐，目标）** | 新增 `pyproject.toml`，`[tool.setuptools.packages.find] where=["src"]`，`pip install -e .` 后包名不变 | 中（加配置 + CI 装包） | 低，最干净 |

> 注：`src` 作为可 import 的包名虽 unconventional（社区惯例 src/ 是不入包的容器层），但作为单应用服务（非 pip 库）完全可行。唯一注意点：项目根必须在 `sys.path`（startup.py 从根启动天然满足；pytest 靠 pytest.ini 的 rootdir）。

### 4.2 config_parser 内部相对路径

[configs/basic_loader.py](file:///d:/Code/haisi/haisi_rag_models_server/configs/basic_loader.py#L23-L27) 通过文件相对位置定位 `params/`：

```python
config_path = os.path.join(
    os.path.dirname(os.path.dirname(os.path.abspath(__file__))),  # 当前=项目根
    "params", "basic_config.yaml"
)
```

迁移到 `src/config_parser/` 后，`dirname(dirname(__file__))` 变为 `src/`，`params/`（→`configs/`）找不到。

**改造：** 改为以项目根定位（向上两级），或读环境变量 `RAG_CONFIG_DIR`：

```python
ROOT = os.path.dirname(os.path.dirname(os.path.dirname(os.path.abspath(__file__))))  # src/config_parser/x.py -> 项目根
config_path = os.path.join(os.environ.get("RAG_CONFIG_DIR", os.path.join(ROOT, "configs")), "basic_config.yaml")
```
