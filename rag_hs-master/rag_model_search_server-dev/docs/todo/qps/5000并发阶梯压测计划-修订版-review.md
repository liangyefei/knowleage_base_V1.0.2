## 一、总体评价

**做得好的部分(保留)**:

- 阶梯递进(200→1000→3000→5000)+ 每周主压/复测/回归三轮取中位,方差控制到位
- 止涨线 + 降级预案 + 五件套留存,风险控制框架完整
- T0 准入一次性锁定 LLM 终档,理解阿里云提额/独占实例采购周期约 2 周
- SLO 有历史基线支撑(10-13 健康期中位 3.2s / P95 5.5s → SLO2 5s/10s)
- 容量外推公式可追溯:QA 3.2 核/180 并发(10-14 实测)、DB 并发×1.2、LLM RPM 并发×12

**核心问题(必须先解决)**:

1. **战略层**:5000 并发的业务必要性缺乏依据,行业头部企业 RAG 实测 100~500 并发即为主流水平
2. **供给层**:deepseek-v4-pro 公共 API 默认限流与需求存在数量级缺口,唯一可行路径 DTU 月费预估 50~100 万+
3. **口径层**:首包即断压测口径下,生产真实在途路数是压测验证值的 6~12 倍,压测通过 ≠ 生产可用

## 二、优化点清单(按优先级)

### P0 · 战略级(不解决则整个计划失去意义)

#### P0-1 目标并发的业务必要性缺乏依据

5000 并发按行业同时在线率(5~10%)反推 = **5~10 万 DAU**,属全国级公众问答平台规模(政务热线 / 央企全员系统)。Excel 未提供任何业务侧证据。

**行业对照**:

| 案例 | 规模 | 备注 |
|---|---|---|
| 德国引擎制造商 5000 员工 RAG | 5000 员工,实际并发 250~500 | Azure OpenAI |
| Intel Xeon 单机 RAG | 100+ 并发无性能下降 | 48 核单机,125 tok/s |
| 腾讯云企业 RAG 基准 | 首 token 8-12s | 未披露并发,典型 10~100 QPS |

**修订建议**:要求业务方提供 DAU / 峰值场景证据(全员培训?政策发布?突发事件?)。无证据则目标降至 1000~2000。若是"3 年规划容量"前置,应在 W2 前由业务负责人书面确认。

#### P0-2 阿里云 LLM 配额硬缺口(数量级)

Excel 05 表已正确识别风险,但未对齐真实数字:

| 指标 | 公共 API 默认(华北2) | W4 需求 | 缺口 |
|---|---|---|---|
| RPM | 15,000 | 60,000 | **4 倍** |
| TPM | 1,200,000(120 万) | 150,000,000(1.5 亿) | **125 倍** |

**关键事实**(阿里云百炼官方文档):

- 限流按主账号维度计算,所有 RAM 子账号/业务空间/API Key 合并
- 动态限流按月消费分等级:等级 1(≤10 万)/ 等级 2(10~100 万)/ 等级 3(≥100 万),高 TPM 档位需高等级
- **DTU(Dedicated Throughput Unit,独占吞吐)**:按 Input/Output TPM 售卖、独占 GPU 资源,是唯一能满足 1.5 亿 TPM 的形态
- DTU 1.5 亿 TPM 档位月费预估 **50~100 万+**(需工单获取正式报价)
- DTU/提额采购周期约 2 周,T0 锁定正确

**修订建议**:
1. T0 第 1 天工单确认三件事:① deepseek-v4-pro 是否支持 DTU ② 1.5 亿 TPM 档位正式报价 ③ 当前账号等级可解锁的档位上限
2. Excel 05 表"部署形态/提额路径"行补上 DTU 正式报价与账号等级现状,替代当前的定性描述
3. 若 DTU 报价超预算,立即启动替代方案评估(见 3.3)

#### P0-3 首包即断口径导致容量结论失真 6~12 倍

| 口径 | output tokens | 单次时长 | 5000 用户在途路数 |
|---|---|---|---|
| 首包即断(压测) | ~15 | ~5s | 5,000 路 |
| 完整生成(生产) | 500~800 | 30~60s | **30,000~60,000 路** |

T0 ⑥ 要求确认"客户端 SSE abort 后推理槽位是否即时释放",但商业 API 通常**不保证**该行为。若不即时释放:TPM 需求从 1.5 亿放大到 9~18 亿,DTU 月费再上翻数倍。Excel 只写"按完整生成时长重算",**没有给出重算后的具体数值与对应报价**,等于 Plan B 空缺。

**修订建议**:
1. T0 ⑥ 拆成两个动作:① 向阿里云书面确认 abort 释放行为 ② 无论确认结果,先按"完整生成口径"算一版配额需求与报价(1.5 亿 vs 9~18 亿两档并列)
2. W2 起主压轮加 1 轮"完整生成口径"抽样(500 并发 × output 500 tokens,10min),验证真实在途路数
3. SLO2 在完整生成口径下重验:TTFT 中位 ≤5s 是否仍成立(输出变长不影响首包,但 TPM 消耗模型完全不同)

### P1 · 方案级(影响成本与可行性)

#### P1-1 平台服务配置无锚点外推,缺独立摸底轮

03 表自认"平台从未在 200 并发以上实测且为实锤 502 瓶颈,本列为无锚点外推"。W2 直接跳 4C×4(16C)、W4 跳 4C×12(48C),依据仅是"login 13.6s→≤3s 约 4.5C 起 + 余量"。10-13/14/16 三次 502 风暴签名一致(readiness 探针与业务 DB 池强绑定),改造是否闭环未单独验证。

**修订建议**:W2 R1 前加独立轮次"平台直压摸底"(脱离 LLM,login + 建会话 + chat 打桩回环),产出单 Pod 极限并发,再定副本数。当前 02 表把它塞在 W2 R1 准入项里,若摸底失败整周延期,应前置到 T0 末或 W1 内并行。

#### P1-2 多模型分流架构方案缺失(成本杠杆最大项)

当前架构所有问答全走 deepseek-v4-pro。但本系统已有 `_phase_route` 路由能力(闲聊/技术关键词/复杂问题分支),天然支持分流:

- 简单问题(闲聊/关键词命中/FAQ,占比约 70%)→ qwen-flash 等轻量模型(公共 API RPM 15,000 级,基本免提额)
- 复杂问题(约 30%)→ deepseek-v4-pro
- 效果:deepseek 实际 RPM 从 6 万降到 1.8 万,TPM 从 1.5 亿降到 4,500 万,**DTU 月费从 50~100 万降到 15~30 万**

**修订建议**:T0 准入项增加"路由分流改造"(路由模型独立配额核对 + 分流比例统计 + 回归测试),W2 前上线。这是把 LLM 成本砍 60~70% 的最直接手段,复用现有代码,改造量小。

#### P1-3 DB 读写分离时间线后置

当前:W3 才"评估读写分离",W4 前完成 Proxy 常态化,中间仅 1 周做评估+接入+验证。max_connections ≥8,000 需参数模板修改 + 重启验证,单实例压力大。

**修订建议**:读写分离评估前移到 W2,R3 后接入读副本,W4 只做 Proxy 调优。resolveKbIds 等查询走读副本,主库压力立减。

#### P1-4 LLM 调用链路诊断日志盲区(与本项目直接相关)

10-16 的 52~57s 停滞、10-19 的 30s connect timeout,当前日志只有一行 `llm_stream_connect_timeout: 30.0s`,pool 状态/底层异常/pid 全无。Excel SLO5 要求"无日志静默 >2s"、03 表要求实时告警,但**主 LLM 调用路径(`_stream_llm_response` / `_non_stream_llm_response`)没有诊断能力**,压测时 LLM 慢/超时只能事后看 ttft_log,定位不到连接池状态。

**修订建议**:W2 前完成 LLM 调用诊断日志改造(同 embedding 已完成的模式:pid + client_id + pool_stats + underlying_exc + shield/task retrieve),并在 03 表"监控告警"行加"LLM 调用诊断日志(pending)"状态标记。

### P2 · 执行级(不阻塞,但建议修订)

#### P2-1 SLO5 表述自相矛盾

SLO5 同时含"TTFT >20s 样本占比 ≤1%"与"5000 并发下每 10s 窗口约 1 万样本,0 容忍与占比 ≤1% 互斥且几乎必挂"。R3 行已把占比改为参考,但 SLO5 本体未改。

**修订建议**:SLO5 改为"无持续停滞(连续 3 个采样周期 TTFT >20s)即止涨线停压",占比 ≤1% 降为观测参考指标。

#### P2-2 Locust worker 内存余量不足

每 worker ≤850 SSE 长连接 × ~18MB(Python + SSE 缓冲)≈ 15G,接近 8C16G 上限,FD ≥6000 已覆盖但内存无余量。

**修订建议**:W2 起加 worker 内存告警(80%);预留升 32G 或减至每 worker 700 用户(需 7 台)的备选;01 表"压测工具"行补内存监控要求。

#### P2-3 token 费用预算缺数字

全计划 ≈209 亿 tokens(首包即断口径),按 deepseek-v4-pro 粗算(input ~0.5 元/百万 + output ~2 元/百万)≈ **10.5 万元**。Excel 写了"预算单列"但没数字,老板无法批。

**修订建议**:05 表 token 行补粗估区间 10~15 万,并注明"若 W2 起加完整生成口径轮次,费用另增约 30~50%"。

#### P2-4 细节补强

- **账号 token TTL**:T0 要求 TTL ≥ 最长压测 +30min,建议补"滑动续期失败时的 fallback(重新 login 限速预热)",避免 R4 60min 长跑二次 login 洪峰
- **环境独占性**:01 表"压测窗口隔离"要求确认 113.45.181.210 独占,建议补"LLM 账号独占"——限流按主账号合并计算,若生产/其他测试共用同一阿里云账号,压测会误伤生产且污染数据
- **冷却规则**:W4 轮次间隔 15min 冷却已写明,建议 W2/W3 轮次同样显式写冷却(LLM 限流窗口分钟级滚动)
- **题目池缓存**:≥500 题防 TTFT 虚低,建议再加"题目池与知识库 chunk 无重复前缀"要求,防 context cache 命中导致 TTFT 虚低

## 三、行业解决方案建议

### 3.1 容量需求重估(先定性,再定量)

**定性**:企业内部知识库 RAG 的主流容量区间是 **100~500 并发 / 10~100 QPS**。5000 并发(≈1000 LLM QPS)是公众级平台容量,须有业务证据支撑。

**定量(两套口径并列进 Excel)**:

| 口径 | LLM QPS | RPM | TPM | 在途路数 | 适用场景 |
|---|---|---|---|---|---|
| 首包即断(现计划) | 1,000 | 6 万 | 1.5 亿 | 6,000 | 压测验证 |
| 完整生成(生产) | 1,000 | 6 万 | **9~18 亿** | 3~6 万 | 生产容量规划 |

### 3.2 阿里云供给路径(按可行性排序)

| 路径 | 能力 | 成本(月) | 采购周期 | 适配 |
|---|---|---|---|---|
| 公共 API + 提额 | RPM 1.5 万→提额(上限受账号等级约束) | 按 token 计费 | ~2 周工单 | 仅够 1000~2000 并发 |
| **DTU 独占吞吐** | 按需买 TPM,唯一能到 1.5 亿+ | 50~100 万+ | ~2 周 | 5000 并发唯一商用路径 |
| PAI-EAS 自建 | 无配额限制 | ~15 万(8 卡 H800 节点级) | 1~2 周 | 长期稳定大流量,需运维团队 |

### 3.3 三条可选路线

**路线 A · 多模型分流(强烈推荐,成本杠杆最大)**

```
用户请求 → _phase_route 路由
  ├─ 闲聊/FAQ/关键词命中(~70%)→ qwen-flash(公共 API,基本免提额)
  └─ 复杂问题(~30%)→ deepseek-v4-pro(DTU 中档即可)
```

- deepseek 负载降 70%:RPM 6 万→1.8 万,TPM 1.5 亿→4,500 万
- DTU 月费 50~100 万 → 15~30 万,**年成本从 600~1200 万降到 180~360 万**
- 复用现有 `_phase_route` 代码,改造集中在路由判定准确性 + 回归测试

**路线 B · PAI-EAS 自建推理(长期最优,短期不选)**

- deepseek-v4-pro 1.6T MoE 需 8 卡 H800 级节点,月租 ~15 万,无配额天花板
- 适合月流量稳定后的成本优化;当前压测期租用即浪费,且需自建推理运维能力
- 建议作为"5000 并发确有必要"后的 6 个月规划项

**路线 C · 分阶段验证(推荐作为主计划框架)**

| 阶段 | 目标并发 | LLM 供给 | 验证目标 | 决策点 |
|---|---|---|---|---|
| W1~W2 | 1,000 | 公共 API + 提额(免费/低成本) | 平台 502 闭环 / QA 线性外推 / DB 池 | 业务方提供 DAU 证据 |
| W3 | 2,000 | 路线 A 分流 + DTU 低档(月 5~10 万) | HPA / 读写分离 / 分流比例 | 证据成立才进 W4 |
| W4 | 5,000(视必要性) | 路线 A + DTU 高档 或 路线 B | 终极容量 | 无证据则停在 2,000 |

### 3.4 架构层配套优化(压测前完成,性价比排序)

1. **login/建会话缓存**(已在 T0 ⑥,保留)——历史 login 中位 13.6s,是 502 洪峰源头
2. **LLM 请求排队 + 熔断**:网关侧对 LLM 调用加信号量(如在途路数上限),超限快速失败返回友好提示,而不是把请求堆在连接池里等 502——这正是 10-19 生产 `PoolTimeout` 的教训
3. **embedding/检索结果缓存**:题目池压测必然命中重复 query,加 query→chunks LRU 缓存可大幅降低 embedding QPS(同时注意缓存命中会让 TTFT 虚低,压测报告需标注命中率)
4. **readiness 与业务池解耦**(已在 T0,保留)——502 风暴根因
5. **SSE abort 传导**:客户端断开时立即取消上游 LLM 请求(当前 fire-and-forget 模式下存在连接不释放风险,10-19 已实锤)——这也是 P0-3 的前提

### 3.5 推荐路线图(对 Excel 的修订版)

```
T0(10-26~10-30)
  ├─ 工单:DTU 报价 + abort 释放行为 + 账号等级现状      [P0,第1天]
  ├─ 业务方:DAU/峰值场景证据书面确认                    [P0,第1天]
  ├─ 平台直压摸底(独立轮次,前置)                     [P1]
  ├─ 原准入项:DB 池/readiness 解耦/login 缓存           [保留]
  └─ 新增:路由分流改造 + LLM 诊断日志改造               [P1]

W1(200 并发)   基线回归,同原计划
W2(1000 并发)  公共 API+提额;分流改造上线;读写分离评估(前移)
W3(2000 并发)  分流生效;DTU 低档;读副本接入;完整生成口径抽样轮
W4(5000 并发)  仅当业务证据成立;DTU 高档 或 PAI 自建;含 30min 稳态 + 60min 长跑
```

## 五、结论

1. **Excel 方法论合格**(8/10),止涨线/降级/留痕框架可直接沿用
2. **三个 P0 未闭环前不开压**:业务必要性、DTU 供给、口径失真——任一未解决,W4 5000 并发都是无效投入或必然失败
3. **最优路径是"分阶段 + 多模型分流"**:W2 验 1000(近零 LLM 成本)→ W3 验 2000(月 5~10 万)→ W4 视业务证据决定 5000(月 15~30 万),对比原计划单一路径(月 50~100 万)成本降至 1/5~1/3,覆盖 90% 政企场景
4. **代码侧两个改造须在 W2 前完成**:路由分流(成本)、LLM 诊断日志(可观测性)——后者与 10-19 生产 PoolTimeout 排查直接相关
