Q: RAG知识库开发 要不要对入库检索做文件级的灰度发布？
A: # 结论先行
**建议做文件级灰度，但不是强制；取决于你的知识库规模、变更频率、业务容错要求。**
> 简单一句话：小体量低频更新知识库可以跳过；面向生产、多文档持续迭代、用户在线使用的RAG，强烈上**文件级灰度**，而不是全库一次性上线。

下面从原理、收益、代价、落地方案、取舍判断，逐层拆解。

## 一、先分清两个概念：全库灰度 vs 文件级灰度
1. **全库灰度**：向量库整个实例切流量，一部分用户查旧库，一部分查新库（版本库切换）
2. **文件级灰度（文档粒度灰度）**：**同一套检索服务**，新上传/更新的文档，只对指定用户/指定会话可见；其余用户检索时，完全看不到这份新文档，旧文档不受影响。
    - 控制维度：**单文件/单文件夹/单文档集**作为灰度单元
    - 检索逻辑：检索召回时，增加**文档权限过滤条件**，灰度白名单用户才可以命中这份文档的切片chunk

> 本质：不是切服务流量，是**在召回层加文档可见性标签**。

## 二、为什么RAG入库检索，适合文件级灰度？
RAG最常见线上风险，基本都来自**单份坏文档污染全库**：
- 文档OCR/解析失败，脏文本入库 → 产生幻觉、错误事实
- 文档分块、embedding不适配，chunk质量差 → 检索漂移、无关召回
- 文档内容过时、涉密、内部草稿误上传 → 敏感信息被检索召回
- 新文档和已有知识库存在事实冲突（新旧版本手册并存）

文件级灰度的核心价值：
1. **风险隔离**：新文档入库后，先只给测试账号/内部种子用户检索，验证召回、回答效果；有问题直接下线单文件，**不影响存量成熟知识库**。
2. **效果评估可对比**：同一检索模型、同一embedding，白名单用户可以对比“有这份文档”vs“没有”的回答差异，单独评估这份文档增益。
3. **回滚极快**：不需要重建向量库、不需要切整个库版本；只修改文档灰度标签，关闭可见性，秒级回滚，不用重删向量。
4. **支持分批次上线**：比如一批200份产品文档，可以先灰度10份验证，没问题再放开剩下。

> 对比：如果直接全量入库，一旦一份文档有问题，要么删整个向量集、要么在线脏数据持续影响所有用户，排查成本很高。

## 三、代价 & 不适合做文件灰度的场景
### 成本
1. **业务层改造**
    - 文档元数据新增字段：`gray_status`（待灰度/灰度中/全量上线/下线）、`gray_white_list`（用户ID/租户/角色）
    - 检索接口改造：每次检索请求携带`user_id/role`，查询阶段**过滤chunk**，只召回该用户可见的文档切片
    - 入库链路：文档解析→分块→向量化→写入向量库，**同时写入元数据库（文档标签、灰度状态）**
    - 管理后台：文档列表支持灰度状态切换、预览灰度效果
2. **检索性能损耗**
    向量检索本身不做过滤，**召回TopK之后，再根据元数据过滤掉无权限文档**；极端情况会出现：向量召回的结果全是灰度不可见文档，召回为空。
    👉 优化方案：向量库支持带metadata预过滤（Milvus、ES、PGVector都支持metadata过滤，把灰度标签作为索引字段，在向量检索阶段直接过滤，而不是召回后过滤）。
3. **逻辑复杂度上升**
    文档更新场景最难处理：一份文档从灰度→全量；文档版本迭代（v1灰度，v2重新灰度）；文件夹批量灰度。要处理chunk的新增、替换、删除，保证标签一致性。

### 不建议做文件级灰度的场景
满足任意一条，可以不做：
1. 知识库很小（几十份以内文档，更新低频，比如季度才更新），每次上线人工完整验收全部文档
2. 纯内部测试环境，没有真实终端用户，允许全库推倒重建
3. 文档之间强耦合，**单文件独立验证没有意义**（比如整套合同体系，单独灰度其中一份，回答会断上下文）
4. 检索引擎不支持metadata过滤，并且你不想额外开发元数据管理模块

## 四、落地设计方案（工程可直接参考）
### 数据模型设计
**文档元数据表（MySQL/PostgreSQL）**
|字段|说明|
| ---- | ---- |
|doc_id|文档唯一ID，一份文件一个doc_id|
|file_name|文件名|
|gray_status|enum：pending / gray / online / offline|
|gray_scope|灰度范围：白名单用户列表 / 租户ID / 角色|
|version|文档版本号，更新文档时递增|

**向量库每个chunk的metadata必须携带：`doc_id`**
> 向量本身不带灰度状态，灰度状态存在元数据库；检索时，根据用户身份拿到**允许访问的doc_id列表**，作为向量检索的过滤条件。

### 完整链路
1. 上传文档 → 解析、清洗、分块、向量化
2. chunk写入向量库，绑定`doc_id`；doc记录写入元数据库，默认`gray_status = pending`
3. 管理员手动开启灰度：设置gray_scope → 状态改为`gray`
4. **检索请求流程**
    ① 传入user_id
    ② 元数据库查询：该用户可见的所有doc_id集合
    ③ 向量检索时带上过滤条件 `doc_id IN [允许列表]`
    ④ 返回chunk，送入LLM生成答案
5. 灰度观测：收集种子用户问答日志，看召回准确率、幻觉、冲突问题
6. 验证通过 → 状态改为`online`（对所有用户开放）；发现问题 → 状态改为`offline`，检索直接过滤

> 进阶：支持**文件夹级灰度**，批量设置目录下所有doc的灰度状态，减少单文件操作。

### 两种检索过滤选型
1. **向量库预过滤（推荐，性能好）**：Milvus、Chroma、PGVector支持metadata过滤，在向量距离计算前就筛掉不可见doc。适合生产。
2. **召回后过滤（简单，性能差）**：向量先召回TopK，再根据doc_id过滤。适合原型，高并发场景不推荐。

## 五、灰度上线的观测指标（用来判断这份文档能不能放开全量）
针对灰度用户，单独统计新文档相关问答：
1. 召回指标：新文档chunk被召回的频次、是否挤占原有正确文档
2. 质量指标：引用这份文档的回答，幻觉率、人工标注正确率
3. 冲突指标：新文档和存量知识库事实冲突的案例
4. 拒绝/异常：有没有出现敏感内容、错误数据被回答

## 六、对比方案选型矩阵
|方案|适用场景|优点|缺点|
|---|---|---|---|
|**文件级灰度（推荐生产）**|持续新增文档，在线业务，文档独立|风险最小，回滚快，单文档可控|需要开发元数据、检索过滤逻辑|
|**版本库灰度（全库切换）**|知识库一次性大批量整体更新|架构简单，没有检索过滤损耗|粒度粗；只要一个文档坏，整个版本库不能上线，回滚慢|
|**直接全量入库**|小库、低频更新、纯内网测试|开发量最小|风险集中，坏文档直接影响全部用户|

## 七、一个折中轻量化方案（不想做太重开发）
如果不想完整实现用户白名单，可做**简易文件灰度**：
- 新文档打上标签 `is_gray: true`
- 系统增加一个**测试开关**：管理员账号检索时包含gray文档；普通用户检索自动排除gray文档
> 不需要复杂白名单，只区分管理员/普通用户。开发成本很低，也能隔离新文档风险，很多中小RAG项目先用这个方案。

Q:知识图谱检索 支持灰度发布吗？
A:# 结论先行
**知识图谱检索天然可以做灰度，但和RAG向量库的「文件级灰度」实现思路不一样；粒度不是文件/Chunk，而是图谱实体、关系、子图/子领域。**
> 一句话区分：向量RAG灰度是**文档可见性**；知识图谱（KG）灰度是**三元组/子图的可见性**。
> 同时：KG灰度难度 > 向量RAG文件灰度，因为图谱有**实体关联传递效应**，这是最大坑。

## 一、KG灰度的两种粒度选型
### 1）细粒度：三元组/实体级灰度（最常用，对应RAG的文件级灰度）
灰度单元：单个实体、某类关系，或者一组关联三元组（子图）
- 给实体/三元组增加元数据标签：`gray_status`、`gray_scope`（白名单用户/角色）
- 查询时做过滤：普通用户查询图谱，**不匹配灰度标签的实体、关系直接被裁剪**；灰度白名单用户才能访问
- 适用场景：新增一条业务规则、新增一类实体（如新增一类产品）、小批量补全图谱数据

⚠️ 核心风险【图谱传递污染】
> 向量Chunk是孤立的；图谱实体互相连接。
> 举例：灰度新增实体`产品A`，它和存量实体`售后规则`有一条关系。
> 如果只标记`产品A`为灰度，**不标记这条关联关系**：普通用户查询售后规则时，可能沿着边关联到灰度实体，泄露灰度数据。
> ✅ 原则：**灰度是子图粒度，不是单个实体粒度；子图=实体+所有关联边，整体打上灰度标签**。

### 2）粗粒度：图谱版本/子领域灰度（对应RAG全库版本灰度）
灰度单元：整个子领域图谱（例如：新业务线的全部图谱），或者完整图谱快照
- 方案A：多套独立图谱实例。旧实例给全量用户，新图谱实例只给灰度用户；验证完成后切换流量。
- 方案B：图谱内部分namespace，不同领域数据隔离，新领域先挂gray标签。
- 适用场景：大批量图谱构建，比如一次性导入整套新业务本体、大规模抽取的三元组集合。
> 优点：没有关联泄露问题；缺点：粒度粗，不能单独上线少量实体。

## 二、KG灰度怎么实现（两种技术路线）
### 路线A：查询时过滤（推荐，对应向量库metadata过滤）
> 适合：Neo4j、NebulaGraph、JanusGraph这类图数据库
1. 元数据改造：**实体节点增加属性 `gray_status, gray_scope`；关系边也必须增加这两个属性**（重点！很多人漏边的标签）
2. 查询层统一拦截：Cypher/nGQL 增加`WHERE`过滤条件
```cypher
// Neo4j示例：普通用户，过滤掉灰度子图
MATCH (e:Entity)-[r:REL]->(e2:Entity)
WHERE e.gray_status <> 'gray' AND r.gray_status <> 'gray'
RETURN e, r, e2
```
灰度用户则不带这个过滤条件，可访问灰度子图。

3. 检索链路：
用户请求 → 拿到用户身份 → 图查询语句注入灰度过滤条件 → 返回裁剪后的子图 → 送入LLM做图谱问答。

> 优点：一套图谱存储，不用多实例；新增子图直接打标签；回滚只改标签，不用删数据。
> 缺点：查询语句必须统一处理，**所有查询入口都要加过滤，容易漏写Cypher，造成灰度数据泄露**；复杂图查询（多跳）会增加过滤开销。

### 路线B：多图谱实例/多图空间隔离（重方案，高可靠）
- 灰度图谱：独立图空间/独立图实例，存放待验证的子图数据
- 路由层：根据用户是否灰度，路由到【生产图谱】or【生产图谱+灰度图谱合并查询】
- 验证完成后，把灰度子图merge入主生产图谱
> 优点：完全隔离，不存在边关联泄露，安全；适合强合规场景。
> 缺点：存储双倍，合并子图、处理实体ID冲突成本高；数据同步复杂。

## 三、KG灰度 vs RAG向量文件灰度，核心差异
|维度|RAG向量库（文件灰度）|知识图谱检索（子图灰度）|
|---|---|---|
|灰度单元|文档/Chunk，数据相互独立|子图（实体+边），数据强关联|
|最大风险|坏Chunk召回污染回答|**关联穿透：普通用户通过存量实体关联到灰度实体**|
|过滤位置|向量检索前/召回后过滤doc_id|图查询语句中过滤节点+边|
|回滚|修改文档标签|修改节点+边标签；或直接不合并主图|
|复杂度|低-中|中-高|
|适用场景|文档、手册、非结构化素材增量上线|业务规则、实体关系、结构化知识增量迭代|

## 四、什么时候建议做KG灰度，什么时候不做
✅ 推荐做KG灰度
1. 图谱**持续迭代**：不断抽取、新增实体/业务规则，在线业务不能停库重建
2. 图谱问答对错误敏感：错误三元组会直接导致事实错误回答，幻觉风险高
3. 新增知识是局部子图，不需要一次性全量更新整个本体
4. 合规要求：新业务知识需要内部验证，不能直接暴露给终端用户

❌ 可以不做
1. 图谱低频更新，每次更新可以停机重建，离线全量验收后上线
2. 图谱很小、本体固定，极少新增实体关系
3. 图谱是一次性构建，后续只读，不再新增数据

## 五、KG灰度落地避坑清单（重点）
1. ❌ 只给节点打灰度标签，**忘记给关系边打标签** → 关联穿透泄露
2. ❌ 部分查询接口没有统一封装Cypher，裸写查询语句绕过过滤 → 安全漏洞
3. ❌ 忽略实体消重：灰度子图实体和主图谱实体ID不一致，上线合并产生重复实体
4. ❌ 多跳查询性能衰减：大规模图谱，全量where过滤会拖慢查询，需要给gray_status建索引
5. ❌ 灰度观测难：相比向量RAG，很难统计「灰度三元组被使用频次」，需要埋点：记录返回结果中命中灰度实体的问答日志

> 观测指标（灰度验证阶段）
> 1. 灰度子图三元组被检索命中次数
> 2. 问答结果依赖灰度三元组时的正确率、错误事实率
> 3. 实体冲突：灰度实体和存量图谱实体有没有矛盾事实
> 4. 召回子图大小：新增子图是否引入无关冗余关系

## 六、工程折中轻量方案（低成本）
如果不想做全量身份白名单，最简版本：
- 节点、边增加布尔属性 `is_gray`
- 增加全局开关：管理员/测试账号查询不过滤`is_gray=true`；所有普通用户自动过滤
> 不用复杂白名单，仅区分测试账号，适合中小型KG+RAG混合知识库，开发量小。

## 七、【RAG+KG混合检索场景】灰度联动（你大概率会遇到）
很多系统是向量检索 + 知识图谱联合检索，灰度要两边协同：
1. 非结构化文档：文件级灰度（向量侧）
2. 结构化业务知识：子图级灰度（图谱侧）
> 重要：**一份文档解析抽取出来的KG子图，灰度状态必须和这份原始文档保持一致**。
> 文档处于灰度 → 它抽取出来的所有实体/三元组也灰度；文档全量上线 → 子图同步放开；文档下线 → 子图同步隐藏。
> 否则会出现：普通用户看不到原文文档，但是能从图谱问答拿到文档抽取出来的知识，出现权限不一致漏洞。

## 思考题（帮你评估落地）
1. 你的知识图谱更新模式：是新增子图，还是整体重建本体？
2. 检索是几跳查询？多跳越多，灰度过滤带来的性能影响越大。
3. 是否和向量RAG混用？如果混用，你需要统一一套灰度状态同步机制。

Q:灰度发布，对于向量入库更新 本质就是改标签吗？
A:# 一句话结论
**绝大多数「文件级灰度」的向量入库更新：本质就是改元数据标签，不需要改动向量本身，也不用重新Embedding。但有例外场景，不是所有向量更新都只是改标签。**

下面拆开讲边界、前提、坑点，顺便区分：**灰度控制逻辑** vs **向量数据变更逻辑**

## 1. 标准文件级灰度：只改标签，不动向量
> 就是咱们前面聊的方案：文档解析→分块→向量化→写入向量库，chunk的metadata带上`doc_id`；灰度状态存在文档元数据（MySQL/PG），**向量本身不存灰度标签**。

流程：
1. 新文档入库，生成chunk向量写入向量库；
2. 文档元数据表标记为 `gray`；
3. 检索阶段：根据用户身份，查出该用户允许访问的`doc_id`集合，向量检索时用`doc_id`做metadata过滤；
4. 灰度验证通过 → **只更新MySQL里这条doc的`gray_status`改成online**，向量完全不动；
5. 发现问题 → 改成offline，检索直接过滤掉这个doc下所有chunk。

✅ 本质：**向量数据一次性写入；灰度开关是「检索时的访问权限过滤」，不是修改向量。**
向量、embedding、chunk内容都不变，只是**查询条件过滤**。
> 类比：数据库表里数据已经插入，只是给记录打一个“是否对外可见”标记，select的时候加where条件。

## 2. 两种“不是只改标签”的场景（很容易混淆）
### 场景A：文档内容更新（不是单纯灰度切换状态）
如果文档**内容修改**：
- 需要重新解析、重新分块、重新生成embedding；
- 新增chunk写入向量库，旧chunk保留/删除；
- 再更新元数据。
👉 这是**业务数据变更**，不是灰度状态切换。灰度只是控制这批新向量能不能被用户检索到。

> 区分：
> - 切换灰度状态：仅改标签 ✅
> - 文档版本升级、内容修改：要重算向量 ❌

### 场景B：向量库不支持metadata过滤，采用「多向量库实例灰度」（版本库灰度）
方案：独立两套向量库，旧库全量用户，新向量库给灰度用户，流量路由切换。
- 这个模式下，**根本没有标签**；灰度是流量路由，向量是两套独立数据集。
- 此时灰度发布不是改标签，是切流量。
> 对应前面说的「全库版本灰度」，和文件级灰度不是一套架构。

## 3. 关键澄清一个容易踩的误区
很多人会想：**能不能直接把gray标签塞到向量库chunk的metadata里面，在向量库存灰度状态？**
> 技术上可行，但工程上不推荐。
- 做法：每个chunk.metadata里写`is_gray=true`，检索时直接在向量库加过滤条件。
- 缺点：
  1. 文档几十上百个chunk，**要批量更新所有chunk的metadata**才能切换灰度状态；
  2. 如果文档很大，上千chunk，一次更新大量向量元数据，开销高；
  3. 容易出现部分chunk更新成功、部分失败，状态不一致。

👉 最佳实践：**灰度状态统一存在文档级元数据库（MySQL），向量库只存doc_id**。
切换灰度，只更新**一行doc记录**，不用碰向量库，原子性好、成本极低。

## 4. 对比知识图谱灰度，帮你串联记忆
- 向量文件灰度：**文档粒度的访问标签，检索按doc_id过滤chunk；向量本体不变**
- KG子图灰度：**子图（节点+边）都要带可见标签；多跳查询容易穿透泄露**

## 5. 一句话总结边界
> **当你做【单文件上线/下线灰度，文档内容不变】：灰度操作本质就是修改文档元数据标签，向量不用动。**
> **当文档本身内容发生变更：灰度只是控制新一批向量是否可见，向量本身必须重新生成。**

Q:向量检索基于元数据中标签过滤，标签是怎么来的。
A:# 一句话总结
**元数据标签分为两类：一类是【文档/业务属性标签】（业务系统生成）；一类是【灰度权限标签】（文档管理模块在入库流程附加），它们都不是向量模型算出来的，是业务侧在文档处理流水线里打进去，跟着chunk一起存入向量库metadata。**

> 核心区分：
> - `doc_id`、`file_name`、`upload_time`、`source_type`、`tenant_id`：**业务属性标签**
> - `gray_scope`、`is_gray`、`doc_status`：**灰度/权限标签**
>
> 向量本身（embedding浮点数组）**不含任何标签**；标签是挂在这个向量分片（chunk）上的附属K-V元数据。

## 一、标签从哪来？完整流水线
```
上传文件 → 文档管理服务（Document Service）
    ↓
1. 文档入库元记录写入MySQL/PG（doc主表，保存灰度状态、白名单、版本）
    ↓
2. 文档解析、清洗、切分chunk
    ↓
3. 【给每个chunk组装metadata字典】
   metadata = {
       "doc_id": "doc_10086",       // 关键外键，关联文档主表
       "file_name": "产品手册v2.pdf",
       "uploader": "zhangsan",
       "tenant_id": "t_001",
       "chunk_idx": 3
   }
    ↓
4. 文本chunk → Embedding模型生成向量
    ↓
5. 向量 + metadata 一起写入向量库(Milvus/PGVector等)
```

> 重点：**灰度状态`is_gray`本身，不建议存在向量库metadata！**
> 前面我们约定的最优方案：向量库只存`doc_id`，**灰度状态保存在文档主表（MySQL）**。
> 检索时：根据user_id查MySQL，拿到该用户可见`doc_id列表`，向量检索带上过滤条件 `doc_id IN [xxx]`。
>
> 👉 向量库里的标签，**核心作用是关联回文档主记录，不是直接存灰度开关**。

## 二、两种实现方式的标签设计对比
### 方案1：推荐方案（灰度状态存在外部文档元库）
向量库chunk metadata只放：`doc_id`、`chunk_idx`、`tenant_id`等**静态不变标签**
- 标签生成时机：**文档切分阶段一次性生成，写入向量库后几乎永不修改**
- 灰度切换：**完全不改动向量库的任何metadata**，只更新MySQL里doc的`gray_status`
- 优点：不用批量更新大量chunk元数据，原子性强，不会出现部分chunk状态不一致

### 方案2：简化方案（直接把灰度标签塞进向量metadata）
> 适合小体量原型，生产不推荐
```json
metadata={
  "doc_id":"doc_10086",
  "is_gray":true
}
```
- 标签生成：入库时打`is_gray=true`
- 灰度放行时：**需要批量更新这个doc下所有chunk的metadata，改成is_gray=false**
- 缺点：一个文档几百上千chunk，批量更新向量库元数据，开销大、容易部分成功，状态撕裂。

## 三、标签来源细分
1. **文档基础信息标签（上传阶段生成）**
`doc_id`（UUID/雪花ID，文档服务生成）、文件名、上传人、上传时间、租户ID、文件类型。
> doc_id是整个链路最核心的关联键，**一个文件全局唯一doc_id，所有它拆分出来的chunk共用同一个doc_id**。

2. **解析/分块阶段自动生成标签**
`chunk_idx`（当前文档第几个切片）、页码、章节号、来源页面、OCR置信度。
> 来自PDF解析器、MinerU等文档解析工具输出。

3. **人工/业务配置标签（管理员手动打）**
业务分类：`category:产品手册`、`department:售后部`；
权限标签：`acl_role:admin`；
> 在文档上传后台手动录入，然后自动透传给所有该文档下的chunk。

4. **抽取得到的知识标签（可选，NLP生成）**
关键词、文档主题标签，用LLM对全文摘要后打标签，可用于过滤。

## 四、检索阶段怎么使用这个标签
以Milvus举例，伪逻辑：
1. 用户发起查询，带上`user_id`
2. 文档元数据库查询：`select doc_id from doc_table where user_has_access(user_id, doc_id)`
3. 拿到允许访问的doc_id数组，作为过滤条件
4. 向量检索：`vector_search(query_embedding, filter="doc_id in [doc1,doc2,doc3]")`
5. 向量库只返回metadata里doc_id命中的chunk

> 这里的`doc_id`就是前面入库时，跟着chunk一起写入向量库的**元数据标签**。

## 五、高频误区澄清
1. ❌ 标签是embedding向量编码里自带的
✅ 不是！向量只是浮点数数组，**标签是独立K-V元数据，和向量分开存储**。向量库支持在向量之外附加metadata字段。

2. ❌ doc_id是从文件名解析出来的
✅ 不是。文档服务生成全局唯一ID，文件名可以重复，doc_id永远唯一。

3. ❌ 修改文档灰度，需要更新向量里的doc_id标签
✅ 不需要。doc_id一旦生成就固定不变；灰度开关在外层文档表。

## 六、延伸：和知识图谱做对照
- 向量侧：**chunk绑定doc_id标签，doc的灰度状态在外层主表**，检索通过doc_id过滤
- KG侧：**节点、边自身挂载gray_status属性**，查询时Cypher过滤节点和边属性

Q:人工 / 业务配置标签（管理员手动打） 业务分类：category:产品手册、department:售后部； 权限标签：acl_role:admin；  这种3种标签一般在实际业务中怎么用，帮我举例。
A:# 概述
先说核心定位：
> `category`【业务分类标签】：**知识内容归类，用于检索过滤、知识库导航、统计**
> `department`【归属部门标签】：**归属主体，用于数据隔离、运维管理、按部门开放知识库**
> `acl_role`【角色权限标签】：**访问控制，谁能看见这条chunk，偏权限鉴权**

三者经常一起搭配，但职责不一样，不要混用。下面用**企业内部RAG客服知识库**举例，场景是售后/产品/销售三个部门，文档有产品手册、故障FAQ、内部预案。

> 前置前提：
> 文档上传后台，管理员上传文件时，在页面下拉框选择这3个标签；系统自动把标签透传给这份文档**所有chunk的metadata**。
> 一个文档下全部chunk，共用同一套 `category / department / acl_role`。

## 1. category: 业务分类标签（内容是什么）
作用：**描述文档内容类型，和“谁能看”无关，只描述知识品类**
可选示例值：
`产品手册`、`故障FAQ`、`合同模板`、`运维预案`、`价格表`、`培训课件`

### 业务用法举例
场景：用户问「A设备怎么拆机」
1. 检索时，**业务可以加引导过滤**：优先召回 `category="产品手册"` 的chunk，减少FAQ、合同内容干扰
    ```
    filter = 'category in ["产品手册","故障FAQ"]'
    ```
2. 后台统计：统计各分类文档数量、各分类chunk被召回次数
    - 产品手册被召回了多少次
    - FAQ召回命中率多少
3. 前端知识库目录：按category分组展示，用户可以在后台筛选查看所有产品手册类文档
4. 路由分流：RAG意图识别识别到【产品操作类问题】，检索时带上category过滤；识别到【合同问题】就过滤合同类文档

> ⚠️ 误区：category**不是权限**。就算category=产品手册，普通员工能不能看，不由category决定。
> category回答「**这是什么类型的知识**」

## 2. department：归属部门标签（知识是谁维护的）
作用：**标记这份知识归属哪个业务部门，运维、数据隔离、责任人管理**
可选示例值：
`售后部`、`产品部`、`销售部`、`财务部`

### 业务用法举例
场景：售后部维护故障FAQ；产品部维护产品手册；销售维护报价资料
1. **部门管理员权限**：售后部管理员登录后台，只能管理 `department="售后部"` 的文档，不能编辑产品部文档。（后台文档管理权限，**不是检索时用户问答权限**）
2. **批量运维**：产品部业务下线，批量归档/下线 `department="产品部"` 的全部文档
3. **数据统计**：各部门知识库维护工作量、各部门知识的召回质量统计
4. 可选：业务上做**部门知识隔离（可选）**，比如销售不能检索售后内部故障预案：检索过滤 `department in [当前用户所属部门]`

> ⚠️ 区分：department 代表**维护归属**，不等于访问权限；但业务上经常拿它做简易隔离。
> department回答「**谁负责维护这份文档**」

## 3. acl_role：访问角色标签（谁有权限看这条知识）
作用：**访问控制标签，检索鉴权用，决定当前用户能不能召回这个chunk**
可选示例值：
`admin`、`aftersale_staff`、`sales`、`all_user`
- `all_user`：全员可见
- `aftersale_staff`：仅售后人员
- `admin`：管理员才能查看的内部敏感预案

### 业务用法举例
场景：一份【重大故障应急处置预案】，acl_role=admin，只有管理员账号能检索召回
1. 用户提问前，拿到当前登录用户角色：比如用户角色是 `aftersale_staff`
2. 向量检索过滤条件：`acl_role in ["all_user", "aftersale_staff"]`
3. 这份预案chunk metadata里 `acl_role=admin`，不满足条件 → 直接被过滤，召回不到。
4. 管理员角色查询，过滤条件带上admin，就可以正常召回这份敏感文档。

> acl_role回答「**哪些角色可以访问这份知识**」

| ---- | ---- | ---- | ---- | ---- |

## 工程落地建议（踩坑点）
1. **标签继承规则**：文档级配置，**所有chunk自动继承**，不要chunk单独打标签。人工只在文档上传时配置一次。
2. **不要用category/department代替acl_role**
    ❌ 错误：用department=售后部，当做权限控制，认为销售不能看售后文档
    ✅ 正确：department只代表维护方；acl_role才是访问权限。
    业务上可以叠加，但是语义要分开，否则后期权限逻辑越写越乱。
3. 和之前**灰度标签的关系**
    - acl_role 是**长期角色权限**
    - gray_status 是**临时发布状态（灰度/全量）**
    > 检索过滤条件 = `(acl_role 匹配) AND (灰度状态允许)`
    > 两个条件同时生效：就算角色有权限，文档还在灰度，普通用户依旧看不到。

> 伪代码检索过滤拼接示例：
```python
# 当前用户角色
user_role = "aftersale_staff"
# 用户是否灰度账号
is_gray_user = False

# 允许访问的acl角色
acl_allow_list = ["all_user", user_role]
# 允许访问doc_id（灰度逻辑从doc主表查询）
allow_doc_ids = get_visible_doc_ids(user_id, is_gray_user)

# 向量库过滤条件
filter_expr = f'''
    acl_role in {acl_allow_list}
    and doc_id in {allow_doc_ids}
    and category in ["产品手册","故障FAQ"]
'''
```

# 1. 标签数据从哪里来？怎么知道有哪些可用标签？
## 1.1 标签存在两处
1）**文档管理元数据库（MySQL/PG，doc主表）**
管理员在后台上传文档，下拉选择标签：`category、department、acl_role`。
doc表字段示例：
|doc_id|category|department|acl_role|file_name|
|---|---|---|---|---|
|doc001|产品手册|售后部|aftersale_staff|A设备拆机手册.pdf|
|doc002|故障FAQ|售后部|all_user|A设备常见故障.md|
|doc003|合同模板|销售部|sales|采购合同.docx|

> 👉 这里维护**标签字典（枚举）**，在后台配置页面做下拉选项，**管理员不能随便输入自由文本，防止标签脏数据**
> category枚举：`["产品手册", "故障FAQ", "合同模板", "运维预案"]`
> 这个枚举存在配置中心/数据库字典表，前端上传页面、后端检索服务共用同一份。

2）**向量库Chunk的metadata**
文档切片后，每一个chunk写入向量库时，**把这份文档的category/department/acl_role原样塞进chunk metadata**。
> 同一个doc下所有chunk，category完全相同，继承文档的标签。
> 向量库中一条chunk记录简化结构：
```json
{
  "id": 10001,
  "vector": [0.12,0.34,...],
  "metadata": {
    "doc_id": "doc001",
    "category": "产品手册",
    "department": "售后部",
    "acl_role": "aftersale_staff",
    "chunk_idx": 5
  }
}
```

✅ **怎么知道有哪些标签可用？**
从【标签字典表】读取，统一管理，不要硬编码在业务代码。
字典表 `sys_tag_category`：
|tag_code|tag_name|description|
|---|---|---|
|product_manual|产品手册|设备操作、安装拆机类文档|
|faq|故障FAQ|问题快速问答|
|contract|合同模板|采购、商务合同|

> 推荐用编码（product_manual）存到向量metadata，中文做展示名，避免中文编码、引号转义坑。

# 2. 在哪里加引导过滤？（插入点非常关键）
RAG检索模块的时序：
1. 用户Query：`A设备怎么拆机`
2. 【意图识别模块】输入query，输出意图类型：`product_operation`（产品操作类）
3. 【检索参数组装层】**这里就是添加category引导过滤的位置！**
   - 根据意图 `product_operation` 查表映射 → 允许category列表 `["product_manual", "faq"]`
   - 同时并行获取**硬权限过滤**：用户角色acl、灰度可见doc_id列表
   - 拼接完整filter表达式，传给向量库SDK
4. 向量库执行：先向量相似度计算 + metadata过滤，返回TopK chunk
5. 拿到chunk，送入LLM生成答案

> ❌ 不能放在LLM里让大模型去筛选chunk；LLM只负责回答，不做检索过滤
> ❌ 不是写在入库流程；入库是打标签，检索阶段才使用标签过滤

## 意图映射配置（放在配置中心/数据库，不要硬编码）
意图→允许category映射表 `intent_category_mapping`
|intent_code|intent_name|allow_category_list|
|---|---|---|
|product_operation|产品操作|["product_manual","faq"]|
|contract_query|合同查询|["contract"]|
|fault_report|故障报修|["faq","product_manual"]|
|general|通用问答|["product_manual","faq","contract","ops_plan"]|

# 3. 代码示例（Python，Milvus SDK，可直接参考）
```python
from pymilvus import Collection
import json

# ====================== 配置：意图 -> category映射（生产放配置中心/Nacos） ======================
INTENT_CATEGORY_MAP = {
    "product_operation": ["product_manual", "faq"],
    "contract_query": ["contract"],
    "fault_report": ["product_manual", "faq"],
    "general": ["product_manual", "faq", "contract", "ops_plan"]
}

# ====================== 模拟输入 ======================
user_query = "A设备怎么拆机"
user_role = "aftersale_staff"       # 从登录态获取用户角色
intent_code = "product_operation"    # 意图识别模型输出结果
topk = 5

# 1. 根据意图拿到【引导过滤category列表】
allow_categories = INTENT_CATEGORY_MAP[intent_code]

# 2. 【硬权限过滤】：查询元数据库，拿到当前用户灰度+acl允许访问的doc_id列表
# get_visible_doc_ids() 访问MySQL文档主表，返回doc_id数组
allow_doc_ids = get_visible_doc_ids(user_id="u123", user_role=user_role)

# 3. 拼接 Milvus filter 表达式
# 条件：category 在引导列表 AND doc_id 在可见列表
filter_expr = (
    f'category in {json.dumps(allow_categories)} '
    f'and doc_id in {json.dumps(allow_doc_ids)}'
)
print("最终向量库filter表达式：", filter_expr)
# 输出：category in ["product_manual", "faq"] and doc_id in ["doc001","doc002"]

# 4. Embedding 向量化query
query_emb = embedding_model.encode(user_query)

# 5. 向量检索，把filter传给Milvus
coll = Collection("knowledge_chunk")
coll.load()

search_params = {
    "metric_type": "IP",
    "params": {"nprobe": 10}
}

result = coll.search(
    data=[query_emb],
    anns_field="vector",
    param=search_params,
    limit=topk,
    expr=filter_expr,  # <<<<<< 【引导过滤+权限过滤在这里传给向量库】
    output_fields=["doc_id", "category", "chunk_text"]
)

# 拿到召回chunk，后续送入LLM
retrieved_chunks = []
for hits in result:
    for hit in hits:
        retrieved_chunks.append(hit.entity.get("chunk_text"))
```

> 如果是PGVector，写法是SQL的WHERE条件：
```sql
SELECT doc_id, category, chunk_text, vector <-> $1 AS distance
FROM knowledge_chunk
WHERE category IN ('product_manual','faq') AND doc_id IN ('doc001','doc002')
ORDER BY distance LIMIT 5;
```

# 4. 两个重要业务策略：软过滤兜底方案（工程必做）
上面这种**category引导过滤有风险**：
如果用户问的拆机内容，**不在产品手册/FAQ里**，会召回为空！
解决方案两种，二选一：
## 方案A：双路检索（推荐生产）
1. 第一路：带category引导过滤，取top5（优先匹配目标分类）
2. 如果第一路召回结果不足2条，**第二路去掉category引导过滤，只保留硬权限过滤，召回兜底结果**
> 硬权限（acl+灰度doc_id）永远不能关闭；category引导过滤可以降级关闭

伪代码逻辑：
```python
# 第一路：带category引导过滤
chunks_primary = vector_search(filter=filter_with_category)
if len(chunks_primary) >= 2:
    final_chunks = chunks_primary
else:
    # 兜底：去掉category引导条件，只保留权限过滤
    filter_only_auth = f'doc_id in {allow_doc_ids}'
    chunks_backup = vector_search(filter=filter_only_auth)
    # 合并、去重，取topK
    final_chunks = dedup_and_merge(chunks_primary, chunks_backup)
```

## 方案B：权重加分（不做过滤，用重排实现软引导）
不直接过滤掉其他category，而是在重排（Rerank）阶段，**给目标category的chunk加分**。
- 产品手册、FAQ chunk → +0.2分数
- 合同、其他类别 → 不加/减分
> 优点：不会出现召回为空；缺点：向量检索要扫更多候选，重排增加开销。适合意图识别不准的场景。

# 5. 后台统计：怎么统计各category召回次数？
**统计不是向量库做，而是检索请求埋点**
每次检索完成后，把召回的chunk信息写入日志/clickhouse：
埋点字段：
`query_id, user_id, intent_code, doc_id, category, chunk_id, is_used`

然后SQL统计示例：
```sql
-- 产品手册被召回多少次
select category, count(distinct query_id) as recall_times
from rag_retrieval_log
where category = 'product_manual'

-- FAQ召回命中率：人工标注的正确召回 / FAQ总召回次数
```

# 7. 常见坑
1. ❌ 标签使用中文字符串直接写filter：Milvus部分版本对中文字符串转义容易报错；**推荐标签编码用英文code，前端展示映射中文**
2. ❌ 意图识别不稳定，错误映射category，导致召回为空 → 必须兜底检索
3. ❌ 把category引导过滤当成权限控制：category只是业务归类，**权限必须用acl_role+灰度doc_id硬过滤**
4. ❌ 标签自由输入，管理员随便写：产品手册 /产品手册（空格），变成两个标签，数据污染，必须用枚举下拉。
