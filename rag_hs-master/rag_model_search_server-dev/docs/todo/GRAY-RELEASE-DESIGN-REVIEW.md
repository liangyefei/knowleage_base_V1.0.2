## 一、正常开发流程方法论

知识库文件级灰度发布是一个典型的**多版本内容权限隔离**需求，正常开发流程应该遵循以下步骤：

### 1.1 需求澄清与方案设计阶段
1. **明确灰度范围**：是知识库级灰度还是文件级灰度？是否需要支持多文件批次发布？
2. **确定可见性规则**：哪些用户能看到灰度内容？灰度内容是否需要特殊标注？
3. **梳理状态流转**：完整的工作流（草稿→审核→灰度→发布→归档），异常回滚路径
4. **审计要求**：是否需要记录每一步操作人和原因？
5. **影响评估**：对现有检索链路、存储、性能的影响有多大？

### 1.2 技术方案关键决策点
| 决策点 | 常见方案 | 选型考虑 |
|--------|----------|----------|
| **多版本存储** | 1. 物理分库/分表<br>2. Milvus同一collection多版本chunk共存<br>3. 独立灰度collection | 方案2侵入性最小，兼容现有架构 |
| **过滤时机** | 1. 检索时过滤（query阶段）<br>2. 检索后过滤（rerank前）<br>3. 结果返回前过滤 | 方案2对检索算法零侵入，实现最简单 |
| **角色对接** | 1. 外部平台API<br>2. 环境变量白名单<br>3. 本地数据库角色表 | 优先1，兜底2，保证开发进度 |
| **KG图谱处理** | 1. 全阶段支持多版本<br>2. 仅发布后构建<br>3. 不支持 | 方案2规避"KG无版本管理"已知问题，风险最小 |

### 1.3 实施阶段
1. **数据模型先行**：定义新表结构，确认唯一约束和索引
2. **状态机核心**：实现状态流转校验，防止非法跳转
3. **接入现有版本体系**：复用已有的`file_version_history`，不重复造轮子
4. **检索链路接入**：在正确的插入点加入过滤逻辑
5. **API暴露**：新增状态机操作API，供管理后台调用
6. **测试验证**：E2E覆盖全流程、权限隔离、异常回滚

## 二、原方案合理性分析

### 2.1 方案优点（✅ 设计非常合理）

#### 1. **侵入性极小，风险可控**
- ✅ 正确识别出插入点：**三路检索收集完成 → 新增过滤 → RRF融合 → 去重 → reranker**
- ✅ 核心检索算法（三路+RRF+rerank+LLM）零改动，符合需求约束
- ✅ Milvus metadata字段扩展，无需修改collection schema，现有数据零迁移
- ✅ 基于已有的文件版本基座（`file_version_history` + blob内容寻址）构建，复用成熟基础设施

#### 2. **架构设计干净优雅**
- **状态机设计完整**：9个状态覆盖正常/异常/归档全场景，驳回都回draft，规则清晰
- **可见性规则明确**：
  - `published` = 全员可见
  - `gray/final_review` = 仅内测可见（标注测试）
  - 其他状态 = 仅管理后台可见
- **数据模型设计合理**：
  - `doc_release`：发布批次主表，含版本标签
  - `doc_release_item`：文件级细粒度控制，`(kb, file_name, version_label)`唯一约束防止冲突
  - `doc_release_audit`：完整审计追踪，驳回原因必填，符合合规要求
- **关键机制处理得当**：
  - 初审通过才灰度入库，旧published chunk不删除 → 驳回零成本（删灰度chunk即可，旧版自动恢复）
  - KG抽取推迟到终审通过 → 规避"KG无版本管理"限制，驳回零污染
  - 同文件多版本命中只保留用户可见最高版本，且放在去重之前 → 解决跨路去重误删问题，这个考虑非常周到

#### 3. **容错与降级设计到位**
- ✅ 角色解析失败采用 **fail-closed**（按普通用户处理，灰度内容不可见），安全默认
- ✅ 过滤异常兜底：只放行`published`，保证服务可用性
- ✅ 存量兼容：metadata无`release_status`视为published，不影响现有数据
- ✅ 环境变量`GRAY_BETA_USER_IDS`白名单兜底，解决"平台API契约未定"的外部依赖风险

#### 4. **分期策略务实**
- **P0** 完成核心功能：状态机+审计+Milvus多版本+过滤+角色解析 → 可独立上线
- **P1/P2** 迭代增强功能：mempalace灰度、代码文件灰度、diff预览 → 不阻塞P0上线
- 一期仅文档灰度，代码文件走状态机但问答灰度不可见 → 聚焦核心目标，降低复杂度

### 2.2 潜在风险与改进建议（⚠️ 需要关注）

#### 1. **Milvus存储膨胀风险**
**问题**：灰度期间新旧两个版本chunk同时存在，文件频繁修改会导致存储量持续增长。

**建议**：
- 增加定期清理任务：自动清理已发布/已驳回的旧灰度chunk
- 对长期处于draft/gray状态（如超过7天）的文档发出提醒
- 数据库层面保留记录，Milvus层面物理删除无用chunk

#### 2. **RRF topk池占位问题**
**问题**：原方案提到"RRF topk池可能被同文件双版本占位"，虽过滤在RRF前已消解，但仍需关注极端情况。

**建议**：
- 过滤时确保同文件只保留一个版本（用户可见最高优先级），从根源上避免占位
- 监控上线后RRF有效候选数变化，评估影响

#### 3. **并发发布一致性**
**问题**：两人同时对同一文件同一版本标签发布，唯一约束能阻止，但需要友好的错误提示。

**建议**：
- API层提前校验冲突，返回明确错误信息
- 考虑加乐观锁或分布式锁防止竞态

#### 4. **知识库删除级联**
**问题**：原方案提到"delete_knowledge_base需级联清release/audit"，这一点容易遗漏。

**建议**：
- 按照`remove_kb_history`模式实现级联删除
- 增加单元测试验证级联删除完整性

#### 5. **性能影响评估**
**问题**：每次问答都需要角色解析（带60s缓存）+ 过滤，增加了些许 latency。

**建议**：
- 角色解析进程内缓存60s，方案已有设计，合理
- 过滤逻辑是纯内存计算，复杂度O(n)，n是候选chunk数（通常几十级别），影响可忽略
- 上线后关注timing日志监控

### 2.3 开放问题澄清

| 开放问题 | 原方案处理 | 评审意见 |
|----------|-----------|----------|
| 平台角色API契约未定 | 先env白名单兜底 | ✅ 处理正确，不阻塞开发 |
| upload_docs_use_path懒创建 | release流要求走blob齐全路径 | ✅ 约束明确，合理 |
| RAG无认证，actor由参数传 | 内网信任模型，沿用现状 | ✅ 符合当前架构，可接受 |

## 三、评审结论

### 总体评价
⭐⭐⭐⭐⭐ **这是一个设计精良、风险可控、侵入性极小的优秀方案**。

原方案作者对现有系统架构理解深刻，找到了最干净的扩展点（RRF前过滤），设计了完整的状态机和审计，充分考虑了容错降级，分期策略务实。核心机制（灰度入库不删旧版、驳回直接删灰度chunk、终审才切换published）设计得非常巧妙，回滚成本几乎为零。

### 可行性结论
✅ **方案可行，建议按原方案实施开发**。

### 必须落实的检查点
1. [ ] 确认Milvus chunk metadata写入`file_version`和`release_status`，无需改schema
2. [ ] 确认过滤逻辑在RRF融合**之前**、去重**之前**执行，保证同文件单版本
3. [ ] 确认`doc_release_item`上`(kb_name, file_name, version_label)`唯一约束
4. [ ] 确认驳回时删除对应Milvus灰度chunk，验证零残留
5. [ ] 确认删除知识库时级联删除release/audit表数据
6. [ ] 验证权限隔离：内测用户见灰度版标【测试】，普通用户只见旧版
7. [ ] 验证存量文档兼容性：无`release_status`视为published

### 额外建议

- 增加SQL初始化脚本，放在`script/`目录下，便于自动化部署
- DEV环境验证通过后，建议先在一个知识库做灰度测试，观察稳定性
